# Threat model

English | [Русский](../ru/THREAT_MODEL.md)

Built along the FSTEC methodology for assessing information security threats of 2021-02-05, with
typical threats checked against the FSTEC threat database. Written in plain words, without codes:
this is engineering work, not a certification exercise.

## What is protected

| Asset | Where it lives | What compromise costs |
|---|---|---|
| Session keys of the layers | memory of the relay process | confidentiality of messages passing that node |
| Node signing key | memory of the relay process (secmem), until the node restarts | the ability to impersonate the node until the certificate's not_after or the node restarts |
| Node onion key (agreement key) | memory of the relay process (secmem); with rotation one period as the published key and the grace period after it, without rotation until the node restarts | the layers of circuits set up under that key, for whoever kept their setup cells |
| Node link key | memory of the relay process (secmem), until the node restarts | the ability to answer a link in place of the node until it restarts; no layer and no recorded link opens with it. Without rotation it is the onion key as well |
| CA key | memory of the jimichi enroll process outside the cluster, only while it issues certificates | issuing certificates for any name and address until the anchor changes |
| Trust anchor (integrity) | ConfigMap jimichi-ca, client environment | a substituted anchor makes the client accept nodes of another CA |
| The link between sender and recipient | timings and volumes, node state | confidentiality of the fact of communication |
| Message content | cells on the network; for -peer clients end-to-end records in the mailbox queues and the plaintext only in the memory of the two clients; for a client without -peer the memory of the exit, which opens the last layer and reads the message | confidentiality of the conversation |
| Client identity key (static agreement key) | memory of the -peer client process (secmem), until it restarts | handshakes in the client's name with its contact, and kk1 forged as the contact's to the client itself (KCI); it opens no past record |
| Ratchet chains and record keys | memory of the -peer client (secmem): a chain until the next record of its direction, a record key for one operation | the next records of that direction until a new handshake |
| Fetch capability F | memory of the -peer client (secmem); a copy in every request, in clear at the mailbox | taking records off the client's queue: they cannot be read, but they can be kept from the client |
| Contact pin | memory of the -peer client for the process | a conversation with a substituted contact until a restart |
| Contact card (confidential to the contact) | memory of the client, the GET /card answer on loopback, memory of the contact | its holder can put records into the owner's queue and push out the contact's puts while the queue is full |

## Adversaries

| Adversary | Capability | What is available |
|---|---|---|
| Passive network observer | sees traffic at the entry and the exit of the chain | timings, volumes, packet sizes |
| Active network observer | additionally delays, duplicates and modifies cells, answers a connection in place of a node | attempts at replay and tampering, at taking the place of a node |
| Operator of one node | full access to their own node, including memory | one layer, the addresses of the neighbours; at the exit of a client without -peer also the message itself and the cover flag |
| Mailbox operator | full access to the node that keeps the queues of a conversation, including memory | per circuit the fetch capability F, the put queue, the time of every request, the outcome of a put, the kind and number of a record, the copies of one record; so it links the two circuits of one conversation. It sees neither the clients' addresses nor keys, content or message length, and with -cover-puts it cannot tell a real record from a dummy |
| Mailbox together with an observer of the entry links | the mailbox and a passive observer on the links from the clients to their entries | who talks to whom: the mailbox joins the two circuits through the queues, and the observer links each circuit to its entry by a correlation attack; the exit is pinned, so it is known which links to watch. How well this does is not measured ([#47](https://github.com/jimichi-org/jimichi/issues/47)) |
| Runtime administrator | root on the machine hosting a node, reads any process memory | node memory, including keys while they exist |
| Certificate authority owner | the operator who runs issuance, or whoever stole the CA key during issuance; issues valid certificates | a certificate for an identity of their own for any name and address, with a network position inserting their own node into a chain |

The adversary knows the design and the source code. Security rests on keys, not on the secrecy of
the implementation.

## Threats and countermeasures

| Threat | Countermeasure | How it is checked | Status |
|---|---|---|---|
| Reading keys from node memory | key buffers off the heap under mlock, dumps and ptrace disabled, zeroing after use. Copies the libraries keep on the heap are not covered (CRYPTO, known gaps) | secmem tests: the kernel marks the key pages as locked and excluded from dumps. In CI on Linux a test that cannot lock the pages or read their flags fails rather than skips. Planned ([#24](https://github.com/jimichi-org/jimichi/issues/24)): searching for the key in a process dump, with and without the measure | partly: the dump search is not implemented ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Keys reaching disk or swap | the node writes nothing to disk; on the testbed its root filesystem is read-only and its manifest declares no volumes. Key buffers are locked with mlock, which keeps them out of swap. The copies libraries keep on the heap are not locked and can reach swap (CRYPTO, known gaps); locking all process memory is planned ([#36](https://github.com/jimichi-org/jimichi/issues/36)) | secmem tests: the kernel marks the key pages as locked. In CI on Linux a test that cannot lock the pages or read their flags fails rather than skips. Planned ([#24](https://github.com/jimichi-org/jimichi/issues/24)): searching for the key in the container image, dumps and node files | partly: only the key buffers are locked ([#36](https://github.com/jimichi-org/jimichi/issues/36)), the search is not implemented ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Past sessions exposed after node keys are stolen | links between neighbours run on ephemeral keys, so a capture from the wire cannot be read without them. The onion key, which takes part in the layer agreement, changes by epochs (-onion-rotate), and a replaced key is released after the grace period: a setup cell kept by a neighbour opens only while its key is held, at most the rotation period plus the descriptor lifetime plus the clock allowance after the key was first published, counted by the wall clock and by the running time of the host, whichever ends first (LIMITATIONS). What remains: the hop keys of circuits that are alive when memory is taken; heap copies the libraries left of a released onion key, of setup secrets and of the hop keys of circuits already torn down, until that memory is reused (CRYPTO, known gaps); a node that cannot act, asleep or unable to make its next key; and a node without rotation, whose key lives until it restarts. The node signing key and the CA key take no part in the agreement | relay tests: a setup for a replaced key opens during the grace period and is refused after the release. Planned ([#24](https://github.com/jimichi-org/jimichi/issues/24)): attempting to open recorded setup cells with the keys found in node memory, by the age of the recording | partly: the test with keys taken from node memory is not implemented ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Linking sender and recipient by traffic | constant cell size, cover traffic, a constant rate at the client (-mode fixed), a random delay before each cell at the client (-jitter), sending on the node's own clock (-period). Random delays and batching at nodes are planned ([#45](https://github.com/jimichi-org/jimichi/issues/45), [#82](https://github.com/jimichi-org/jimichi/issues/82)) | our own correlation attack between the entry link and the last link between nodes: AUC, TPR at FPR 0.01 and top-1 under different parameters. A recipient client exists, but the attack is measured on the echo topology; measuring the topology of a conversation (two entries and the mailbox) is planned ([#47](https://github.com/jimichi-org/jimichi/issues/47)) | partly: no random delays or batching at nodes ([#45](https://github.com/jimichi-org/jimichi/issues/45), [#82](https://github.com/jimichi-org/jimichi/issues/82)) |
| One node learning the whole route | nested encryption; a node sees only its neighbours: the client connects to its entry alone and asks it for the bundles of every listed node, so the request does not show the chain, and for a circuit a node connects only to the next node. Not covered: a node can serve a different validly signed onion key to each of the others, and the key that opens a setup cell then tells it whose mirror the client used, so a rogue exit can learn the entry (LIMITATIONS) | e2e: per start of a client one relay answers a request for the mirror, and no relay a request for its own descriptor; wire and relay tests: one cell carries a different counter on every link, and a node before the exit sees the same header on a cover and a payload cell. Planned ([#117](https://github.com/jimichi-org/jimichi/issues/117)): compromising one node of a chain in the lab and checking what it holds (EXPERIMENT, block 3) | partly: the node compromise scenario is not implemented ([#117](https://github.com/jimichi-org/jimichi/issues/117)) |
| Node keys substituted when fetched | the signed descriptor: the client takes keys only from a bundle verified against the anchor, every bundle on its own; a listed bundle that fails the check counts as a node the entry left out, within -missing, and the entry's own bundle must pass, or the client refuses to build the circuit; the entry that serves the bundles can withhold them, and one it alters counts as withheld | e2e: a client holding the anchor of another CA refuses to build the circuit; pki tests for every refusal; client tests: a listed bundle that fails the check counts as left out within -missing, and an entry whose own bundle fails the check or is missing refuses the mirror, with a drawn and with a fixed chain | implemented |
| An active party between nodes takes the place of the next node | every link of a circuit is authenticated with the link key from the verified descriptor of the node it leads to; a node extends a circuit only to the nodes of its roster | relay tests: a setup naming an address outside the roster is refused without a connection; a responder without the expected link key fails the handshake and is sent no setup cell | implemented |
| A party or a parameter of a key agreement is replaced (a public key, the identity of a node, the link mode, the suite, the version) | the hash of the exchange transcript, the suite and the scheme version go into every agreement and into the derivation of every key: if the two sides differ in one byte of the transcript they get different keys, and the first AEAD check fails (CRYPTO, section "Key derivation"). When nodes are authenticated, the setup transcript and the transcript of an authenticated link also hold the identity key the node's certificate certifies, so a setup layer and a link open only at the node that holds the key and binds the same identity (CRYPTO, section "Transcript") | golden vectors in crypto/providertest for both suites, with and without an identity key; wire tests on both suites: a setup layer does not open with another onion key, hop index, link identifier or identity key, nor with the identity at one side only, and the keys of every hop of a chain are recomputed in the test from a transcript written out byte by byte; link tests on both suites: a changed mode byte, another link key at the responder, another identity key or one at one side only, and frame keys derived from one agreement alone fail the handshake, and an answer under a transcript written out byte by byte is accepted; relay tests on both suites: a chain delivers only through nodes that hold the keys and bind the identities named for them. An ephemeral key re-encoded on the way: in link on c25519 (the top bit of X25519), on GOST at the provider level (a point shifted by a point of order 4 gives another secret under its own transcript) | implemented |
| A node inserted through a compromised CA | the CA key lives outside the cluster and only while it issues certificates; the client draws the chain uniformly among its N listed nodes, so k rogue nodes hold both ends of a chain with probability k(k-1)/(N(N-1)) and some node of a chain of h nodes with 1 - C(N-k,h)/C(N,h), 0.1 and 0.9 for two rogue nodes of five and chains of three when the entry leaves no node out of its mirror (2/15 for both ends when a rogue entry leaves out one honest node, LIMITATIONS); layers are encrypted per node. Not covered: from one address the holder of the CA key can keep ordered pairs of honest nodes busy and so influence which chains survive (LIMITATIONS) | chains sampled with the client's own choice against these values, with full mirrors and with nodes left out of them (EXPERIMENT, block 3). Planned: inserting one and two nodes and measuring the residual leak ([#117](https://github.com/jimichi-org/jimichi/issues/117)), measuring what keeping pairs of honest nodes busy costs and how far it raises the share of surviving chains the rogue nodes hold ([#125](https://github.com/jimichi-org/jimichi/issues/125)) | partly: the measurements with inserted nodes and with pairs kept busy are not implemented ([#117](https://github.com/jimichi-org/jimichi/issues/117), [#125](https://github.com/jimichi-org/jimichi/issues/125)) |
| The chain revealed or steered by the node that serves the descriptors | the entry is asked for the bundles of every listed node whatever the chain, every one of them is verified on its own, the other hops are drawn after that from the system generator, and the client logs no node of the chain; the entry can withhold the mirror, and the client then exits and draws another entry (a -peer client only before its first circuit; on a rebuild it asks the same entry again until it exits after 10 min), or leave out at most -missing listed nodes, a listed bundle that fails the check counted among them, which bounds how far it steers the choice; a node that withholds its descriptor from the others only removes itself from their mirrors and from the nodes they extend a circuit to. A -peer client rebuilds its circuit through the same entry: first the same chain, and new middle hops only when that chain cannot be dialled, at most 2 times per process, so an entry that closes every circuit steers the middle hop at most three times (on the testbed the colluder ends up as the middle hop of a rogue entry with probability 7/8, and of a rogue mailbox that leaves the circuits through an honest middle hop unanswered with probability 19/27 under an honest entry, LIMITATIONS) | client tests: for one mirror the request and the log are the same whatever chain is drawn, a node off the chain that fails the check counts as left out within -missing, and the entry's own bundle that fails the check refuses the mirror; cmd/client tests: a rebuild goes through the same entry and the same chain, a rogue entry that closes every circuit and leaves its middle hop out of the mirror gets at most three draws, and enumerating every outcome gives 7/8, and 19/27 for a rogue mailbox; lab: chains sampled over mirrors that leave nodes out and over mirrors that lack withheld descriptors, the chosen chains that fail at setup counted apart, against the values the model gives (EXPERIMENT, block 3) | implemented |
| Linking a flow by cell headers | link encryption between neighbours, frames of one size on the wire; an identifier and a counter of its own on every link, counters strictly in turn | link tests: a capture of a link holds neither the counter nor the identifier of the cell it carried; wire and relay tests: one cell carries a different counter on every link, in both directions | implemented |
| Replay and tampering | On the wire a link frame is sealed with an AEAD whose nonce is the frame number: a copied or altered frame does not open and the circuit on that link closes. Inside the circuit there is an AEAD on every layer (the random fill after a layer is outside it and the next node replaces it) and counters go strictly in turn on every link. Forward, a node opens its layer and only then takes the counter: a cell that does not open is dropped and takes no turn, while a copy, a gap or a reorder of genuine cells closes the circuit. Backward, a node cannot open the layers and checks only the kind and the counter order, so a reply with an altered body travels on to the client. The client checks every reply, cover and payload alike: the header (version, kind, the identifier of its own link), every layer, the number strictly next, and no more replies than the cells it wrote. The first reply that fails a check closes the circuit; a client without -peer exits and builds a new circuit after its restart, a -peer client rebuilds it through the same entry and exits with code 3 after three such replies within 10 min (ARCHITECTURE, "The -peer client"). Control cells: a node keeps the tags of those it opened for as long as it holds the onion key that opened them, and a copy that carries another encoding of the ephemeral key does not open the layer: the bytes of the key are part of the setup transcript. For -peer clients the content is under the end-to-end layer: a record the mailbox or a node changed does not open at the recipient and is dropped, and a mailbox reply is parsed strictly. Not covered: the exit of a client without -peer opens the last layer and can replace the content of a message and of a reply; a reply that never arrives is not noticed by these checks, only by waiting for it; a node of the chain with a single cell, or a party on the wire with a damaged frame, closes the circuit, which is a denial of service (LIMITATIONS) | link tests: a copied frame and a frame with an altered byte do not open, and after a frame that does not open the link takes no genuine one either; wire tests: a cell with an altered body, counter or kind does not open, nor does a copy of a control cell with another encoding of the ephemeral key; relay tests: a copy, a gap and a step back close the circuit in either direction, backward a far counter and a cell of another kind do too, a forward cell that does not open is dropped without closing, a copy of a control cell is refused; client tests: a reply with an altered bit in any of its 512 bytes is refused, an altered reply, a copied reply, replies out of order or with a gap and a reply too many close the circuit at the first such cell, replies in turn, cover included, do not, and a frame from the entry that does not open closes it as well | implemented |
| Proving that a message was sent | cover and payload cells have the same size and header for every node before the exit, and the frames on the wire are of one size: the cover flag sits inside the innermost layer. The moment of sending is hidden only at a constant rate (-mode fixed, set on the testbed): in the immediate mode, the default of the client, a cell leaves when the user sends, and without -cover every data cell is a message. A -peer client sends a request on every tick, and from the mailbox the moment of sending is hidden only with -cover-puts (the default), once the session is established and while the contact fetches: otherwise a put comes only with a real record, and a refused put shows that the contact does not fetch (LIMITATIONS) | wire and relay tests: a node before the exit sees the same header on a cover and a payload cell, and the exit answers each with one cell. Planned ([#119](https://github.com/jimichi-org/jimichi/issues/119)): distinguishing the two kinds from observable features, expecting chance level | partly: the distinguisher is not implemented ([#119](https://github.com/jimichi-org/jimichi/issues/119)), the moment of sending is hidden only at a constant rate |
| Proving authorship to a third party | deniable authentication in the end-to-end layer: a KK handshake made of key agreements only, records under shared keys, no signing key at the client (CRYPTO, "Signatures" and "Deniability"). The recipient is convinced of the author by a shared secret, but can compute every value of the transcript itself, without the sender's key, so a transcript together with the recipient's keys does not prove the sender's participation to a third party. Not covered: a transcript witnessed by a mailbox or an observer of the sender's link colluding with the recipient, online deniability and metadata (the "Deniability" section below) | `cmd/lab -set deny` on both suites with the recipient in both roles: the recipient forges the conversation with the production session code, the genuine and the forged transcript pass one check and have the same structure, a forgery made with a fresh key in place of the recipient's fails the check at its first record, a provider wrapper sees the sender's private key in the genuine session and sees it neither in the forgery nor in the checks; lab/scenario tests on the same, and a forgery with the sender's key wiped beforehand; noise and e2e tests: not a single signing call | implemented in the end-to-end layer (noise, e2e): offline deniability for both parties; on the testbed the layer is used by the -peer clients |
| Coercion after the session | ephemeral key buffers are zeroed, the node writes no key to disk; library copies on the heap live until the memory is reused and are not locked against swap ([#36](https://github.com/jimichi-org/jimichi/issues/36)). A -peer client holds its identity key, F and the ratchet chains in secmem until the process restarts and writes none of them to disk; a surrendered identity key opens only future handshakes, and the current ratchet chain only the future records of its direction | relay tests: a node holds no cipher of a circuit once it is closed; e2e tests: a live session holds exactly two chain keys, one per direction, and Close releases every key. Planned ([#24](https://github.com/jimichi-org/jimichi/issues/24)): searching memory and disk for the key after the session ends | partly: the search after a session is not implemented ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Reading and replacing messages at the exit | for -peer clients the end-to-end layer: a KK handshake between the static keys of the pinned cards, a hash ratchet per direction, a record of 392 bytes under an AEAD with a body of up to 368 bytes; the exit is a mailbox that holds records only (CRYPTO, "End-to-end layer") | KK golden vectors for both suites; e2e tests: a changed or foreign record does not open, a copy and a late record are dropped, and none of them changes the session; conversation tests: a conversation through relays with the mailbox at the exit; cmd/client tests: two -peer processes talk through a mailbox; e2e.sh: a round trip between client-a and client-b through relay-5 | implemented |
| Substituted contact card | the card is served only by the admin port on loopback through a port-forward, its hash is checked against the card_hash line in the log of the same container, the whole card is pinned for the process; another card after pinning gives 409 and the stopped state until the operator restarts the client | cmd/client tests: the order of the checks of PUT /contact, the stopped state, 409 to everything after it, the 409 flushed before the stop, the conversation, the identity key and F released by the stop, and no further request of a stopped process at the mailbox; scripts tests: introduce.sh refuses a log without a card_hash line or with two, a card with another hash at either client, a 409 to its PUT, a log without the pin of the card it put and a container restart during the introduction, and the refusal check of e2e.sh runs against stand-ins; e2e.sh: the card of a foreign key and then the previous card get 409, and the client does not restart | partly: before the pin the introduction trusts the kube API ([#90](https://github.com/jimichi-org/jimichi/issues/90), LIMITATIONS) |
| Linking the two circuits of a conversation at the mailbox | none: the mailbox sees the fetch queue and the put queue of every circuit | | not covered ([#84](https://github.com/jimichi-org/jimichi/issues/84), [#96](https://github.com/jimichi-org/jimichi/issues/96)) |
| Linking client-a and client-b by the mailbox together with an observer of the entry links | a request of a constant length on every tick, a put in every request (-cover-puts), own-clock sending at the nodes | not measured: the correlation attack runs on the echo topology ([#47](https://github.com/jimichi-org/jimichi/issues/47)) | not measured ([#47](https://github.com/jimichi-org/jimichi/issues/47)) |
| Past messages of a client exposed | the hash ratchet: a record key lives for one operation, the previous chain key is wiped at each step, skipped keys are not kept | e2e tests: the ratchet in order and with a gap, a live session holds exactly two chain keys | partly: no post-compromise recovery, no DH ratchet (LIMITATIONS) |
| Denial of service against a conversation | the circuit rebuilt through the same entry with a bound on draws of the middle hops, a new handshake after the session goes stale, a bad mailbox reply does not close the circuit | conversation tests: rebuild, recovery by a new handshake, bad replies; cmd/client tests: the bound on draws of the middle hops, held by a rogue entry and a rogue mailbox alike, and a client process that exits with code 3 after three refused replies and with code 1 when no circuit can be built again | not prevented: any node of either circuit or the mailbox stops the conversation while it keeps at it (LIMITATIONS) |

## Deniability: what is claimed and what is not

Three properties are claimed, all within the limits named below. Deniability of sending and
having nothing to surrender after a session are not measured yet, the measurements are planned.
Deniable authentication follows from the design of the handshake and is shown by forging a
conversation, not measured:

- Deniability of sending: an observer cannot tell a cell carrying a message from a cover cell, so
  it cannot prove that the user sent anything at that moment. This holds when the client sends at
  a constant rate (-mode fixed): in the immediate mode, the default, a cell leaves when the user
  sends, and without -cover every data cell is a message. The distinguisher that will measure the
  property is planned ([#119](https://github.com/jimichi-org/jimichi/issues/119)).
- Offline deniable authentication for both parties of the end-to-end layer. The recipient is
  sure of the author: the record keys need either the sender's key or its own. But a session
  transcript, even together with the recipient's private keys, does not prove the sender's
  participation to a third party unless the judge holds an independent trusted record of who
  transmitted these ciphertexts and when: the recipient builds a transcript with the same
  plaintexts, distributed like the genuine one, by itself (CRYPTO, "Deniability"), and
  `cmd/lab -set deny` does so with the production session code. A mailbox or an observer of the
  sender's link colluding with the recipient lifts the condition: a log of put requests by
  circuit together with the binding of a circuit to the sender's address (through the entry or a
  correlation attack) is a witnessed transcript, and the simulation does not cover it.
- Nothing to surrender after the session: keys are ephemeral, their buffers are zeroed, and a node
  writes no key to disk. The copies libraries leave on the heap are not locked and on a host with
  swap can be paged out to disk before that memory is reused (LIMITATIONS). How long those copies
  survive is to be measured, not assumed ([#24](https://github.com/jimichi-org/jimichi/issues/24));
  locking all process memory is planned ([#36](https://github.com/jimichi-org/jimichi/issues/36)).

Not claimed for authentication: online deniability, that is against a judge acting together with
the recipient during the session; deniability of metadata: mailbox records of requests, network
observations, the moments circuits are set up and torn down; a witnessed transcript; a sender's
device compromised before the session.

Not claimed: hidden volumes and a second bottom in storage. Such schemes fall to an adversary
holding several snapshots of the state over time and give no verifiable guarantee. The nodes store
nothing at all, so the property is not needed there. The client stores nothing either for now: its
container with two volumes is planned ([#20](https://github.com/jimichi-org/jimichi/issues/20)),
and LIMITATIONS states where the deniability of such a container ends.

## Out of scope

- Compromise of the user's device and client.
- A global observer seeing all traffic of all participants at once.
- Side-channel attacks on the primitive implementations.
- Denial of service beyond the node limits: a node gives one address at most its share of links,
  handshakes and setups and bounds the life of circuits (ARCHITECTURE, node limits; the numbers
  are in LIMITATIONS). Every node keeps the per-address limits, since any node can be an entry;
  the circuits a node forwards share one address's allowance at the next node. On the testbed a
  cell port takes connections from client and relay pods only (where the network plugin enforces
  network policies). Load from enough addresses to fill the global caps, filling the setup-tag
  cache of an onion key (about 91 hours from one address, about 90 addresses within one rotation
  period of the testbed), one address that keeps several ordered pairs of nodes busy and so
  influences which chains survive (LIMITATIONS), a node that refuses the circuits it does not
  like, and stopping a node are neither prevented nor measured.
- Denial of service against a mailbox beyond the binding of circuits to queues and the eviction:
  filling queues and records from many addresses, holding queues with open circuits (the numbers
  are in LIMITATIONS).
- Analysis requiring long-term statistics on real users: the testbed dataset is synthetic.
