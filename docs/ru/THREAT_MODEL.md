# Модель угроз

[English](../en/THREAT_MODEL.md) | Русский

Модель построена по методике оценки угроз безопасности информации ФСТЭК России от 05.02.2021,
типовые угрозы сверены с банком данных угроз ФСТЭК. Изложение словами, без кодов: работа
инженерная, а не аттестационная.

## Что защищаем

| Актив | Где находится | Что теряем при компрометации |
|---|---|---|
| Сессионные ключи слоёв | память процесса relay | конфиденциальность сообщений, прошедших через узел |
| Ключ подписи узла | память процесса relay (secmem), до перезапуска узла | возможность выдать себя за узел до not_after сертификата или перезапуска узла |
| Онион-ключ узла (ключ согласования) | память процесса relay (secmem); с ротацией один период как опубликованный ключ и льготный период после него, без ротации до перезапуска узла | слои цепочек, установленных под этим ключом, для того, кто сохранил их служебные ячейки |
| Ключ канала узла | память процесса relay (secmem), до перезапуска узла | возможность отвечать на канал вместо узла до его перезапуска; ни один слой и ни один записанный канал им не открывается. Без ротации он же онион-ключ |
| Ключ УЦ | память процесса jimichi enroll вне кластера, только на время выпуска сертификатов | выпуск сертификатов на любые имя и адрес до смены якоря |
| Якорь доверия (целостность) | ConfigMap jimichi-ca, окружение клиента | подменённый якорь заставляет клиента принять узлы чужого УЦ |
| Связь отправителя и получателя | тайминги и объёмы трафика, состояние узла | конфиденциальность самого факта общения |
| Содержимое сообщений | ячейки в сети; у клиентов -peer записи сквозного слоя в очередях mailbox и открытый текст только в памяти двух клиентов; у клиента без -peer память выхода, который снимает последний слой и читает сообщение | конфиденциальность переписки |
| Ключ личности клиента (статический ключ согласования) | память процесса клиента -peer (secmem), до его перезапуска; контейнер клиента выводит его из пароля тома и файла при каждом открытии, в файле его нет | рукопожатия от имени клиента с его контактом и подделка kk1 от контакта для самого клиента (KCI); прошлых записей он не открывает |
| Цепочки ратчета и ключи записей | память клиента -peer (secmem): цепочка до следующей записи своего направления, ключ записи на одну операцию | следующие записи этого направления до нового рукопожатия |
| Право забора F | память клиента -peer (secmem); копия в каждой заявке, у mailbox в открытом виде; контейнер выводит его так же, как ключ личности | снятие записей из очереди клиента: прочесть их нельзя, но можно не дать их получить |
| Закрепление контакта | память клиента -peer на процесс; в контейнере карточка контакта лежит в томе навсегда для этого контейнера | разговор с подменённым контактом: без контейнера до перезапуска; карточка, записанная в контейнер, остаётся на всё время жизни этого контейнера (клиент с -vault в плане), и выход только через новый контейнер |
| Карточка контакта (конфиденциальна для контакта) | память клиента, ответ GET /card на loopback, память контакта | держатель кладёт записи в очередь владельца и вытесняет put контакта, пока очередь полна |
| Файл контейнера клиента | диск устройства клиента: соль и две запечатанные области, в записанном томе карточка контакта; ключей в файле нет | вместе с паролем тома ключ личности и F этого тома (выводом) и его карточку контакта, то есть с кем владелец говорит; без пароля только то, что это контейнер. Порча файла лишает владельца открытия |
| Пароль тома | у владельца; на время открытия в памяти процесса (secmem) | вместе с файлом равен ключу личности и F тома: выдать себя за владельца перед контактом, забрать и удалить записи его очереди, увидеть связь с контактом. Без файла не даёт ничего: соль только в файле |

## Нарушители

| Нарушитель | Возможности | Что ему доступно |
|---|---|---|
| Пассивный наблюдатель сети | видит трафик на входе и выходе цепочки | тайминги, объёмы, размеры пакетов |
| Активный наблюдатель сети | дополнительно задерживает, дублирует, подменяет ячейки, отвечает на соединение вместо узла | попытка навязать повтор и подмену, встать на место узла |
| Оператор одного узла цепочки | полный доступ к своему узлу, включая память | один слой, адреса соседей; на выходе клиента без -peer ещё само сообщение и признак фоновой ячейки |
| Оператор mailbox | полный доступ к узлу, который держит очереди разговора, включая память | по каждой цепочке право забора F, очередь put, время каждой заявки, исход put, вид и номер записи, копии одной записи; поэтому связывает две цепочки одного разговора. Не видит адресов клиентов, ключей, содержимого и длины сообщений; настоящую запись от фиктивной при -cover-puts не отличает |
| mailbox вместе с наблюдателем каналов входов | mailbox и пассивный наблюдатель на каналах от клиентов к их входам | кто с кем говорит: mailbox склеивает две цепочки через очереди, а наблюдатель связывает каждую цепочку с её входом атакой корреляции; выход закреплён, поэтому известно, какие каналы смотреть. Успех не измерен ([#47](https://github.com/jimichi-org/jimichi/issues/47)) |
| Администратор среды выполнения | root на машине с узлом, чтение памяти любого процесса | память узла, включая ключи, пока они существуют |
| Владелец удостоверяющего центра | оператор, запускающий выдачу, или тот, кто украл ключ УЦ за время выпуска; выпускает валидные сертификаты | сертификат своей личности на любые имя и адрес, при позиции в сети подстановка своего узла в цепочку |
| Изъявший файл контейнера | файл в одном состоянии; под принуждением пароль одного тома; перебор паролей офлайн | что это контейнер (флаг, путь, размер 8224 байта) и по метаданным файловой системы момент создания; с паролем карточку контакта тома, а ключ личности и F выводом. Не узнаёт, есть ли второй том: при допущениях CRYPTO ("Контейнер") и только для сгенерированного пароля второго тома. Знающий ПО потребует второй пароль: у любого контейнера две области |
| Нарушитель с несколькими состояниями файла | изъятия в разные дни, резервные копии, синхронизация | ничего сверх одного состояния: после создания файл не меняется |
| Активный нарушитель между изъятиями | запись в файл между двумя изъятиями | может испортить любую область или подменить другую область свежим пустым томом; изменённый том не открывается, а реакция владельца на подмену выдаёт том при следующем изъятии (раздел "Контейнер клиента") |

Предполагается, что нарушитель знает устройство системы и исходный код: стойкость держится
на ключах, а не на секретности реализации.

## Угрозы и что им противопоставлено

| Угроза | Мера | Проверяется | Статус |
|---|---|---|---|
| Чтение ключей из памяти узла | буферы ключей вне кучи под mlock, запрет дампов и ptrace, зануление после использования. Копии, которые библиотеки держат на куче, мера не покрывает (CRYPTO, известные дыры) | тесты secmem: ядро помечает страницы ключей как заблокированные и исключённые из дампов. В CI на Linux тест, который не может заблокировать страницы или прочитать их флаги, падает, а не пропускается. В плане ([#24](https://github.com/jimichi-org/jimichi/issues/24)): поиск ключа в дампе процесса, со включённой мерой и без | частично: поиска в дампе нет ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Ключи попадают на диск или в swap | узел не пишет на диск; на стенде его корневая файловая система только для чтения, томов в манифесте нет. Буферы ключей заблокированы через mlock и в swap не выгружаются. Копии, которые библиотеки держат на куче, не заблокированы и могут попасть в swap (CRYPTO, известные дыры); блокировка всей памяти процесса в плане ([#36](https://github.com/jimichi-org/jimichi/issues/36)). Клиент ключей на диск тоже не пишет. Контейнер клиента пишет на диск только соль и зашифрованную карточку контакта; файл и пароль тома воспроизводят ключ личности и F (строки о контейнере ниже) | тесты secmem: ядро помечает страницы ключей как заблокированные. В CI на Linux тест, который не может заблокировать страницы или прочитать их флаги, падает, а не пропускается. Тесты vault: ни в файле, ни в расшифрованных областях нет байтов ключа личности, F, k_s, W, K_b и пароля. В плане ([#24](https://github.com/jimichi-org/jimichi/issues/24)): поиск ключа в образе контейнера, дампе и файлах узла | частично: заблокированы только буферы ключей ([#36](https://github.com/jimichi-org/jimichi/issues/36)), поиска нет ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Раскрытие прошлых сессий после кражи ключей узла | каналы между соседями на эфемерных ключах: запись с провода без них не читается. Онион-ключ, который участвует в согласовании слоя, меняется по эпохам (-onion-rotate), а заменённый ключ освобождается после льготного периода: служебная ячейка, сохранённая соседом, открывается, только пока узел держит её ключ, не дольше периода ротации плюс срок дескриптора плюс допуск часов после первой публикации ключа, по настенным часам и по времени работы хоста, смотря что кончится раньше (LIMITATIONS). Что остаётся: ключи хопа цепочек, живых в момент снятия памяти; копии на куче, которые библиотеки оставили от освобождённого онион-ключа, от секретов установки и от ключей хопа уже разорванных цепочек, до повторного использования этой памяти (CRYPTO, известные дыры); узел, который не может действовать, спящий или неспособный создать следующий ключ; и узел без ротации, чей ключ живёт до перезапуска. Ключ подписи узла и ключ УЦ в согласовании не участвуют | тесты relay: установка под заменённый ключ открывается в льготный период и отклоняется после освобождения. В плане ([#24](https://github.com/jimichi-org/jimichi/issues/24)): попытка открыть записанные служебные ячейки ключами, найденными в памяти узла, в зависимости от возраста записи | частично: проверки ключами из памяти узла нет ([#24](https://github.com/jimichi-org/jimichi/issues/24)) |
| Связывание отправителя и получателя по трафику | постоянный размер ячейки, фоновый трафик, постоянная скорость у клиента (-mode fixed), случайная задержка перед каждой ячейкой у клиента (-jitter), отправка по своим часам узла (-period). Случайные задержки и пакетирование на узлах в плане ([#45](https://github.com/jimichi-org/jimichi/issues/45), [#82](https://github.com/jimichi-org/jimichi/issues/82)) | собственная атака корреляции между каналом входа и последним каналом между узлами: AUC, TPR при FPR 0,01 и top-1 при разных параметрах. Клиент-получатель есть, но атака измеряется на эхо-топологии; измерение топологии разговора (два входа и mailbox) в плане ([#47](https://github.com/jimichi-org/jimichi/issues/47)) | частично: случайных задержек и пакетирования на узлах нет ([#45](https://github.com/jimichi-org/jimichi/issues/45), [#82](https://github.com/jimichi-org/jimichi/issues/82)) |
| Один узел цепочки узнаёт весь маршрут | вложенное шифрование; узел видит только соседей: клиент соединяется только со своим входом и просит у него комплекты всех узлов списка, поэтому запрос не показывает цепочку, а узел ради цепочки соединяется только со следующим узлом. Не покрыто: узел может отдать каждому из остальных свой действующий подписанный онион-ключ, и ключ, открывший служебную ячейку, покажет ему, чьим зеркалом пользовался клиент, так что подставной выход может узнать вход (LIMITATIONS) | e2e: на каждый запуск клиента один relay отвечает на запрос зеркала, и ни один relay не отвечает на запрос своего дескриптора; тесты wire и relay: у одной ячейки на каждом канале свой counter, узел до выхода видит одинаковый заголовок у фоновой и полезной ячейки. Что знает один узел, следующий протоколу и отдающий всем один онион-ключ, выведено из протокола: он знает позицию перед собой, свою и следующую, поэтому при трёх хопах вход эха называет 3 из 4 позиций маршрута, середина 3, выход 2, а на стороне клиента -peer вход 3 из 3, середина 2, mailbox 1; при одном подставном узле из пяти средняя доля восстановленного маршрута эха 2/5, тесты метрик перебирают все цепочки (EXPERIMENT, блок 3). Что видят и связывают узлы стенда, не измерено ([#117](https://github.com/jimichi-org/jimichi/issues/117)) | частично: вид узла выведен из протокола, на стенде не измерен ([#117](https://github.com/jimichi-org/jimichi/issues/117)) |
| Подмена ключей узлов при получении | подписанный дескриптор: клиент берёт ключи только из комплекта, проверенного по якорю, каждый комплект проверяется отдельно; комплект узла списка, не прошедший проверку, считается узлом, которого вход не отдал, в пределах -missing, а комплект самого входа обязан пройти проверку, иначе клиент отказывается строить цепочку; вход, который отдаёт комплекты, может их не отдать, а изменённый им комплект считается неотданным | e2e: клиент с якорем чужого УЦ отказывается строить цепочку; тесты pki на каждый отказ; тесты клиента: комплект узла списка, не прошедший проверку, считается исключённым в пределах -missing, а вход, чей собственный комплект не прошёл проверку или отсутствует, означает отказ от зеркала, при случайной и при фиксированной цепочке | реализовано |
| Активный нарушитель между узлами встаёт на место следующего узла | каждый канал цепочки аутентифицирован ключом канала из проверенного дескриптора узла, к которому он ведёт; узел продолжает цепочку только на узлы своего ростера | тесты relay: установка с адресом вне ростера отклоняется без соединения; ответчик без ожидаемого ключа канала не проходит рукопожатие, и служебная ячейка ему не отправляется | реализовано |
| Подмена стороны или параметров согласования ключей (открытый ключ, личность узла, режим канала, набор, версия) | хэш транскрипта обмена, набор и версия схемы входят в каждое согласование и в вывод каждого ключа: если у сторон различается хоть один байт транскрипта, они получают разные ключи, и первая же проверка AEAD не проходит (CRYPTO, раздел "Вывод ключей"). При аутентификации узлов в транскрипт установки и аутентифицированного канала входит и ключ личности, который заверяет сертификат узла, поэтому слой установки и канал открываются только у узла, который держит ключ и привязывает ту же личность (CRYPTO, раздел "Транскрипт") | золотые векторы crypto/providertest для обоих наборов, с ключом личности и без него; тесты wire на обоих наборах: слой установки не открывается с другим онион-ключом, номером узла, идентификатором канала или ключом личности, ни с личностью только у одной стороны, а ключи каждого узла цепочки пересчитаны в тесте по транскрипту, выписанному побайтно; тесты link на обоих наборах: изменённый байт режима, другой ключ канала у ответчика, другой ключ личности или личность только у одной стороны и ключи кадров, выведенные только из одного согласования, дают отказ рукопожатия, а ответ по транскрипту, выписанному побайтно, принимается; тесты relay на обоих наборах: цепочка доставляет только через узлы, которые держат ключи и привязывают названные для них личности. ## Отрицаемость: что заявляем и чего не заявляем

Заявляем три свойства, все в границах, названных ниже. Отрицание факта отправки и отсутствие ключей
после сессии не измерены: для первого различитель есть, но меряет он узлы без отправки по своим
часам, а не настройку, при которой свойство заявлено, для второго измерение в плане. Отрицаемая
аутентификация следует из устройства рукопожатия и показана подделкой переписки, а не измерена:

- Отрицание факта отправки: наблюдатель не отличает ячейку с сообщением от фоновой, поэтому не может
  доказать, что пользователь в этот момент отправлял сообщение. Это верно, когда клиент шлёт с
  постоянной скоростью (-mode fixed) и узлы отправляют по своим часам (-period): в немедленном
  режиме, а он по умолчанию, ячейка уходит, когда пользователь отправляет, и без -cover каждая
  ячейка данных это сообщение, а без -period момент ответа выхода зависит от вида ячейки
  (LIMITATIONS). При -mode fixed с -period свойство следует из устройства и не измерено:
  различитель ячеек (EXPERIMENT, блок 7, `cmd/lab -set cover`), только для клиента без -peer,
  меряет постоянную скорость с узлами, которые пересылают сразу, а там момент ответа выхода зависит
  от вида ячейки; чисел до его серии нет ([#23](https://github.com/jimichi-org/jimichi/issues/23)).
- Офлайн-отрицаемая аутентификация для обеих сторон сквозного слоя. Получатель уверен в авторе:
  ключи записей требуют либо ключа отправителя, либо его собственного. Но транскрипт сессии, даже
  вместе с закрытыми ключами получателя, не доказывает третьему лицу участия отправителя, если у
  судьи нет независимой доверенной записи о том, кто и когда передал эти шифротексты: получатель
  сам строит транскрипт с теми же открытыми текстами, распределённый так же, как настоящий
  (CRYPTO, "Отрицаемость"), и `cmd/lab -set deny` делает это производственным кодом сессии.
  Mailbox или наблюдатель канала отправителя в сговоре с получателем это условие снимают: журнал
  заявок put по цепочкам вместе с привязкой цепочки к адресу отправителя (через вход или атаку
  корреляции) это засвидетельствованный транскрипт, и симуляция его не покрывает.
- Нечего выдать после сессии: ключи эфемерные, их буферы зануляются, сам узел ключей на диск
  не пишет. Клиент -peer держит ключ личности, F и текущие цепочки до конца процесса; их выдача
  открывает только будущие рукопожатия и будущие записи (строка о принуждении после сессии).
  Контейнер клиента ключей не хранит, но выданный пароль тома вместе с файлом отдаёт ключ
  личности и F, выведенные из них, то есть личность всех запусков клиента с этим контейнером
  (клиент -peer с -vault в плане). Копии, которые библиотеки оставляют на куче, не
  заблокированы и на хосте со swap могут быть выгружены на диск раньше, чем эту память займут
  снова (LIMITATIONS). Сколько живут эти копии, будет измерено, а не предположено
  ([#24](https://github.com/jimichi-org/jimichi/issues/24));
  блокировка всей памяти процесса в плане ([#36](https://github.com/jimichi-org/jimichi/issues/36)).

Не заявляем для аутентификации: онлайн-отрицаемость, то есть против судьи, который во время
сессии действует вместе с получателем; отрицаемость метаданных: записи mailbox о заявках,
наблюдения сети, моменты установки и разрыва цепочек; засвидетельствованный транскрипт;
устройство отправителя, скомпрометированное до сессии.

## Контейнер клиента: что заявляем и чего не заявляем

Контейнер клиента (ARCHITECTURE, "Контейнер клиента") заявляет, в границах ниже:

- файл в одном состоянии и пароль одного тома не выдают, есть ли второй том: при допущениях
  растяжения PasswordKey в модели случайного оракула, IND-CPA AEAD с одноразовым ключом и PRF
  DeriveKey и только для сгенерированного пароля второго тома, не меньше 80 бит (CRYPTO,
  "Контейнер"). Различитель, которым это будет измерено, в плане
  (EXPERIMENT, блок 5);
- состояния файла после создания совпадают байт в байт: файл пишется один раз, поэтому
  несколько состояний не дают ничего сверх одного. Трасса состояний в плане (EXPERIMENT, блок 5);
- целостность открываемого тома: изменённый том не открывается;
- в файле нет ключевого материала, даже зашифрованного; при этом файл и пароль тома
  воспроизводят ключ личности и F;
- при допущении PRF DeriveKey и DerivePair карточка, построенная из тома, неотличима от
  карточки клиента -peer без контейнера (CRYPTO, "Карточка"), поэтому ни контакт, ни mailbox по
  ней о контейнере не узнают.

Неотличимость файла без пароля от случайных байт держится только при допущении IND$, для
Кузнечик-MGM оно не доказано.

Не заявляем: утверждение для пароля, выбранного человеком; защиту от принуждения: ПО известно
двумя областями, и принуждающий потребует второй пароль, поэтому второй том это легенда, а не
иммунитет, а легенда правдоподобна, только если ею пользуются: неактивная очередь легенды и
молчащий контакт её выдают; момент создания по метаданным файловой системы; остаток неудачного
создания; окружение (времена строк журнала, mailbox, история оболочки); работающий клиент, swap и
файл подкачки; обновляемый контейнер с историей сообщений
([#159](https://github.com/jimichi-org/jimichi/issues/159)). Узлы ничего не хранят, поэтому им
это свойство не нужно. Границы в LIMITATIONS.

Совет владельцу: ErrNoVolume на пароле, который раньше открывал том, может значить порчу или
подмену файла между изъятиями. Контейнер на том же устройстве тогда не пересоздают: новый файл
вместо прежнего покажет при следующем изъятии, что второй том был.

## Вне модели

- Компрометация работающего устройства пользователя и его клиента. Файл контейнера в покое,
  изъятый или скопированный, в модели (раздел "Контейнер клиента").
- Глобальный наблюдатель, который видит весь трафик всех участников одновременно.
- Атаки по сторонним каналам на реализацию примитивов.
- Отказ в обслуживании сверх ограничений узла: узел даёт одному адресу не больше его доли
  каналов, рукопожатий и установок и ограничивает время жизни цепочек (ARCHITECTURE,
  ограничения узла; числа в LIMITATIONS). Каждый узел держит ограничения на один адрес, потому
  что входом может быть любой узел; цепочки, которые узел пересылает, делят у следующего узла
  запас одного адреса. На стенде порт ячеек принимает соединения только от подов клиентов и подов
  relay (там, где сетевой плагин применяет сетевые политики). Нагрузка с числа адресов,
  достаточного для общих пределов, заполнение кэша меток онион-ключа (около 91 часа с одного
  адреса, около 90 адресов за один период ротации на стенде), один адрес, который держит
  занятыми несколько упорядоченных пар узлов и так влияет на то, какие цепочки выживут
  (LIMITATIONS), узел, который отказывает неугодным ему цепочкам, и остановка узла не
  предотвращаются и не измеряются.
- Отказ в обслуживании mailbox сверх привязки цепочек к очередям и вытеснения: заполнение
  очередей и записей с многих адресов, удержание очередей открытыми цепочками (числа в
  LIMITATIONS).
- Анализ, требующий длительного накопления статистики по реальным пользователям: датасет стенда
  синтетический.
