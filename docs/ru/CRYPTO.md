# CryptoProvider

[English](../en/CRYPTO.md) | Русский

Статус: оба набора реализованы и проходят providertest. По умолчанию c25519: результаты
сравнимы с зарубежными работами. ГОСТ второй набор, сравнивается с основным по стоимости.
Набор выбирается флагом -suite у узла, клиента и стенда; узел публикует свой набор вместе с
ключом, клиент с другим набором не стартует.

## Операции

| Операция | ГОСТ (crypto/gost) | По умолчанию (crypto/c25519) |
|---|---|---|
| Эфемерная пара | ГОСТ Р 34.10-2012, 256 бит, paramSetA (TC26) | X25519 |
| Согласование | VKO_GOSTR3410_2012_256 (Р 50.1.113-2016; RFC 7836, 4.3.1), UKM из хэша транскрипта, затем KDF | X25519, затем HKDF-SHA-256 с хэшем транскрипта |
| KDF | KDF_GOSTR3411_2012_256 (Р 50.1.113-2016; RFC 7836, 4.5) | HKDF-SHA-256 (RFC 5869) |
| AEAD | Кузнечик-MGM (Р 1323565.1.026-2019), nonce 16 байт, тег 16 | XChaCha20-Poly1305, nonce 24, тег 16 |
| Подпись | ГОСТ Р 34.10-2012, 256 бит | Ed25519 |
| Хэш | Стрибог-256 | SHA-256 |
| Пара из секрета | KDF_GOSTR3411_2012_256 с номером кандидата в seed, выборка скаляра в [1, q-1] с отказом | HKDF-SHA-256 (формула DeriveKey), обрезка скаляра RFC 7748 |
| Ключ из пароля | PBKDF2 (Р 50.1.111-2016; RFC 8018) с HMAC_GOSTR3411_2012_512 | Argon2id (RFC 9106), t = 3, 64 МиБ, p = 4 |

Различие размеров nonce и накладных расходов видно через интерфейс: wire не хардкодит размеры.

## Интерфейс

```go
type Suite uint8

type CryptoProvider interface {
	Suite() Suite

	GenerateEphemeral() (priv *secmem.Buffer, pub []byte, err error)
	Agree(priv *secmem.Buffer, peerPub []byte, ctx Context) (*secmem.Buffer, error)
	MixKey(chain, secret *secmem.Buffer, ctx Context) (*secmem.Buffer, error)
	DeriveKey(secret *secmem.Buffer, purpose string, ctx Context, size int) (*secmem.Buffer, error)
	KeySize() int

	DerivePair(secret *secmem.Buffer, ctx Context) (priv *secmem.Buffer, pub []byte, err error)
	PasswordKey(password *secmem.Buffer, ctx Context) (*secmem.Buffer, error)

	NewAEAD(key *secmem.Buffer) (AEAD, error)

	GenerateSigning() (priv *secmem.Buffer, pub []byte, err error)
	Sign(priv *secmem.Buffer, msg []byte) ([]byte, error)
	Verify(pub, msg, sig []byte) bool

	Hash(data ...[]byte) []byte
}

type AEAD interface {
	NonceSize() int
	Overhead() int
	Seal(dst, nonce, plaintext, ad []byte) []byte
	Open(dst, nonce, ciphertext, ad []byte) ([]byte, error)
	// Destroy drops the cipher; whether its key copy is wiped depends on the library.
	Destroy()
}

const ContextSize = 32

type Context struct{ /* набор и хэш транскрипта */ }

func NewContext(p CryptoProvider, exchange string, parts ...[]byte) (Context, error)
func (c Context) Sum() []byte
func (c Context) Suite() Suite
func (c Context) Valid() bool

func TranscriptBytes(s Suite, exchange string, parts ...[]byte) ([]byte, error)
func Label(s Suite, purpose string) ([]byte, error)
func DeriveLabel(s Suite, purpose string) ([]byte, error)

const PasswordMax = 256

func ValidPassword(p []byte) bool

var (
	ErrBadKeySize, ErrOpen, ErrBadPublicKey error
	ErrBadLabel, ErrBadContext             error
	ErrNoScalar                            error // DerivePair в ГОСТ: все 128 кандидатов вне диапазона
	ErrBadPassword                         error
)
```

Принятые решения:
- Секреты пересекают границу интерфейса только как *secmem.Buffer. Открытые ключи и подписи
  это []byte: они не секретны, а типизация на каждый набор усложнила бы wire.
- Agree, MixKey и DeriveKey принимают Context: это хэш транскрипта обмена, 32 байта. Он
  привязывает каждый секрет и каждый ключ к открытым ключам сторон, параметрам обмена, набору и
  версии схемы. Нулевое значение Context и контекст другого набора провайдер отвергает, так что
  вывести ключ без транскрипта нельзя. Раскладка и формулы в разделе "Вывод ключей".
- Метку KDF собирает провайдер из версии схемы, набора и purpose. Вызывающий код передаёт только
  purpose и свою строку метки подставить не может.
- MixKey сцепляет второе согласование с первым: результат зависит от обоих секретов и остаётся
  длиной KeySize.
- KeySize отдаёт длину ключа AEAD, чтобы wire не хардкодил 32 байта.
- DeriveKey в обоих наборах принимает секрет ровно в KeySize байт и размер от 1 до KeySize;
  ключ короче KeySize это начало полного. wire берёт 16 байт на метку повтора служебной ячейки и
  по 8 байт на смещения счётчиков.
- AEAD безопасен для одновременного использования: узел снимает слои и накладывает обратные
  одним ключом из разных горутин. MGM в gogost хранит состояние вызова, поэтому набор ГОСТ
  сериализует вызовы блокировкой. providertest проверяет это одновременными Seal и Open.
- Nonce назначает вызывающий код: провайдер их не хранит и не считает. link нумерует кадры одного
  направления канала с нуля и кладёт номер в последние 8 байт nonce, остальные нулевые. wire
  собирает nonce слоя ячейки из направления, идентификатора цепочки и счётчика. Повтор nonce под
  одним ключом исключается форматом ячейки. В 16-байтном nonce старший бит всегда нулевой, как
  требует MGM: в wire первым идёт счётчик с направлением, случайный идентификатор цепочки
  последним, в link старшие байты нулевые.
- GenerateSigning выдаёт долговременную пару для аутентификации узла, отдельно от эфемерной.
- Из пакетов crypto/ стандартной библиотеки вне crypto/ используется только crypto/rand:
  случайность для идентификаторов, серийных номеров и заполнения. Примитивом это не считается.
- DerivePair выдаёт пару согласования того же вида, что GenerateEphemeral, но как функцию секрета
  ровно в KeySize байт и Context: одни secret и ctx дают одну пару, другие независимую. Это метод
  провайдера, а не код вызывающего: выборка скаляра своя у каждого набора, закрытый ключ не
  появляется вне провайдера обычным срезом, а метку `pair/1`, как у Agree и MixKey, собирает
  провайдер. Вызывающий код purpose не передаёт и разводит пары через Context (имя обмена и
  части). Пара служит только согласованию и в Sign не передаётся (раздел "Подписи").
- В наборе ГОСТ кандидат это выход KDF_GOSTR3411_2012_256 с номером i от 0 до 127 в конце seed, у
  которого снят бит 255; берётся первый с 0 < k < q. q = 2^254 + δ, δ около 2^124, поэтому
  кандидат принимается с вероятностью чуть больше 1/2: в среднем нужно 2 кандидата, больше 8 с
  вероятностью около 2^-8, а все 128 отвергаются с вероятностью меньше 2^-128. Тогда DerivePair
  возвращает ErrNoScalar, буфер освобождён, пары нет; ошибки памяти secmem отдаются как есть.
  Граница 128 равна уровню стойкости и умещается в байт номера.
- Номер кандидата в seed, а не KDF_TREE_GOSTR3411_2012_256 (RFC 7836, 4.5): в gogost KDF_TREE
  нет, а свой цикл над HMAC был бы своей реализацией KDF. Номер в seed KDF_GOSTR3411_2012_256 это
  приём самих рекомендаций ТК26: TLSTREE (RFC 9189) и ESPTREE (RFC 9227) кладут номер ключа в
  seed. Каждый кандидат это один библиотечный вызов KDF, тот же, что у DeriveKey.
- Выборка с отказом, а не лишние биты (FIPS 186-5, A.2.1: k = (c mod (q-1)) + 1 из 512 бит).
  Лишние биты дают пренебрежимое смещение и постоянное число вызовов, но деление на math/big
  оставляет на куче частное и рабочие слова, равносильные ключу, без возможности их стереть, и
  требует двух блоков KDF. Выборка с отказом только сравнивает, число из кандидата стирается, а
  проверка диапазона общая с генерацией эфемерной пары. Это приём проверки кандидатов (FIPS
  186-5, A.2.2; SP 800-56A rev. 3, 5.6.1.2.2) с кандидатом длины bitlen(q) = 255: принятый скаляр
  равномерен на [1, q-1], смещения нет. Эфемерная пара берёт кандидаты по 256 бит из crypto/rand:
  распределение то же, кандидатов вдвое больше.
- PasswordKey растягивает пароль в ключ KeySize байт. Цену задаёт набор под purpose `password/1`,
  параметра цены у вызывающего нет, поэтому дешёвого пути к тому же ключу нет. Другая цена это
  purpose `password/2`, версия схемы при этом не меняется.
- Пароль от 1 до PasswordMax = 256 байт, байты как введены, без нормализации; 0x00, \r и \n
  запрещены (ValidPassword), чтобы командная строка, порт управления и провайдер читали одну
  строку. Иначе ErrBadPassword. Буфер пароля вызов не меняет.
- Соль PasswordKey это хэш транскрипта ctx, а части контекста провайдеру не видны, поэтому
  проверить их он не может. Вызывающий код кладёт в контекст свежую случайную часть не короче 16
  байт (RFC 9106, 3.1; SP 800-132, 5.1) на каждый контейнер и хранит её вместе с ним. У
  контейнера клиента это одна соль из 32 байт crypto/rand на файл, общая для двух его томов:
  Open растягивает один пароль один раз и пробует обе области (раздел "Контейнер"). При
  постоянном контексте соль у всех контейнеров набора была бы одна, и одно вычисление на догадку
  пароля проверяло бы её сразу против всех.
- Стойкость пароля, частота попыток и чтение пароля без копии в строке остаются за вызывающим
  кодом. При включённом занулении PasswordKey заканчивается принудительной сборкой мусора
  (раздел "Известные дыры"), паузой всего процесса, поэтому вызывающий код открывает контейнер до
  запуска канала и фиксированного расписания ячеек, и пауза не видна во времени ячеек.
- Набор ГОСТ растягивает пароль PBKDF2 с HMAC_GOSTR3411_2012_512, а не Argon2id: внутри Argon2id
  BLAKE2b, а набор ГОСТ состоит только из алгоритмов ГОСТ, функции с затратой памяти в
  рекомендациях ТК26 нет. Число итераций C_GOST = 2600 подобрано одноразовым замером на машине
  стенда так, чтобы процессорное время на догадку (ядро-секунды, user + sys по getrusage) было в
  пределах 0,8-1,25 от Argon2id набора c25519. Это соотношение верно только для Стрибога gogost
  в Linux-контейнерах стенда, где его и мерили: тот же код вне контейнера и оптимизированный
  Стрибог на обычном процессоре считают догадку быстрее, а GPU и специализированное железо, где
  PBKDF2 не нужна память, ещё быстрее. Поэтому нарушителю догадка против набора ГОСТ обходится
  дешевле, чем против Argon2id, во сколько раз, не измерено (LIMITATIONS).

## Вывод ключей

Каждый секрет и каждый ключ зависит от транскрипта обмена, от набора и от версии схемы, а при
аутентификации узлов и от личности узла. Подмена открытого ключа, личности, режима, набора или
версии на любой стороне даёт другие ключи, и первая же проверка AEAD не проходит.

### Метка

`метка = ASCII("jimichi/v2/" || набор || "/" || purpose)`, набор это `c25519` или `gost`.
Байта 0x00 в метке нет, длина не больше 50 байт.

| purpose | Длина метки, c25519 / ГОСТ | Кто выводит | Размер ключа |
|---|---|---|---|
| `agree` | 23 / 21 | провайдер, внутри Agree | 32 |
| `mix` | 21 / 19 | провайдер, внутри MixKey | 32 |
| `setup` | 23 / 21 | wire, ключ слоя установки | 32 |
| `cell` | 22 / 20 | wire, ключ хопа | 32 |
| `setup/replay` | 30 / 28 | wire, метка повтора служебной ячейки | 16 |
| `counter/fwd`, `counter/bwd` | 29 / 27 | wire, смещения счётчиков | 8 |
| `link/i2r`, `link/r2i` | 26 / 24 | link, ключи кадров | 32 |
| `noise/key` | 27 / 25 | noise, ключ сообщения рукопожатия | 32 |
| `noise/split/i2r`, `noise/split/r2i` | 33 / 31 | noise, ключи направлений после рукопожатия | 32 |
| `e2e/step/key` | 30 / 28 | e2e, ключ записи | 32 |
| `e2e/step/next` | 31 / 29 | e2e, следующий ключ цепочки ратчета | 32 |
| `vault/volume` | 30 / 28 | vault, ключ тома | 32 |
| `vault/block` | 29 / 27 | vault, ключ области на одну запечатку | 32 |
| `vault/fetch` | 29 / 27 | vault, право забора F тома | 16 |
| `pair/1` | 24 / 22 | провайдер, внутри DerivePair | 32 |
| `password/1` | 28 / 26 | провайдер, внутри PasswordKey | 32 |

- purpose и имя обмена: `[a-z0-9]+(/[a-z0-9]+)*`, от 1 до 32 байт.
- `agree`, `mix`, `pair`, `password` и всё, что начинается с `transcript/`, `pair/` или
  `password/`, оставлены провайдеру: DeriveKey с таким purpose возвращает ошибку, поэтому
  вызывающий код не может повторить выход Agree, MixKey, DerivePair или PasswordKey. Метод
  провайдера с новой меткой оставляет за собой её имя и её префикс.
- Строки домена подписей (раздел "Подписи") версионируются отдельно и в эту схему не входят.

### Транскрипт

```
T  = ASCII("jimichi/v2/" || набор || "/transcript/" || обмен) || 0x00 || u8(n)
     || n раз: u16be(длина части) || часть
th = Hash(T)        SHA-256 или Стрибог-256, 32 байта
```

- Частей от 1 до 255, каждая от 1 до 65535 байт.
- Раскладка однозначна: в строке нет 0x00, за ней разделитель, число частей и длина каждой
  части. Те же байты, разрезанные в других местах, дают другой хэш.
- NewContext берёт хэш и имя набора у переданного провайдера, поэтому контексту можно верить
  настолько же, насколько этому провайдеру: тип гарантирует, что контекст есть, а не то, что это
  хэш набора от транскрипта. wire, link и relay передают провайдер самого набора. Хэш не
  выбирается по набору внутри crypto: пакет ГОСТ сам импортирует crypto, так что Стрибог пришлось
  бы взять в пакет интерфейса прямо из сторонней библиотеки, а пакет интерфейса криптобиблиотек
  не импортирует. И пользы это не дало бы: обёртка, которая возвращает выбранные ею байты из
  Hash, так же возвращает их из Agree и DeriveKey.
- NewContext копирует части в T и сразу хэширует: срез из тела ячейки не может измениться между
  двумя выводами ключей.
- Транскрипт состоит из открытых данных и ключом подписи узла не подписывается. Sum отдаёт
  копию хэша.

Установка цепочки, обмен `setup`, один контекст на хоп:

| № | Часть | Байты | Клиент | Узел |
|---|---|---|---|---|
| 1 | версия | 1 | версия формата ячейки | версия формата ячейки |
| 2 | индекс хопа | 1 | номер хопа в цепочке | поле counter служебной ячейки |
| 3 | идентификатор канала | 8, big endian | выбранный для хопа | из заголовка ячейки |
| 4 | онион-ключ | открытый ключ | из проверенного дескриптора | открытая половина пробуемого онион-ключа |
| 5 | эфемерный ключ клиента | открытый ключ | сгенерированный | байты в начале слоя |
| 6 | ключ личности узла, только при аутентификации узлов | ключ подписи | из проверенного сертификата | свой, тот, что заверяет его сертификат |

Длина T: 120 байт на c25519, 182 на ГОСТ; с частью 6 154 и 248.

Канал, обмен `link`:

| № | Часть | Байты |
|---|---|---|
| 1 | версия | 1 |
| 2 | режим | 1: 0x00 анонимный, 0x01 аутентифицированный |
| 3 | эфемерный ключ инициатора | как в hello после байта режима |
| 4 | эфемерный ключ ответчика | как отправлен |
| 5 | ключ канала ответчика, только в режиме 0x01 | инициатор берёт из дескриптора, ответчик свой опубликованный |
| 6 | ключ личности ответчика, только в режиме 0x01 и при аутентификации узлов | инициатор берёт из проверенного сертификата, ответчик свой |

Длина T в режимах 0x00 и 0x01: 109 и 143 байта на c25519, 171 и 237 на ГОСТ; с частью 6 177 и
303.

Личность узла:
- Ключ личности это открытый ключ подписи узла, который заверяет его сертификат (Verified.Identity).
  Он создаётся при старте узла и живёт, пока живёт процесс, поэтому не меняется при повторной
  выдаче сертификата, в отличие от байтов самого сертификата.
- Узел с -auth привязывает свой ключ личности с самого старта: к каждой установке, которую он
  открывает, и к каждому аутентифицированному каналу, который принимает. До сертификата он не
  отдаёт дескриптора и никуда не продлевает цепочки, поэтому никто не знает ключей, по которым к
  нему обратиться. Клиент берёт ключ личности каждого узла цепочки из его проверенного
  сертификата, узел берёт ключ личности следующего узла из дескриптора соседа в своём кэше.
- Без аутентификации узлов (-auth=false) обе стороны привязывают пустую личность: части 6 нет,
  и транскрипт имеет на одну часть меньше. Пустую часть раскладка не допускает, а число частей
  отличает обе формы. Узел с -auth и клиент или соседний узел без -auth не согласуют ни одного
  ключа: это несовпадение конфигураций, и установка или рукопожатие канала с ним не проходят.
- Слой установки и аутентифицированный канал открываются только у узла, который держит закрытую
  половину ключа и привязывает ту же личность.

Обмены сквозного слоя перечислены в разделе "Сквозной слой".

### Формулы

c25519: HKDF-SHA-256 (RFC 5869: Extract в разделе 2.2, Expand в разделе 2.3, один блок выхода),
`info(p) = метка(p) || 0x00 || th`.

| Операция | Вычисление |
|---|---|
| Agree | `Z = X25519(priv, pub)`; `PRK = HMAC(ключ = th, Z)`; `HMAC(PRK, info(agree) \|\| 0x01)` |
| MixKey | `PRK = HMAC(ключ = chain, secret)`; `HMAC(PRK, info(mix) \|\| 0x01)` |
| DeriveKey | `HMAC(secret, info(purpose) \|\| 0x01)[0:size]` |
| DerivePair | `raw = HMAC(secret, info(pair/1) \|\| 0x01)`; `priv = raw` с обрезкой RFC 7748 (раздел 5): `priv[0] &= 0xf8`, `priv[31] &= 0x7f`, `priv[31] \|= 0x40`; `pub = X25519(priv, 9)` |
| PasswordKey | `Argon2id(P = пароль, S = метка(password/1) \|\| 0x00 \|\| th, t = 3, m = 65536 КиБ, p = 4, T = 32)`, второй рекомендуемый вариант RFC 9106 (раздел 4) |

- DerivePair хранит уже обрезанный скаляр. X25519 обрезает скаляр и сам, поэтому открытый ключ и
  каждое согласование те же, что дал бы необрезанный raw, а закрытый ключ в векторах однозначен.
  GenerateEphemeral кладёт в буфер 32 случайных байта без обрезки, распределение открытого ключа
  у обоих одно.
- S PasswordKey длиной 61 байт на c25519 и 59 на ГОСТ.

ГОСТ: VKO_GOSTR3410_2012_256 и KDF_GOSTR3411_2012_256 (RFC 7836, разделы 4.3.1 и 4.5),
`KDF(K, label, seed) = HMAC_Стрибог256(K, 0x01 || label || 0x00 || seed || 0x01 || 0x00)`.

| Операция | Вычисление |
|---|---|
| Agree | `UKM = th[0:8]` как число little endian, ноль заменяется единицей; `KEK = VKO(priv, pub, UKM)` после проверок точки; `KDF(KEK, метка(agree), th)` |
| MixKey | `KDF(chain, метка(mix), th \|\| secret)` |
| DeriveKey | `KDF(secret, метка(purpose), th)[0:size]` |
| DerivePair | для i = 0, 1, ..., 127: `c_i = KDF(secret, метка(pair/1), th \|\| u8(i))`, `c_i[31] &= 0x7f`; priv это первый c_i с `0 < LE(c_i) < q`; `pub = LE(x) \|\| LE(y)` точки `LE(priv)·P`, как у эфемерной пары; все 128 отвергнуты: ErrNoScalar |
| PasswordKey | `PBKDF2(PRF = HMAC_GOSTR3411_2012_512, P = пароль, S = метка(password/1) \|\| 0x00 \|\| th, c = 2600, dkLen = 32)`: начало блока T_1 |

Профиль ГОСТ:
- K_in всегда 256 бит: KEK, выход Agree или выход MixKey; секрет DeriveKey и DerivePair ровно 32
  байта. Это нижняя граница длины ключа HMAC_GOSTR3411_2012_256 (RFC 7836, 4.1.1).
- label это константа схемы без 0x00, seed всегда 32 байта, в MixKey 64, в DerivePair 33 (th и
  номер кандидата). RFC 7836 (4.5) требует, чтобы label и seed назначал протокол, и рекомендует
  фиксировать их длины. Вход DerivePair однозначен: в метке нет 0x00, хвост 01 00 фиксирован, а
  метка pair/1 вызывающему коду недоступна, поэтому с DeriveKey и MixKey он не пересекается.
- Выход один блок, не больше 32 байт.
- UKM 64 бита берётся из начала хэша транскрипта, полный хэш идёт в seed. RFC 7836 (4.3.1)
  допускает UKM до половины длины открытого ключа и рекомендует 64 бита и больше, если хотя бы
  одна сторона использует статический ключ. gogost умножает общую точку на UKM отдельным скалярным
  умножением, и более широкий множитель удлинил бы его.
- В MixKey второй секрет стоит в позиции seed. Функция та же, но seed здесь не открытое
  значение: это отступление от обычного использования KDF_GOSTR3411_2012_256. Основание: HMAC
  рассматривается как псевдослучайная функция по ключу chain и как экстрактор по сообщению, в
  которое входит secret, поэтому выход неизвестен, пока неизвестен хотя бы один из двух секретов.
  Формального доказательства для этой композиции в работе нет.

### Кто что вызывает

Установка: клиент и узел строят один и тот же `ctx = NewContext(p, "setup", ...)`,
`secret = Agree(.., ctx)`, затем DeriveKey с тем же ctx для `setup`, `cell`, `counter/fwd`,
`counter/bwd`. Узел кроме того выводит `setup/replay`, клиент метку повтора не выводит.
Узел с двумя онион-ключами строит контекст отдельно для каждого: слой, собранный под ключ одной
эпохи, ключом другой не открывается.

Канал, оба согласования под одним контекстом:

| Режим | Согласования | Ключ, из которого выводятся ключи кадров |
|---|---|---|
| 0x00 | эфемерный с эфемерным (ee) | `ee` |
| 0x01 | эфемерный инициатора с ключом канала ответчика (es), затем ee | `MixKey(chain = es, secret = ee, ctx)` |

Ключи кадров: DeriveKey с `link/i2r` и `link/r2i`. Первый кадр ответчика подтверждает весь
транскрипт: если хоть один его байт у сторон различается, кадр не открывается.

Проверка пары, обмен `relay/keycheck`: узел генерирует одноразовую пару и под контекстом из
проверяемого открытого ключа и одноразового открытого ключа согласует секрет с обеих сторон.
Секреты должны совпасть, ключи из них не выводятся, оба сразу освобождаются. Ключ канала
проверяется при старте узла, каждый онион-ключ до того, как его примет кольцо: первый при
старте, следующие при каждой ротации. Узел, у которого опубликованный ключ канала не согласуется
с закрытым (открытый ключ другой пары или ключ, который согласование отвергает), не стартует:
иначе он не подтвердил бы ни одного аутентифицированного канала, а при -onion-rotate 0, когда
ключ канала служит и онион-ключом, не открыл бы ни одной установки. Пара онион-ключа, которая не
согласуется, отвергается так же, под ней узел не открыл бы ни одной установки: при старте узел
не запускается, при ротации опубликованный ключ остаётся на месте, а попытка считается
неудавшейся ротацией. Проверка, которая не прошла по другой причине, прежде всего когда секрет
негде заблокировать, сообщает эту причину, а не плохую пару.

Контейнер клиента (раздел "Контейнер"): DerivePair и PasswordKey вызывает только vault. Обмены
`vault/password` (растяжение пароля), `vault/volume` (ключ тома), `vault/block` (ключ области на
одну запечатку) и `vault/identity` (пара и F тома). vault/profile своих обменов не вводит: ключ
карточки контакта он проверяет через e2e.NewSession, обменом `e2e/check`. Пакеты сквозного слоя
и драйвер разговора DerivePair и PasswordKey не вызывают, и это держат проверки исходного кода
noise, e2e и conversation.

### Правила изменения

- Версия схемы (сейчас `v2`) меняется при любом изменении раскладки транскрипта, формул, имени
  или размера существующего purpose. Версии между собой не совместимы, согласования версий нет:
  узлы и клиенты обновляются вместе. На проводе версия не видна, байт версии ячейки
  (wire.Version) при смене схемы ключей не меняется.
- Новый purpose версию не меняет: он добавляет строку в таблицу меток и золотой вектор в
  crypto/providertest.
- Золотые векторы закрепляют композицию: хэши пяти транскриптов (установка и оба режима канала
  без личности, установка и аутентифицированный канал с ключом личности), все выводимые ключи,
  MixKey и Agree на фиксированных ключах для обоих наборов. В комментарии к ним записано, как
  пересчитать значения без этого кода. Оба примера VKO в RFC 7836 (приложение B, примеры 7 и 8)
  даны на 512-битном paramSetA, поэтому примитивы ГОСТ проверяются примерами стандартов в тестах
  crypto/gost (VKO_GOSTR3410_2012_256 примером 7, KDF_GOSTR3411_2012_256 примером 9), а
  композицию на 256-битном paramSetA закрепляют векторы схемы с промежуточными значениями (хэш
  транскрипта, UKM, KEK), записанными в crypto/providertest. Они посчитаны независимой
  реализацией, которая в репозиторий не входит; всё, кроме KEK, это хэш или HMAC и
  пересчитывается любой реализацией Стрибога.
- Сквозной слой закрепляют векторы полного рукопожатия KK и первых записей обоих наборов
  (e2e/vectors_test.go, noise/vector_test.go) с промежуточными значениями и рецептом пересчёта в
  комментарии. Значения c25519 посчитаны отдельной реализацией на Python, значения ГОСТ обвязкой
  композиции над провайдерами, которая на c25519 побайтно совпала с Python; каждый примитив ГОСТ
  при этом закреплён примером стандарта.
- Вывод `pair/1` и цена `password/1` закреплены: другой вывод пары или другая цена получают новый
  purpose (`pair/2`, `password/2`), а не новую версию схемы.
- Векторы DerivePair (оба набора: th, priv, pub; во внутренних тестах ещё необрезанный raw на
  c25519, номер принятого кандидата и каждый отвергнутый кандидат с причиной на ГОСТ) и PasswordKey
  (оба набора, в том числе под -short) посчитаны отдельными реализациями на Python, которые в
  репозиторий не входят. На c25519 это hashlib, hmac и X25519 пакета cryptography, обрезка и
  Argon2id написаны в скрипте; Argon2id сначала воспроизводит пример RFC 9106 (5.3) и векторы
  эталонной реализации PHC. На ГОСТ без зависимостей написаны по стандартам Стрибог, HMAC, KDF,
  PBKDF2 и арифметика кривой в аффинных координатах, а сами реализации сначала воспроизводят RFC
  6986 (M1 и M2), примеры приложения B RFC 7836 (HMAC, KDF и VKO вместе с открытыми ключами
  сторон), векторы Р 50.1.111-2016 и все прежние значения ГОСТ из crypto/providertest. pygost и
  openssl с gost-engine служат только дополнительной сверкой там, где они установлены.

Проверки провайдера одинаковы в обоих наборах и идут в таком порядке: размеры секретов,
контекст, метка, открытый ключ; в PasswordKey сначала пароль, затем контекст.

| Аргумент | Правило | Ошибка |
|---|---|---|
| priv | длина закрытого ключа набора | ErrBadKeySize |
| secret, chain | ровно KeySize (DeriveKey, MixKey, DerivePair); освобождённый буфер тоже ошибка | ErrBadKeySize |
| size | от 1 до KeySize | ErrBadKeySize |
| password | от 1 до PasswordMax байт, без 0x00, \r и \n; освобождённый буфер тоже ошибка | ErrBadPassword |
| ctx | создан через NewContext провайдером того же набора | ErrBadContext |
| purpose, обмен | формат имени; в DeriveKey не из оставленных провайдеру | ErrBadLabel |
| части транскрипта | от 1 до 255, каждая от 1 до 65535 байт | ErrBadContext |
| peerPub | длина; точка малого порядка (в c25519 её отвергает сам X25519); в ГОСТ ещё и точка вне кривой или с координатой не меньше p | ErrBadPublicKey |
| выборка скаляра DerivePair, только ГОСТ | все 128 кандидатов вне [1, q-1], вероятность меньше 2^-128 | ErrNoScalar |

## Подписи

Подписи и хэши пакет pki берёт только через CryptoProvider (Sign, Verify, Hash), своих
примитивов у него нет.

| Ключ | Что подписывает | Строка домена |
|---|---|---|
| ключ УЦ | сертификат узла | `jimichi/cert/v1\x00` |
| ключ подписи узла | запрос сертификата | `jimichi/csr/v1\x00` |
| ключ подписи узла | дескриптор узла | `jimichi/descriptor/v1\x00` |

- Строка домена стоит перед телом только в подписываемом сообщении. Подпись объекта одного вида
  не проверяется как подпись другого, даже если тела совпадут байт в байт.
- ca_id (первые 8 байт) и cert_hash (32 байта) считаются через Hash набора: SHA-256 или
  Стрибог-256.
- Verify отвергает открытый ключ малого порядка до проверки подписи: под ним подпись к любому
  сообщению делается без закрытого ключа. crypto/ed25519 проверяет без кофактора и такие ключи
  принимает (под нейтральной точкой подходит R = [S]B), поэтому c25519 сначала декодирует ключ,
  требует каноническую запись и отвергает точку, которая после умножения на кофактор 8 даёт
  нейтральную. ГОСТ отвергает точки вне кривой и точки порядка 2 и 4, у нейтральной точки нет
  аффинной записи. providertest проверяет ключи малого порядка для обоих наборов.
- Правило для вызывающего кода: в ГОСТ ключ подписи получается тем же генератором на той же кривой,
  что и эфемерная пара, поэтому ключ подписи нельзя использовать в согласовании, а ключ
  согласования, в том числе ключ DerivePair, для подписи. Интерфейс этого не проверяет: Sign
  принимает любой скаляр нужной длины.
- Подписи личности никогда не аутентифицируют сообщения клиентов. У клиента нет ключа подписи:
  его ключ личности это ключ согласования, и в Sign он не передаётся. Подпись отправителя над
  сообщением или транскриптом доказывала бы третьему лицу, кто его отправил. Пакеты сквозного
  слоя (noise, e2e) не вызывают GenerateSigning, Sign и Verify. Их тесты проверяют это дважды:
  в исходном коде пакетов таких вызовов нет, а каждый тест пакетов, в том числе на отвергнутых,
  повторённых и подделанных входах, идёт на провайдере, на котором такой вызов валит тест.
  Подписи есть только у УЦ и узлов.
- Ключ УЦ и ключ подписи узла хранятся в буферах secmem, pki отдаёт наружу только открытые ключи.
  Копии, которые библиотеки делают при генерации и подписи, перечислены в разделе "Известные дыры".

## Ключи узла

| Ключ | Что делает | Сколько живёт |
|---|---|---|
| Ключ подписи узла | подписывает запрос сертификата и дескрипторы; его открытая половина (ключ личности) при аутентификации узлов входит в транскрипт установки и канала узла (раздел "Транскрипт") | до конца процесса |
| Ключ канала | тот, кто открывает канал к узлу, подмешивает его в рукопожатие, и это аутентифицирует узел на этом канале | до конца процесса |
| Онион-ключ | с ним клиент согласует секрет слоя при установке цепочки | с -onion-rotate один период как опубликованный ключ и льготный период после него; без ротации в этой роли служит ключ канала, до конца процесса |
| Ключи хопа цепочки | открывают и шифруют ячейки одной цепочки на одном узле | до разрыва цепочки |
| Ключи кадров канала | шифруют кадры одного канала; выводятся из согласования двух эфемерных ключей, а в аутентифицированном режиме ещё и из согласования с ключом канала ответчика (раздел "Вывод ключей") | до закрытия канала |

- Ключ подписи, ключ канала и онион-ключ генерируются через CryptoProvider прямо в буферы
  secmem. Онион-ключ освобождается, а его буфер зануляется, в конце льготного периода
  (ARCHITECTURE, эпохи онион-ключа) и при завершении процесса.
- Установка стоит узлу одного согласования на каждый онион-ключ, который он держит: одного вне
  льготного периода, двух внутри него, то есть двух VKO на наборе ГОСТ.
- Освобождение онион-ключа стирает только его буфер secmem. Копии скаляра, которые библиотеки
  сделали при согласованиях, остаются на куче до повторного использования этой памяти
  ("Известные дыры").

## Сквозной слой

Между двумя клиентами поверх цепочки идёт свой слой: карточка контакта, рукопожатие по шаблону
KK и хэш-ратчет на каждое направление (пакеты noise и e2e). Узлы его не открывают: для них запись
слоя это часть полезной нагрузки ячейки. Записи идут через mailbox на выходе (пакет mailbox,
`-exit mailbox`) и драйвер разговора (пакет conversation); ими пользуется клиент `cmd/client
-peer` (ARCHITECTURE, "Клиент -peer").

Все операции слоя идут через Agree, MixKey, DeriveKey, Hash и AEAD провайдера, поэтому формулы
наборов те же, что в разделе "Формулы". Наборы различаются только байтом набора в карточке,
длиной открытого ключа P, длиной nonce и длиной нулевой нагрузки рукопожатия L.

| | c25519 | ГОСТ |
|---|---|---|
| P / nonce / тег | 32 / 24 / 16 | 64 / 16 / 16 |
| запись | 392 | 392 |
| L, нули в kk1 и kk2 | 343 | 311 |
| inner записи данных / тело максимум | 371 / 368 | 371 / 368 |
| карточка с адресом из 38 байт, текст | 89 байт, 127 символов | 121 байт, 169 символов |

### Обмены

| Обмен | Части | Длина T, c25519 / ГОСТ |
|---|---|---|
| `noise/e2e/kk` | 0x01, карточка инициатора, карточка ответчика | 228 / 290 |
| `noise/hash` | h, данные d | 77 + len(d) / 75 + len(d) |
| `noise/dh` | h, байт токена | 76 / 74 |
| `noise/key` | h | 74 / 72 |
| `noise/split` | h | 76 / 74 |
| `e2e/step` | SID, направление, u32be(n) | 82 / 80 |
| `e2e/card` | карточка | 130 / 160 |
| `e2e/check` | одноразовый открытый ключ, ключ собеседника | 108 / 170 |
| `mailbox/queue` | право забора F, 16 байт (пакет mailbox) | 62 / 60 |

Длины для карточек и обмена `e2e/card` даны при адресе mailbox из 38 байт.

### Карточка контакта

```
u8 версия = 1 | u8 набор (1 ГОСТ, 2 c25519) | u8 длина адреса | адрес mailbox | очередь, 16 байт | ключ личности, P байт
```

- Каноническая форма: разбор и сборка дают те же байты, хвост запрещён. Адрес проходит правила
  pki для адресов узлов, очередь не нулевая, ключ ровно P байт.
- Очередь это первые 16 байт хэша транскрипта `mailbox/queue` от права забора F
  (`mailbox.QueueID`). Карточка собеседника несёт только очередь, поэтому разбор принимает
  любую очередь, кроме нулевой; драйвер разговора сверяет очередь своей карточки с F.
- Текст `<набор>:<base64 с дополнением>`; префикс равен набору внутри карточки, однозначность
  проверяется круговым разбором, как у якоря доверия.
- `card_hash` это хэш транскрипта `e2e/card` от карточки, 32 байта. Короткого отпечатка нет.

### Машина noise

Состояние: h (32 байта, открытое), ck (secmem, пусто до первого согласования), свой статический
ключ (только через интерфейс Static: открытый ключ и Agree), статический ключ собеседника, свой
эфемерный ключ (secmem), эфемерный ключ собеседника, номер сообщения.

| Операция | Определение |
|---|---|
| начало | `h = Hash(T("noise/"+имя, пролог...))`; затем MixHash ключей предсообщений, сначала инициатора |
| MixHash(d) | `h = Hash(T(noise/hash, h, d))`, d не пустой |
| токен e, запись | `(e, E) = GenerateEphemeral()`; E в сообщение; MixHash(E) |
| токен e, чтение | следующие P байт как эфемерный ключ собеседника RE; MixHash(RE) |
| DH-токен t | `ctx = NewContext(noise/dh, h, [t])`; `sec = Agree(свой, чужой, ctx)`; первый: `ck = sec`, далее `ck = MixKey(ck, sec, ctx)`, прежние ck и sec освобождаются |
| EncryptAndHash(pt) | `k = DeriveKey(ck, noise/key, NewContext(noise/key, h), 32)`; `c = AEAD(k).Seal(nonce 0, pt, ad = h)`; k освобождается; MixHash(c). Без ck ошибка |
| DecryptAndHash(c) | тот же k, Open, MixHash(c) |
| Split | `ctx = NewContext(noise/split, h)`; `i2r`, `r2i` = DeriveKey(ck, noise/split/i2r и noise/split/r2i, ctx, 32); SID = h; ck и e освобождаются |

Порядок внутри одного сообщения: MixHash вида записи (его делает e2e), токен e, DH-токены по
порядку шаблона (h между ними не меняется, их различает байт токена в контексте), затем
EncryptAndHash нагрузки.

Токены: e = 1, s = 2, ee = 3, es = 4, se = 5, ss = 6. Первая буква DH-токена называет ключ
инициатора, вторая ключ ответчика:

| Токен | Инициатор (свой, чужой) | Ответчик (свой, чужой) |
|---|---|---|
| ee | e, re | e, re |
| es | e, rs | s, re |
| se | s, re | e, rs |
| ss | s, rs | s, rs |

- Нулевой nonce безопасен: каждый ключ из EncryptAndHash служит одной Seal, h меняется после
  каждого шифротекста, эфемерный ключ свежий. Старший бит нулевого nonce MGM равен 0.
- Чтение сообщения не меняет состояние при ошибке: значения считаются во временных буферах и
  применяются только после успешного Open и проверки нагрузки, иначе освобождаются, а h
  возвращается к концу прошлого сообщения вместе с MixHash вида. Подделанное сообщение не ломает
  рукопожатие, которое ждёт настоящее.
- Токен s внутри сообщения (передача статического ключа) пока не поддерживается.
- Эфемерный ключ даёт только провайдер; задать его через API нельзя. Заданный эфемерный ключ
  нужен только векторам и проверке отрицаемости, им хватает обёртки над CryptoProvider.

Это форма Noise, а не экземпляр Noise Protocol Framework: Agree отдаёт выход KDF, а не сырой
результат DH; h и ck идут через Context провайдера; начального ck из имени протокола нет.
Векторы Noise (cacophony) к нему неприменимы, вариант на ГОСТ нестандартный. Свойства шаблона KK
заявляются по аналогии, формальной модели нет.

### Рукопожатие KK

- Инициатор тот, чей ключ личности меньше при побайтовом сравнении. Равные ключи или своя
  очередь в карточке собеседника это отказ. Одновременных инициаций нет.
- Перед сессией ключ собеседника проверяется пробным согласованием одноразовой пары с ним под
  контекстом `e2e/check` (одноразовый открытый ключ, ключ собеседника). Выход и одноразовый ключ
  сразу освобождаются, ключ личности в проверке не участвует; ключ, который согласование
  отвергает, означает отказ карточке.
- Имя `e2e/kk` (обмен `noise/e2e/kk`), пролог `[0x01, карточка инициатора, карточка
  ответчика]`, предсообщения: ключ инициатора S_I, затем ключ ответчика S_R.
- Перед каждым сообщением рукопожатия MixHash([вид записи]): вид входит в h, в ad и во все
  последующие ключи.
- kk1: `01 | E_I | c1`, kk2: `02 | E_R | c2`; c это EncryptAndHash L нулевых байт. При чтении
  нагрузка обязана быть нулевой.
- Сторона тратит на рукопожатие 4 Agree, 3 MixKey, 4 DeriveKey (2 ключа сообщений и 2 в Split),
  16 хэшей транскрипта и 1 GenerateEphemeral; проверка ключа собеседника добавляет ещё по одному
  GenerateEphemeral и Agree на сессию.

| Формула | c25519 | ГОСТ |
|---|---|---|
| выход DH-токена, th = хэш контекста `noise/dh` | `HMAC(HMAC(th, X25519(a, B)), метка(agree) \|\| 0x00 \|\| th \|\| 0x01)` | `KDF(VKO(a, B, UKM = th[0:8]), метка(agree), th)` |
| ck со второго токена | `HMAC(HMAC(ck, sec), метка(mix) \|\| 0x00 \|\| th \|\| 0x01)` | `KDF(ck, метка(mix), th \|\| sec)` |
| ключ сообщения, Split, шаг ратчета | `HMAC(ключ, метка(purpose) \|\| 0x00 \|\| th \|\| 0x01)` | `KDF(ключ, метка(purpose), th)` |
| шифр записи, nonce 0 | XChaCha20-Poly1305: подключ HChaCha20(k, 0^16), ChaCha20-Poly1305 с nonce 0^12 | Кузнечик-MGM, nonce 0^16 |

Состояния сессии: рукопожатие, установлена, подтверждена (ответчик после первой записи данных
инициатора), устарела. Эпоха растёт при каждой смене сессии.

| Правило | Инициатор | Ответчик |
|---|---|---|
| запись рукопожатия | kk1 предлагается, пока mailbox его не сохранил | kk2 предлагается, пока mailbox его не сохранил или пока не пришла первая запись инициатора |
| ожидание | kk2 ждётся 60 с с момента сохранения kk1, иначе новое рукопожатие со свежим e_I | нет |
| копии | kk2, равный принятому байт в байт, это копия; любой другой kk2 отвергается без смены состояния | kk1, равный принятому байт в байт, это копия; kk1 с E_I из кольца последних 64 виденных (кольцо пополняется после успешного Open, самое старое вытесняется) это повтор |
| новое рукопожатие | после устаревания или когда номера записей кончились | свежий kk1, который открылся, заменяет сессию, если её нет, она не подтверждена или устарела; иначе отказ |
| первые записи | сразу после kk2 запись данных (настоящая или фиктивная): подтверждение для ответчика | настоящие сообщения только после подтверждения, фиктивные можно |
| устаревание | 450 отвеченных заборов (90 с при периоде 200 мс) без открывшейся записи ответчика | то же без записи инициатора; устаревший ответчик ничего не запечатывает, поэтому устаревает и инициатор и начинает рукопожатие, которое ответчик примет |

Открывшаяся запись снимает устаревание. Сессия, в которой каждая сторона кладёт запись чаще
раза в 90 с, не устаревает; расписание записей задаёт драйвер разговора (ARCHITECTURE, подраздел
"Разговор").

Уровни безопасности нагрузки по таблице Noise для шаблона KK и что с ними делают правила:

| Сообщение | Аутентичность | Конфиденциальность | Правило |
|---|---|---|---|
| kk1 | 1: подмена при компрометации ключа (KCI), держатель ключа ответчика подделает kk1 от имени инициатора; повторяемо | 2 | данных нет; повтор ловит кольцо; KCI и повтор старого kk1 вне кольца сбрасывают только сессию, которой нет, неподтверждённую или устаревшую: ключи данных требуют se = DH(s_I, e_R), без них подтверждения не будет, а живую сессию сбросить нельзя |
| kk2 | 2 | 4 | данных нет |
| данные | 2 | 5 | ратчет сверху |

- Неизвестная доля ключа и подмена личности: обе карточки в прологе, оба статических ключа в
  предсообщениях.
- Отражение: у направлений разные ключи Split и байт направления в контексте каждого шага
  ратчета, вид записи входит в h.
- Сокрытие личности: KK не передаёт статических ключей.

### Хэш-ратчет

На каждое направление цепочка ck_n (secmem) и номер n; ck_0 это i2r или r2i из Split.

```
ctx_n   = NewContext(e2e/step, SID, [d], u32be(n))      d: 0x01 i2r, 0x02 r2i
mk_n    = DeriveKey(ck_n, e2e/step/key,  ctx_n, 32)
ck_n+1  = DeriveKey(ck_n, e2e/step/next, ctx_n, 32)     ck_n освобождается сразу
запись  = 03 | u32be(n) | AEAD(mk_n).Seal(nonce 0, inner, ad = 03 | u32be(n))
inner   = флаги (бит 0: фиктивная, прочие 0) | u16be(длина) | тело | нули, всего 371 байт
```

- Отправитель назначает n при запечатывании и никогда не использует его дважды; повтор записи
  это копия тех же байтов. На номере 2^32 - 1 сессия кончается, инициатор начинает новое
  рукопожатие.
- Получатель хранит следующий ожидаемый номер и битовую карту на 64 номера ниже него:
  - номер ниже ожидаемого с битом в карте: копия;
  - номер ниже ожидаемого без бита или ниже карты: опоздавшая запись;
  - номер дальше ожидаемого больше чем на 64: вне окна;
  - иначе временная копия цепочки шагает до n, запись открывается, и только при успехе
    состояние меняется (пропущенные номера считаются потерянными). Подделанный номер стоит не
    больше 64 шагов. Пропущенные ключи не хранятся.
- После разрыва больше 64 записей в одном направлении (пачка, потерянная у mailbox, или долгий
  перерыв) все следующие записи этого направления вне окна и тоже теряются. Направление
  возвращает только новая сессия: принимающая сторона ничего не открывает и устаревает,
  устаревшая сторона ничего не запечатывает, поэтому устаревает и другая, и инициатор начинает
  новое рукопожатие. При заборе раз в 200 мс это не дольше 2 x 90 с плюс 60 с ожидания kk2.
- Фиктивная запись пустая. Ненулевое заполнение, лишние биты флагов, длина больше 368 и
  фиктивная запись с телом отвергаются. Настоящая и фиктивная запись стоят одинаковых вызовов
  провайдера.
- Прямая секретность на каждую запись. Восстановления после компрометации нет (ратчета на DH
  нет); новое рукопожатие после устаревания даёт его побочно, а не по расписанию.

### Ключи клиента

| Ключ | Создаётся | Где | Живёт |
|---|---|---|---|
| ключ личности клиента (статический ключ согласования) | GenerateEphemeral при старте | secmem | до конца процесса |
| право забора F | crypto/rand | secmem; копия в каждом запросе на куче клиента и открыто у mailbox | до конца процесса клиента -peer |
| одноразовый ключ проверки карточки | GenerateEphemeral | secmem | одно согласование при создании сессии |
| e_I | GenerateEphemeral | secmem | до kk2 или нового рукопожатия: ожидание сохранения kk1 плюс 60 с |
| e_R | GenerateEphemeral | secmem | только запись kk2 |
| выходы Agree, ck, ключи сообщений рукопожатия | Agree, MixKey, DeriveKey | secmem | один шаг |
| цепочки ратчета | Split, DeriveKey | secmem | до следующей записи в этом направлении |
| mk_n | DeriveKey | secmem; на c25519 копия в структуре AEAD | одна Seal или Open, затем Destroy |

Установленная сессия держит ключ личности и две цепочки ратчета; инициатор до kk2 ещё e_I и ck;
запись с пропуском на время приёма добавляет временную цепочку и ключ записи.

### Отрицаемость

Утверждение: офлайн-отрицаемость для обеих сторон. Транскрипт сессии (kk1, kk2 и все записи
данных), даже вместе с закрытыми ключами получателя, не доказывает третьему лицу, что в сессии
участвовал отправитель, если у судьи нет независимой доверенной записи о том, кто и когда передал
эти шифротексты. Стороны симметричны: отправителем может быть и инициатор, и ответчик, поэтому
подделка любой из сторон в любой роли это та же процедура с переставленными метками, и проверка
ниже покрывает подделывающего в обеих ролях.

Аргумент совершенной симуляции:

1. Каждый байт транскрипта это детерминированная функция открытых значений (обе карточки, E_I,
   E_R), открытых текстов и четырёх выходов Agree: es, ss, ee и se. Контекст каждого выхода
   собран только из открытых значений: h на момент токена и байт токена.
2. Agree симметричен под одним Context на обоих наборах: Agree(a, B, ctx) = Agree(b, A, ctx).
   Это проверяют тесты соответствия провайдеров (согласование в обе стороны и золотые векторы
   согласования) и векторы сквозного слоя: обе стороны каждого DH-токена получают один выход.
3. Получатель знает свой статический ключ и сам выбирает оба эфемерных ключа тем же
   GenerateEphemeral, что и честные стороны. Ключ отправителя входит в два выхода, и каждый из
   них получатель вычисляет со своей стороны; остальные два зависят только от эфемерных ключей,
   которые он выбрал сам.

| Отправитель | Выходы с ключом отправителя | Как их вычисляет получатель |
|---|---|---|
| инициатор | ss = DH(s_I, s_R), se = DH(s_I, e_R) | Agree(s_R, S_I), Agree(e_R, S_I) |
| ответчик | es = DH(e_I, s_R), ss = DH(s_I, s_R) | Agree(e_I, S_R), Agree(s_I, S_R) |

4. Nonce фиксированы, нагрузки рукопожатия нулевые, других случайных значений в транскрипте нет.
   Поэтому подделка распределена ровно так же, как настоящий транскрипт с теми же открытыми
   текстами, без вычислительных допущений, даже для судьи, которому отдали оба статических ключа.
5. Сломало бы это только значение, которое может вычислить лишь отправитель, то есть подпись.
   Отсюда правило раздела "Подписи": подписи личности никогда не аутентифицируют сообщения
   клиентов.

Условие о засвидетельствованном транскрипте: аргумент говорит только о байтах транскрипта.
Mailbox или наблюдатель канала отправителя в сговоре с получателем это условие снимают: журнал
заявок put по цепочкам вместе с привязкой цепочки к адресу отправителя (сговор со входом или
атака корреляции) это независимая запись о том, кто передал шифротексты, и симуляция её не
покрывает.

Проверка: пакет lab/scenario и `cmd/lab -set deny`.

- Genuine проводит настоящую сессию двух личностей. Forge строит сессию с теми же открытыми
  текстами, имея закрытые ключи только получателя. Verify проигрывает транскрипт новой сессии
  получателя: каждая запись отправителя должна открыться в заявленный текст, каждая запись
  получателя должна получиться заново байт в байт.
- Обе стороны подделки это производственная сессия e2e. Сторона отправителя идёт через интерфейс
  noise.Static: подставной ключ знает только открытую половину ключа отправителя и на каждое
  согласование отвечает согласованием ключа получателя, статического или эфемерного, с этой
  половиной (шаг 3). Эфемерный ключ получателя записывает, а при проверке подставляет обёртка над
  CryptoProvider; в производственном API задать эфемерный ключ нельзя.
- Проверка идёт на обоих наборах примитивов при обеих ролях получателя. Настоящий и подделанный
  транскрипты проходят Verify и одинаковы по структуре: те же записи по автору, виду и размеру,
  тот же открытый заголовок (вид и номер записи) и те же заявленные тексты. Две подделки одного
  сценария не делят ни эфемерного ключа, ни записи.
- Отрицательный контроль: подделка со свежим ключом вместо ключа получателя проходит Verify под
  этим ключом, а под ключом получателя Verify отвергает её первую запись, и это несовпадение
  криптографии, а не проверка имён.
- Обёртка провайдера, которая видит каждое согласование, видит закрытый ключ получателя при
  подделке, то есть подделка идёт через неё, и видит закрытый ключ отправителя в настоящей сессии
  и не видит его ни при подделке, ни при проверке. Тест создаёт отправителя вне lab/scenario и
  стирает его закрытый ключ до первого вызова: подделка всё равно проходит Verify.
- Отчёт `artifacts/deny-<набор>-<время>.json` несёт вердикты с номером записи, на которой
  отвергнут контроль, допущение и записи в hex (в записях рукопожатия открытые эфемерные ключи) и
  ни одного байта секретных ключей: тест читает его как закрытую схему и ищет в нём каждый кусок
  каждого секрета прогона. Это демонстрация на конкретных ключах, а не измерение.

Не заявляется: онлайн-отрицаемость, то есть против судьи, который во время сессии действует
вместе с получателем; отрицаемость метаданных (записи mailbox, наблюдения сети, тайминги
цепочек); засвидетельствованный транскрипт; устройство отправителя, скомпрометированное до
сессии. Формальной модели нет: аргумент опирается на симметрию Agree, проверенную тестами, и на
то, что других значений в транскрипте нет.

## Контейнер

Контейнер клиента (пакет vault, ARCHITECTURE, "Контейнер клиента") берёт у провайдера
PasswordKey, DeriveKey, DerivePair и AEAD, своих примитивов у него нет.

### Формулы контейнера

```
ctx_pw      = NewContext(p, "vault/password", соль)
W           = PasswordKey(пароль, ctx_pw)
ctx_s       = NewContext(p, "vault/volume", соль, [s])          s = 0, 1, номер области
k_s         = DeriveKey(W, "vault/volume", ctx_s, 32)            ключ тома; W освобождается сразу
ctx_b       = NewContext(p, "vault/block", [s], r)               th_b = ctx_b.Sum()
K_b         = DeriveKey(k_s, "vault/block", ctx_b, 32)           одна Seal или Open
область     = r || Seal(K_b, nonce = 0^NonceSize, открытый текст[4048], ad = th_b)
ctx_id      = NewContext(p, "vault/identity", соль, [s])
(priv, pub) = DerivePair(k_s, ctx_id)                            ключ личности
F           = DeriveKey(k_s, "vault/fetch", ctx_id, 16)          право забора
своя карточка = (набор, адрес mailbox карточки контакта, QueueID(F), pub)
```

| Обмен | Части | Длина T, c25519 / ГОСТ |
|---|---|---|
| `vault/password` | соль 32 | 79 / 77 |
| `vault/volume` | соль 32, номер области 1 | 80 / 78 |
| `vault/block` | номер области 1, r 32 | 79 / 77 |
| `vault/identity` | соль 32, номер области 1 | 82 / 80 |

- Соль это 32 байта crypto/rand, одна на файл и общая для двух томов: Open растягивает один
  пароль один раз и пробует обе области, поэтому ключи томов разводит номер области в ctx_s, а не
  соль. Это та свежая часть контекста, которую PasswordKey требует от вызывающего (раздел
  "Интерфейс").
- Один ключ на одну Seal: r это 32 свежих байта crypto/rand на каждую запечатку, поэтому нулевой
  nonce безопасен, как у записей сквозного слоя. nonce в файле нет; у MGM старший бит нулевого
  nonce равен 0, как требует режим.
- Пустой том запечатывается тем же кодом, но вместо k_s под ключом из 32 байт crypto/rand,
  который освобождается сразу после запечатки.
- На ключ тома три метки: `vault/block` на каждое r, `pair/1` внутри DerivePair и
  `vault/fetch`. HMAC под k_s это PRF, выходы независимы. Пару и F разводят метки при одном
  контексте ctx_id. Соль и номер области в ctx_id повторяют то, что уже вошло в k_s, и явно
  закрепляют личность за местом тома. Отдельного секрета личности перед DerivePair нет: разводит
  и так метка `pair/1`.
- Вывод личности (ctx_id, `pair/1`, `vault/fetch`) принадлежит формату файла v1, как цена
  `password/1`: другой вывод это purpose `pair/2` вместе с новым форматом файла (другой размер),
  иначе прежние контейнеры при открытии дали бы другие личности. Байт версии содержимого
  описывает только раскладку профиля, его читает vault/profile уже после вывода.
- Нулевой F (около 2^-128) и ErrNoScalar (меньше 2^-128) при создании дают ошибку без файла, при
  открытии ErrCorrupt; повторов нет. Прочие ошибки DerivePair и DeriveKey, в том числе ошибки
  secmem при нехватке памяти под mlock, отдаются как есть, а не как ErrCorrupt.
- vault и vault/profile не вызывают GenerateSigning, Sign и Verify: пара тома служит только
  согласованию (раздел "Подписи").

### Что в файле

В файле нет ключевого материала ни в каком виде, даже зашифрованного: ни ключа личности, ни F,
ни ключей сессии, ни W, k_s и K_b. В нём только соль и две запечатанные области, а в открытом
тексте записанного тома версия и карточка контакта. Это утверждение о байтах файла, а не о
стойкости: файл и пароль тома воспроизводят ключ личности и F так же, как пароль открыл бы их,
если бы они хранились в томе под ключом из пароля. Пароль без файла не даёт ничего: соль есть
только в файле.

### Один и несколько состояний файла

Игра: нарушитель получает файл в одном состоянии и пароль pw_a одного тома. Мир 0: вторая
область это пустой том под случайным выброшенным ключом. Мир 1: у второй области свой пароль
pw_b, сгенерированный (не меньше 80 бит) и не равный pw_a, и любое содержимое. Место тома pw_a
случайно в обоих мирах.

1. Гибрид 1. В мире 1 W_b = PasswordKey(pw_b, ctx_pw). Пока pw_b вне перебора, W_b для
   нарушителя неотличим от случайного (растяжение в модели случайного оракула), а тогда k_b и
   K_b неотличимы от случайных при PRF DeriveKey. Плата: доля перебранного пространства паролей
   и преимущество против PRF. Для сгенерированного пароля доля пренебрежима, для пароля,
   выбранного человеком, нет, поэтому он вне утверждения.
2. Гибрид 2. Под одноразовым случайным K_b с нулевым nonce открытый текст тома заменяется
   открытым текстом пустого тома той же длины 4048. Плата: преимущество против IND-CPA AEAD с
   одноразовым ключом.
3. Получился пустой том под случайным ключом с r из того же источника, а это и есть область
   мира 0. Миры совпадают.
4. Ключ второй области, выведенный из W_a, в обоих мирах её не открывает, и работа открытия
   одинакова: Open пробует обе области всегда.

- Допущения: IND-CPA AEAD с одноразовым ключом, PRF DeriveKey и сгенерированный пароль второго
  тома не меньше 80 бит. При них файл в одном состоянии и пароль одного тома не выдают, есть ли
  второй том.
- Ключ личности тома b это функция k_b, в файле его нет. Открытый ключ тома b у его контакта без
  pw_b различению не помогает: связать его с файлом можно только через k_b, то есть перебором
  пароля. Содержимое записанного тома не длиннее 339 байт, остаток открытого текста нули,
  распределение области то же.
- Несколько состояний: файл пишется один раз, при создании, поэтому состояния файла после
  создания совпадают байт в байт и не дают ничего сверх одного.
- Неотличимость файла без пароля от равномерных байт требует IND$: шифротекст и тег неотличимы
  от случайной строки. Для XChaCha20-Poly1305 с одноразовым ключом это стандартное допущение.
  Для Кузнечик-MGM оно следует из строения режима (гаммирование счётчиком, тег как выход
  блочного шифра) при PRP Кузнечика, но доказательства в работе нет: это допущение.
- Где аргумент кончается: пароль в переборе, метаданные файловой системы, память работающего
  клиента, окружение (времена строк журнала, mailbox, история оболочки). Формального
  доказательства нет, есть рассуждение; измерение в плане (EXPERIMENT, блок 5).

### Карточка

Карточка, построенная из тома, распределена так же, как карточка клиента -peer без контейнера.
Без контейнера на c25519 pub = X25519(clamp(u), 9) для равномерного u (GenerateEphemeral,
обрезку делает X25519), на ГОСТ k равномерен на [1, q-1], F равномерен на ненулевых 16 байтах.
Из тома те же формулы идут над выходом PRF под k_s: clamp(raw), выборка с отказом на [1, q-1], F
из DeriveKey с отказом от нуля. Различитель карточек с контейнером и без него дал бы различитель
PRF, поэтому ни контакт, ни mailbox по карточке о контейнере не узнают.

Контакт, у которого есть карточка владельца, проверяет догадку пароля через очередь только
вместе с солью из файла: PasswordKey, два DeriveKey и Hash для QueueID(F), без умножения на
точку. Цена та же, что у проверки по тегу области: одно растяжение на догадку.

## Работа с памятью (crypto/secmem)

- Буфер выделяется через mmap на отдельных страницах вне кучи Go, mlock, madvise(MADV_DONTDUMP).
- Release: зануление, munlock, munmap. Двойной Release не паникует.
- Процесс: prctl(PR_SET_DUMPABLE, 0), RLIMIT_CORE=0. Это закрывает ptrace и /proc/pid/mem для того
  же uid, против root не помогает.
- Страницы вне кучи, блокировка, запрет дампов и защита процесса работают только в сборке под
  Linux. В других системах буфер это срез на куче Go, который сообщает, что не заблокирован, а
  при освобождении только зануляется, и то лишь при включённом занулении. Защита процесса там
  возвращает ошибку: с флагами по умолчанию узел, клиент и jimichi enroll не стартуют и работают
  только с -harden=false и -keymem без lock.
- В контейнере mlock ограничен RLIMIT_MEMLOCK. Узел проверяет бюджет при старте, до создания
  первого ключа, и не стартует, если его меньше 80 КиБ или если блокировку просили, а она не
  вышла. Узел с ротацией держит по одной заблокированной странице на онион-ключ, не больше двух,
  и, когда хватает памяти, ещё четыре, которые отдаёт прямо перед созданием следующего ключа:
  одну под ключ, три под проверку его пары. Он берёт их при старте, после проверки пар своих
  ключей, после каждой ротации, а если тогда места не нашлось, то снова после освобождения
  заменённого ключа. Новый онион-ключ, страница которого не заблокирована, он не принимает.
- Каждая мера включается конфигурацией, чтобы измерить её вклад:

| Флаг | Что включает |
|---|---|
| -keymem all | все меры, по умолчанию |
| -keymem none | базовая сборка: ключи на куче Go, без блокировки, без запрета дампов, без зануления |
| -keymem offheap,lock,dontdump | всё, кроме зануления: вклад зануления в дамп процесса виден только с ключами на куче (none против zero), страницы вне кучи после munmap процессу уже не видны |
| -keymem offheap,lock,dontdump,zero | любое подмножество; lock и dontdump требуют offheap |
| -harden | prctl(PR_SET_DUMPABLE, 0) и RLIMIT_CORE=0 для процесса |

## Библиотеки

- ГОСТ: gogost 5.14.1 Сергея Матвеева (GPLv3), модуль github.com/pedroalbanese/gogost. Домен
  автора go.cypherpunks.su не отвечал, в прокси Go модуля нет, поэтому взято зеркало с тем же
  номером версии в коде, версия закреплена в go.mod и go.sum (псевдоверсия коммита
  44a1f1ec2524). Совпадение кода с авторским выпуском по независимому источнику не проверено,
  проверка в плане ([#50](https://github.com/jimichi-org/jimichi/issues/50)). Библиотечные пакеты
  зеркала проверены: ни сетевого, ни файлового ввода-вывода, unsafe только в быстром XOR.
  Соответствие стандартам проверяют контрольные примеры в crypto/gost: VKO по RFC 7836, KDF по
  Р 50.1.113-2016, Кузнечик-MGM по RFC 9058, Стрибог-256 по RFC 6986.
- Точка собеседника проверяется до VKO: координаты меньше p, точка на кривой и не из подгруппы
  порядка 2 или 4. Библиотека сама этого не делает, а на точке вне кривой ключ канала или
  онион-ключ узла можно было бы вытянуть по частям. Для смешанных точек кофактор 4 снимается
  внутри VKO.
- UKM для VKO это первые 8 байт хэша транскрипта как число little endian, ноль заменяется
  единицей; полный хэш идёт затравкой в KDF. Приём взят из KEG (RFC 9189, раздел 8.3.1): там UKM
  это первые 16 байт хэша, и ноль так же заменяется единицей. Другую длину UKM провайдер не
  принимает.
- Подпись берёт дайджест Стрибога в порядке байт gogost. Подписи проверяет только сама система,
  совместимость с другими реализациями не заявляется.
- c25519: golang.org/x/crypto (curve25519, chacha20poly1305, hkdf). Подпись Ed25519 по RFC 8032
  на filippo.io/edwards25519, прямо над буфером secmem. crypto/ed25519 начиная с Go 1.25 кэширует
  развёрнутый ключ по слабому указателю на ключ: на памяти mmap рантайм аварийно завершается, а на
  куче развёрнутый ключ живёт до сборки мусора.
- GenerateSigning в c25519 пишет seed из crypto/rand прямо в буфер secmem и выводит из него
  открытый ключ по RFC 8032 (раздел 5.1.5) на filippo.io/edwards25519, стирая свои скаляры и
  дайджесты. crypto/ed25519.GenerateKey оставлял бы seed и развёрнутый ключ в куче, а ключ подписи
  узла живёт всё время процесса. Копии внутри SHA-512 и edwards25519 остаются, они указаны в
  разделе "Известные дыры". Тест сверяет открытый ключ и подписи с ed25519.NewKeyFromSeed.
- PasswordKey в c25519: golang.org/x/crypto/argon2 (IDKey). Матрица 64 МиБ лежит на куче Go,
  четыре полосы считаются в своих горутинах, поэтому процессорного времени уходит около четырёх
  стен. Внутренний тест сверяет функцию с векторами эталонной реализации PHC, а константы цены с
  RFC 9106 (раздел 4).
- PasswordKey в ГОСТ: crypto/pbkdf2 стандартной библиотеки со Стрибогом-512 gogost.
  golang.org/x/crypto/pbkdf2 это замороженная обёртка над той же функцией, которая на ошибке
  падает. При GODEBUG=fips140=only crypto/pbkdf2 не принимает хэш вне SHA-2 и SHA-3, и PasswordKey
  набора ГОСТ возвращает ошибку. Внутренний тест сверяет функцию с примерами Р 50.1.111-2016 (c =
  1, 2 и 4096, пароль и соль с нулевыми байтами, dkLen 100). Пароль передаётся строкой, которая
  смотрит на байты буфера secmem (unsafe.String), а не копией: crypto/pbkdf2 пользуется ей только
  во время вызова, как ключом HMAC. Библиотека возвращает начало целого 64-байтового блока T_1, и
  провайдер зануляет весь блок.
- DerivePair в ГОСТ держит одно состояние KDF gogost (gost34112012256.NewKDF) на вызов, а не на
  кандидата; открытый ключ считается так же, как у эфемерной пары. Внутренние тесты сверяют
  выборку с подставным потоком кандидатов, а состав с прямым вызовом KDF и gost3410.
- Внутренние тесты обоих наборов проверяют шаги, которые держат ключевой материал вне кучи: KDF в
  DerivePair получает ключом байты секрета в secmem, и каждый выданный им кандидат зануляется, а
  растяжение PasswordKey получает байты пароля из буфера, соль и цену формулы, и весь его выход
  зануляется, при включённом занулении, а при выключенном нет. Проверки исходного кода покрывают
  то, чего такие тесты не видят, копию, оставленную на куче: выход библиотеки идёт только в буфер
  secmem, в копирование в него и в зануление своего среза, каждое число закрытого ключа gogost
  стирается отложенным wipe, а X25519 получает каждый закрытый ключ байтами его буфера.
  providertest проверяет, что при занулении PasswordKey вызывает одну принудительную сборку мусора,
  а без него ни одной.

## Известные дыры

secmem защищает только буферы, которыми код управляет сам. Библиотеки делают свои копии, и часть
из них живёт долго:

| Где | Что | Сколько живёт |
|---|---|---|
| x/crypto chacha20poly1305 | рабочий ключ AEAD, скопированный в структуру шифра; в сквозном слое ключ сообщения рукопожатия и ключ каждой записи mk_n | у цепочки и канала всю их жизнь, без зануления; в сквозном слое структура служит одной Seal или Open, а копия остаётся до повторного использования памяти кучи; сборка состояния AEAD на каждый вызов из ключа в secmem в плане ([#39](https://github.com/jimichi-org/jimichi/issues/39)) |
| crypto/ecdh | скаляр X25519, в том числе ключа канала, онион-ключей узла, ключа личности клиента и закрытого ключа DerivePair при вычислении открытого, и общий секрет, в том числе статический-статический (ss), одинаковый для всех сессий одной пары клиентов до KDF | до повторного использования освобождённой памяти кучи, возможно уже после освобождения самого ключа |
| x/crypto hkdf, crypto/hmac | внутренние блоки HMAC (ключ XOR константа) с PRK, секретом цепочки, секретом канала (ee или выход MixKey) и ключом сцепления MixKey, в сквозном слое с ck рукопожатия и ключами цепочек ратчета; состояние SHA-256 с общим секретом X25519 и вторым секретом MixKey; последний выведенный блок, в том числе mk_n, а в DerivePair необрезанный закрытый ключ, равносильный ему | до повторного использования памяти кучи; свою копию PRK провайдер зануляет, если зануление не выключено (-keymem none или список без zero) |
| генерация и подпись Ed25519 | состояние SHA-512 с seed или префиксом nonce, копия скаляра в edwards25519 | до повторного использования памяти кучи; свои скаляры и дайджесты генерация и подпись стирают всегда, в том числе при -keymem none |
| gogost, Кузнечик | раундовые ключи в структуре шифра, первые два из них сам ключ | всю жизнь цепочки или канала; Destroy их стирает, если зануление не выключено (-keymem none или список без zero) |

Арифметика gogost на math/big не константна по времени. Утечка ключа канала и онион-ключей узла
по времени VKO возможна для нарушителя, который меряет время ответа узла; атаки по сторонним
каналам вне модели угроз.

Пароль вместе с Context, под которым его растягивали, равносилен выходу PasswordKey и всему, что
из него выводится, поэтому копии пароля и рабочего состояния растяжения равносильны этому ключу.
В контейнере клиента из выхода PasswordKey выводятся ключ тома, ключ личности и F, а соль лежит в
файле. Поэтому пароль тома вместе с файлом равносилен ключу личности и F этого тома, и копии
пароля и рабочего состояния растяжения равносильны ключу личности.

Значения контейнера в строках таблицы:
- x/crypto hkdf, crypto/hmac (c25519): блоки HMAC с W (`vault/volume`) и с ключом тома k_s
  (`vault/block`, `vault/fetch`, DerivePair); последний блок читателя Expand это k_s в
  `vault/volume`, K_b в `vault/block`, необрезанный ключ личности, равносильный ему, в
  DerivePair и блок, начало которого F, в `vault/fetch`.
- gogost, KDF: состояния HMAC-Стрибог с W и k_s, в DerivePair одно на вызов; последний блок
  Стрибога, половина которого выход: копии k_s, K_b, F и каждого кандидата DerivePair, у
  последнего это принятый ключ личности.
- crypto/ecdh и gogost, ГОСТ Р 34.10: скаляр ключа личности, пока DerivePair вычисляет открытый
  ключ, на каждом открытии тома.
- x/crypto chacha20poly1305 и gogost, Кузнечик: ключ области K_b в структуре шифра на одну Seal
  или Open, как ключ записи mk_n сквозного слоя.

Время DerivePair в наборе ГОСТ:
- Число кандидатов зависит от секрета, но отвергнутые кандидаты это выходы псевдослучайной
  функции под другими номерами, независимые от принятого, и о закрытом ключе оно ничего не
  говорит. Для одного секрета оно постоянно, поэтому повторные вызовы с тем же секретом на одном
  устройстве уточняют и его, и время умножения на точку. Время умножения несёт то же, что VKO с
  этим ключом. В контейнере секрет это ключ тома, поэтому число кандидатов постоянно для тома и
  различает тома, а повторные открытия на одном устройстве уточняют его и время умножения; о
  ключе личности оно ничего не говорит.
- Проверка 0 < k < q на math/big переменна по времени. Старшее 64-битное слово q равно 2^62,
  поэтому для принятого кандидата сравнение решается на старшем слове, иначе лишь с вероятностью
  около 2^-62; с той же вероятностью SetBytes отбрасывает нулевое старшее слово. Сравнения за
  постоянное время нет: умножение gogost (double-and-add на math/big) всё равно переменно по
  времени.
- Стрибог и Кузнечик в gogost табличные: обращения к памяти зависят от ключа во всех вызовах KDF и
  AEAD. Как и прочие сторонние каналы, это вне модели угроз.

Куча Go объекты не перемещает, но освобождённую память не зануляет, а стеки горутин при росте
копируются. Mlock и MADV_DONTDUMP на эти копии не распространяются: заблокированы только страницы
secmem, поэтому копии ключей на куче и на стеках могут попасть в swap, а при -harden=false и в
дамп процесса. Блокировка всей памяти процесса в плане
([#36](https://github.com/jimichi-org/jimichi/issues/36)). Измерение того, сколько копий остаётся
и сколько они живут, запланировано в блоке 4 программы исследования
([#24](https://github.com/jimichi-org/jimichi/issues/24)) и пока не проводилось.
