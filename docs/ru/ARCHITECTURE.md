# Архитектура

[English](../en/ARCHITECTURE.md) | Русский

## Что это за система

Обмен сообщениями через цепочку узлов-ретрансляторов с вложенным шифрованием маршрута. Цепочку,
по умолчанию из трёх узлов, клиент выбирает случайно из списка узлов. В цепочке из двух и более
узлов ни один узел не видит одновременно клиента и сообщение: вход знает адрес клиента, выход
открывает сообщение. Ключевой материал узел держит в памяти процесса и на диск не пишет, размер
ячейки постоянный. Два клиента в режиме -peer разговаривают через mailbox на выходе своих
цепочек: сообщение запечатано сквозным слоем между клиентами (CRYPTO, "Сквозной слой"), и
mailbox хранит только записи постоянного размера, которые не может прочесть. Клиент без -peer
шлёт сообщения выходу, который возвращает их эхом: на этой топологии идут измерения.

## Компоненты

| Компонент | Назначение |
|---|---|
| client | выбирает и строит цепочку, шифрует слои, шлёт полезные и фоновые ячейки, принимает ответ; с -peer ведёт разговор с одним контактом через mailbox |
| relay | снимает свой слой, пересылает следующему узлу; на диск не пишет ничего; выходом отвечает эхом или как mailbox (-exit) |
| noise, e2e | сквозной слой между клиентами: карточка контакта, рукопожатие KK, хэш-ратчет |
| mailbox | очереди записей сквозного слоя на выходе, только в памяти |
| conversation | разговор клиента с контактом: заявка на каждом тике, окно put, пересборка цепочки |
| crypto | CryptoProvider: два набора примитивов за одним интерфейсом |
| crypto/secmem | буферы ключей вне кучи Go: mlock, запрет дампов, зануление |
| wire | формат ячейки и вложенное шифрование маршрута |
| vault | контейнер клиента: файл постоянного размера с одним или двумя томами под своими паролями; том хранит карточку контакта, а ключ личности и F выводятся из пароля тома и соли файла при каждом открытии (раздел "Контейнер клиента"); клиент -peer с контейнером в плане ([#20](https://github.com/jimichi-org/jimichi/issues/20)) |
| lab | прогон экспериментов, наблюдатель и метрики; отчёты в artifacts/ пишет cmd/lab |
| web | в плане ([#21](https://github.com/jimichi-org/jimichi/issues/21)), кода пока нет: дашборд стенда с графом сети, тем, что видит каждый узел, и результатом атаки в реальном времени |

## Поток сообщения

```
client-a -> вход A -> середина A -> mailbox (выход) <- середина B <- вход B <- client-b
```

Разговор двух клиентов -peer:

1. Клиенты знакомы: каждый закрепил карточку другого, в которой адрес mailbox, очередь и
   статический ключ (подраздел "Клиент -peer").
2. Каждый строит свою цепочку, выход которой это mailbox (шаги ниже относятся к каждой).
3. На каждом тике каждый клиент шлёт одну заявку: забор из своей очереди и put записи в очередь
   собеседника.
4. Сообщение запечатано сквозным слоем в запись 392 байта: сначала рукопожатие KK, затем
   хэш-ратчет (CRYPTO, "Сквозной слой"). mailbox кладёт запись в очередь получателя.
5. Получатель забирает запись ответом на свою заявку и открывает её своей сессией.

Клиент без -peer шлёт сообщения выходу, и выход с -exit echo (по умолчанию) возвращает каждое
как ответ: эту топологию измеряет обвязка lab. Построение одной цепочки:

1. У клиента есть список из N узлов и длина цепочки, по умолчанию три. Вход он выбирает
   равновероятно из N узлов, клиент -peer из N - 1 узлов, кроме mailbox.
2. Подписанные комплекты узлов списка клиент получает у входа, единственного узла, с которым он
   соединяется. Вход может не отдать до -missing из них (по умолчанию 1). Комплект это сертификат
   узла от УЦ и дескриптор с ключами узла, подписанный ключом подписи узла.
3. До установки цепочки клиент проверяет каждый комплект по якорю доверия, каждый отдельно
   (раздел "Аутентификация узлов"). Комплект, не прошедший проверку, считается узлом, которого
   вход не отдал, в пределах -missing. Комплект самого входа обязан пройти проверку, иначе
   клиент отказывается строить цепочку.
4. Остальные узлы цепочки он выбирает равновероятно из остальных узлов, комплекты которых прошли
   проверку, у клиента -peer середины, а последним mailbox (раздел "Выбор цепочки"), и с каждым
   узлом цепочки отдельно согласует эфемерный ключ сессии.
5. Клиент шифрует сообщение по слою на узел: внешний для входа, внутренний для выхода.
6. Каждый узел снимает ровно свой слой и узнаёт только адрес следующего хопа.
7. Ключи сессии живут до конца цепочки, их буферы зануляются. Копии, которые держат библиотеки,
   описаны в CRYPTO.

## Выбор цепочки

- Список узлов (-nodes) статический: N адресов, N не меньше длины цепочки. Обнаружения узлов
  нет. Длина цепочки (-hops) по умолчанию 3 и не больше, чем вмещает одна служебная ячейка: 4 на
  c25519, 3 на ГОСТ (раздел "Формат ячейки").
- Список проверяется при старте, до любого запроса и до любого выбора: некорректный или
  повторённый адрес, узлов меньше, чем хопов, или хопов больше, чем вмещает служебная ячейка,
  останавливают клиента.
- Вход выбирается равновероятно из N узлов. Остальные хопы выбираются, когда комплекты, которые
  отдал вход, проверены: равновероятно и без повторов из остальных узлов, комплекты которых
  прошли проверку, в порядке цепочки (первые шаги тасования Фишера-Йетса). Когда вход отдал все
  N узлов и все прошли проверку, каждая упорядоченная цепочка из разных узлов равновероятна, и
  три хопа из пяти узлов дают 60 цепочек. Когда вход отдал не все или не все прошли проверку
  (-missing), цепочка выбирается среди оставшихся (LIMITATIONS).
- Случайность берётся из системного генератора (crypto/rand). Выбор из m узлов читает 64 бита,
  отбрасывает значение и читает снова, пока оно меньше 2^64 mod m, и только потом берёт остаток
  по модулю m: без этого малые остатки выпадали бы чаще.
- Запрос ко входу не зависит от остальной цепочки: клиент просит одно зеркало и проверяет в нём
  комплект каждого узла списка, каждый отдельно, а не только тех, которые использует. Комплект,
  который не прошёл проверку, считается узлом, которого вход не отдал: цепочка выбирается среди
  остальных, а -missing (по умолчанию 1, не больше N минус длина цепочки) ограничивает
  отсутствующие и не прошедшие проверку узлы вместе. Зеркало, в котором нет комплекта самого
  входа или его комплект не прошёл проверку, означает отказ от цепочки: клиент соединяется со
  входом, и ему нужен проверенный комплект входа. Комплекты узлов между собой не сравниваются:
  слой установки и канал каждого узла привязаны к его личности (CRYPTO, раздел "Транскрипт").
- У клиента без -peer любой сбой завершает процесс: вход не отвечает, в зеркале нет проверенного
  комплекта самого входа или не хватает больше узлов списка, чем допускает -missing, установка не
  удалась. Оркестратор перезапускает клиента, и новый процесс выбирает новый вход. В пределах
  одного запуска клиент к другому входу не переходит, клиент -peer тоже.
- При случайной цепочке клиент не пишет в журнал, какие узлы в неё вошли. В журнале имя,
  отпечаток и срок сертификата каждого проверенного узла, в порядке списка (с -fixed-chain ещё
  и срок дескриптора), одна строка с числом проверенных узлов и узлов списка и одна строка с
  числом хопов и числом узлов списка. Неудачный запрос ко входу и сбой на цепочке записываются
  только видом причины (код ответа, предел размера, неудавшееся рукопожатие, истёкшее время,
  несостоявшееся соединение): сама ошибка называет адрес входа.
- -fixed-chain берёт первые -hops узлов списка в порядке списка, первый из них как вход, и
  ничего не выбирает случайно. Комплекты всех узлов списка, которые отдал вход, проверяются так
  же, но обязательны, и обязательно прошедшими проверку, только узлы самой цепочки, а ошибки
  называют узел полностью. Флаг
  предназначен для измерений, которым требуется известный путь; ни одно измерение его не
  использует: обвязка lab строит свою цепочку сама, в постоянном порядке.
- Когда N равно длине цепочки, цепочка это случайная перестановка списка.

Клиент -peer:

- Выход закреплён на mailbox (-mailbox, один из узлов списка). Вход выбирается равновероятно
  среди остальных N - 1 узлов (ChooseEntryExcept), середины равновероятно и без повторов среди
  узлов, которые не вход и не mailbox и комплекты которых прошли проверку, mailbox последним
  (ChooseRestTo). При полном зеркале каждая упорядоченная цепочка, которая кончается на mailbox,
  равновероятна.
- Зеркало принимается по тому же правилу и ещё должно содержать проверенный комплект mailbox,
  иначе отказ `the entry holds no bundle for the mailbox` (JudgeMirrorTo). mailbox поэтому
  никогда не бывает входом.
- -hops не меньше 2: при одном хопе mailbox был бы и входом. С -fixed-chain узел номер -hops в
  списке обязан быть mailbox.
- Строк по узлам списка у -peer нет; ни путь, ни адреса узлов в журнал не пишутся, отказы и сбои
  только видом причины.
- Конец цепочки не конец разговора. Пересборка всегда идёт через тот же вход и по свежему
  зеркалу этого входа:
  1. сначала та же цепочка: те же середины и тот же mailbox, с ключами из нового зеркала;
  2. новые середины выбираются, только когда эту цепочку установить нельзя: в зеркале нет её
     узла, соединение со входом не удалось или две цепочки подряд через неё кончились раньше
     первого ответа (установку, которую вход или середина не продолжили, клиент видит только
     так); так бывает не больше 2 раз за процесс;
  3. после этого клиент снова и снова устанавливает последнюю выбранную цепочку. Остановить
     разговор вход, mailbox или середина могут всегда, направлять выбор середин дальше не может
     никто.
- Закрытие дальней стороной, истёкшее ожидание ответа, отказ ответа и неудавшаяся отправка
  подчиняются одному правилу, ни одно из них не даёт выбора сверх предела. Зеркало, которое
  клиент не принимает, не даёт ни выбора, ни установки. Предел и вероятность, с которой
  подставной вход или подставной mailbox получает середину-сообщника, посчитаны в LIMITATIONS.
- Паузы между попытками и предел по времени задаёт драйвер разговора: 1 с, удвоение до 60 с, не
  дольше 10 мин, затем выход с кодом 1; три отказа ответа за 10 мин дают код 3 (подраздел
  "Разговор").
- С -fixed-chain пересборка всегда устанавливает ту же цепочку и ничего не выбирает.

## Формат ячейки

Ячейка постоянного размера 512 байт, формат одинаков для полезных и фоновых ячеек.

| Поле | Размер | Назначение |
|---|---|---|
| version | 1 | версия формата |
| kind | 1 | данные, служебная, заполнение канала |
| circuit | 8 | идентификатор цепочки, свой на каждом канале между соседями |
| counter | 8 | номер ячейки на канале, источник nonce и защита от повтора; на каждом канале своё значение |
| body | 494 | слои: по тегу аутентификации в 16 байт на хоп, длина и полезная нагрузка |

- Nonce не передаётся: он выводится из направления, идентификатора цепочки и counter. Ключ
  принадлежит одному узлу одной цепочки, поэтому пара (направление, counter) под ним не повторяется.
- Counter принимает своё значение на каждом канале цепочки. При установке узел выводит из общего
  секрета с клиентом два смещения, по одному на направление, и прибавляет своё смещение по модулю
  2^62 к counter каждой ячейки, которую передаёт дальше. Клиент знает смещения всех узлов и шифрует
  слой каждого узла тем значением, которое придёт на канал в этот узел. Служебная ячейка от этого
  не растёт.
- Номер ячейки в каждом направлении меньше 2^60, поэтому за жизнь цепочки значения одного канала
  не повторяются.
- Каждый слой это AEAD над содержимым следующего слоя. Ассоциированные данные включают версию,
  вид ячейки, counter канала в этот узел и номер узла в цепочке, поэтому ячейку нельзя подставить
  на чужую позицию, а узел не может сдвинуть counter, не сломав слой.
- Идентификатор цепочки переписывается на каждом канале и в ассоциированные данные не входит:
  слой привязан к нему через nonce, а ключ хопа выведен под транскриптом установки, в который
  входит идентификатор канала в этот узел (раздел "Установка цепочки"). Вперёд узел находит
  цепочку по идентификатору ячейки и строит из него nonce. Назад узел идентификатор пришедшей
  ячейки не читает и ставит свой, а клиент сверяет идентификатор ответа с идентификатором своего
  канала.
- Слой узла с номером i занимает первые 494 - 16 * i байт тела. Сняв свой слой, узел дополняет
  тело случайными байтами до 494, поэтому на каждом канале ячейка одного размера и позиция узла
  в цепочке по размеру не видна.
- Полезная и фоновая ячейки снаружи одного вида "данные". Признак фоновой лежит внутри последнего
  слоя, в старшем бите поля длины: его видит только выход. Узлы на пути, включая вход, который
  знает клиента, не отличают фоновую ячейку от полезной.
- Полезная нагрузка внутри последнего слоя: два байта длины, данные, случайное заполнение.
  При трёх узлах на сообщение остаётся 444 байта, в обоих наборах; при четырёх, только на
  c25519, остаётся 428.
- Служебная ячейка вмещает четыре узла на c25519 и три на ГОСТ: открытый ключ ГОСТ 64 байта
  против 32, и каждый слой установки дорожает на эту разницу. Это ограничивает длину цепочки, и
  клиент при старте сверяет с этим -hops.
- Counter на каждом канале идут строго подряд: узел принимает ячейку, только если её counter на
  единицу больше предыдущего принятого по модулю 2^62. Узел, кроме выхода, берёт первое значение
  в каждом направлении как пришло: оно зависит от смещений других узлов. Выход ждёт заданное
  первое значение прямого направления, а клиент проверяет номер каждого ответа (раздел "Обратный
  канал"). Копия, пропуск, шаг назад или скачок
  закрывают цепочку, и ячейка дальше не идёт: пропущенный повтор дал бы активному наблюдателю
  бесплатную временную метку, а пропуск или перестановка прошли бы на все следующие каналы.
- Выход знает, с каким counter придёт первая прямая ячейка: клиент кладёт это значение в слой
  выхода при установке. Ячейки, потерянные в начале цепочки на любом узле, выход видит как
  нарушение порядка и закрывает цепочку.
- Прямую ячейку узел сначала открывает и только потом проверяет её counter. Ячейка, которая не
  открылась, отбрасывается и на порядок не влияет.
- Клиент присваивает counter в момент записи ячейки в канал, после случайной задержки, поэтому
  ячейки уходят в порядке counter.

## Канальное шифрование

Ячейка между соседями идёт не открыто, а внутри зашифрованного кадра. Без этого слоя заголовок
ячейки виден на проводе: наблюдатель на канале видел бы вид, идентификатор цепочки и counter
каждой ячейки.

- Рукопожатие: инициатор присылает байт режима и эфемерный открытый ключ. Ответчик присылает
  свой эфемерный открытый ключ и один кадр: ячейку заполнения канала, зашифрованную как кадр 0
  своего направления. Общий секрет из двух эфемерных ключей даёт прямую секретность канала.
- Этот кадр подтверждает ключи до отправки любой ячейки. Инициатор завершает рукопожатие, только
  когда кадр открылся под выведенными им ключами и содержит ячейку заполнения, в пределах срока,
  заданного тем, кто соединяется. Иначе рукопожатие не состоялось, и инициатор не отправил
  ничего, кроме своего приветствия. Ответчик шлёт кадр в обоих режимах, кадры его направления
  дальше идут с номера 1. Часть ответчика в рукопожатии это его ключ и этот один кадр: 32 + 528
  байт на c25519, 64 + 528 на ГОСТ.
- Ключи кадров привязаны к транскрипту рукопожатия: версия формата, байт режима, эфемерные ключи
  обеих сторон в том виде, как они прошли по проводу, а в аутентифицированном режиме ещё и ключ
  канала ответчика и, при аутентификации узлов, ключ личности ответчика, который заверяет его
  сертификат. Хэш транскрипта входит в каждое согласование и в вывод каждого ключа (CRYPTO,
  раздел "Вывод ключей"). Байт приветствия или ответа, изменённый в пути, либо отвергается сразу
  (неизвестный режим, ключ, который не принимает согласование), либо даёт сторонам разные ключи,
  и кадр подтверждения не открывается; в любом случае рукопожатие не проходит.
- В аутентифицированном режиме инициатор делает второе согласование, своего эфемерного ключа с
  ключом канала ответчика из проверенного дескриптора: клиент для входного узла, узел для
  следующего узла цепочки. Два секрета сцепляются (MixKey), и ключи кадров зависят от обоих.
  Поэтому каждый канал цепочки аутентифицирован до узла, к которому он ведёт: ключи кадров
  выводит только владелец этого ключа канала, привязавший ту же личность, и ответчик без них не
  может выдать подтверждение и не получает ни одной ячейки. Ответчик кладёт в транскрипт свой
  опубликованный ключ канала и свой ключ личности, а приветствие в аутентифицированном режиме к
  ответчику без ключа канала отклоняется до любого согласования. Инициатора ответчик не
  аутентифицирует.
- Узел продолжает цепочку только на узел своего ростера, проверенный дескриптор которого у него
  есть (раздел "Аутентификация узлов"). Установка с любым другим адресом отклоняется без
  соединения и учитывается счётчиком (refused_extend). Следующему узлу, который не завершил
  рукопожатие, служебная ячейка не отправляется, и сбой учитывается счётчиком (failed_extend).
  В обоих случаях служебная ячейка учитывается и среди отброшенных, как у любой неудавшейся
  установки.
- Без аутентификации узлов (-auth=false) проверенных ключей канала у узла нет: он продолжает
  цепочку на любой адрес, а его канал до следующего узла анонимный. Анонимный канал скрывает
  заголовки только от пассивного наблюдателя. Это конфигурация без меры: так запускает свои узлы
  обвязка lab, а с конфигурацией с аутентификацией её не сравнивает ни один блок экспериментов.
- Из секрета выводятся два ключа, по одному на направление. Nonce это номер кадра в направлении.
- Привязка не занимает ни байта на проводе: в приветствии, ответе и кадре для неё нет полей.
- Кадр это ячейка 512 байт плюс тег 16 байт, итого 528. На проводе после рукопожатия только кадры
  одного размера, ни идентификаторов, ни счётчиков.
- Все примитивы канального слоя берутся из того же CryptoProvider, поэтому канал работает и на
  наборе ГОСТ.
- Ячейка вида "заполнение канала" живёт только на одном канале: её создаёт отправитель кадра,
  а принимающая сторона канала отбрасывает её, не передавая в цепочку. Снаружи она неотличима
  от любого другого кадра.

## Режимы отправки

| Режим | Как идут ячейки | Что видно наблюдателю |
|---|---|---|
| Немедленный | ячейка уходит, как только есть что отправить, фоновые добавляются сверху | рисунок отправок повторяет разговор |
| Постоянная скорость | ячейки уходят по расписанию, полезная занимает место фоновой | рисунок на канале не зависит от разговора |

Второй режим и есть мера против связывания потоков. Цена: сообщение ждёт своего слота, поэтому
задержка растёт при низкой скорости расписания и падает при высокой. Очередь клиента вмещает 256
сообщений: когда сообщения приходят чаще, чем их отправляет расписание, и очередь полна, новое
сообщение отбрасывается и учитывается счётчиком, а вызывающий код ошибки не получает.

Клиент -peer требует -mode fixed, но расписание у него своё: драйвер разговора шлёт ровно одну
заявку на каждый тик -rate через немедленный режим библиотеки, пока есть цепочка, и фоновых
ячеек провода не шлёт. Заявка есть на каждом тике, есть ли сообщение или нет, поэтому рисунок на
канале от разговора не зависит. -jitter задерживает каждую заявку внутри её тика и должен быть
меньше -rate.

Постоянной скорости на клиенте мало: узел, пересылающий ячейку сразу, переносит фазу расписания
клиента на следующий канал, и она доходит до выхода. Поэтому узел умеет отправлять по своим часам.

- Параметр узла: период отправки. Ноль означает немедленную пересылку, как без меры.
- На каждую цепочку и каждое направление у узла своя очередь и свой таймер. На каждом тике
  уходит одна ячейка из очереди, а если очередь пуста, ячейка заполнения канала.
- Первый тик выпадает на случайный момент внутри периода. Иначе таймер стартовал бы вместе с
  установкой цепочки, а она идёт сквозь цепочку почти мгновенно, и фаза клиента снова
  совпала бы с фазой узла.
- Очередь ограничена, чтобы ни память узла, ни задержка не росли без предела, если клиент шлёт
  чаще периода узла. Ячейка, пришедшая в полную очередь, закрывает цепочку: узел не теряет ячеек
  цепочки, потеря сломала бы порядок counter на следующих каналах. Такое закрытие учитывается в
  счётчике закрытых цепочек.
- Перетасовки между цепочками нет: каждая цепочка идёт по своим TCP-соединениям, и смешивать
  на канале нечего. Режим перемешивания с переупорядочиванием между цепочками в плане
  ([#82](https://github.com/jimichi-org/jimichi/issues/82)).

Вход и середина отправляют по своим часам в обе стороны, выход только в обратную: вперёд ему
отправлять некому. Цена меры: на каждом таком шаге ячейка ждёт в среднем половину периода, то
есть около двух с половиной периодов на круг туда и обратно, а по каналам между узлами и от
входа к клиенту идёт постоянный поток на каждую цепочку, даже когда клиент молчит.

Мера закрывает тайминг ячеек данных от наблюдателя на канале, по которому шлёт узел с включённой
мерой. Служебная ячейка установки и моменты открытия и закрытия соединений цепочки идут не по
часам узла и остаются видны (LIMITATIONS). Соседний узел снимает канальное шифрование и по виду
ячейки отличает заполнение от настоящей ячейки, против нарушителя-узла мера не работает.

## Обратный канал

Ответ идёт по той же цепочке в обратную сторону: выходной узел накладывает свой слой, каждый
следующий узел добавляет свой, и только клиент снимает их все. Направление входит в nonce, поэтому
прямые и обратные ячейки под одним ключом никогда не совпадают по nonce. Счётчик обратного
направления свой, и каждый узел проверяет порядок counter в каждую сторону отдельно. Как и
прямой, он принимает своё значение на каждом канале: выход и каждый узел на обратном пути
прибавляют своё смещение обратного направления.

Обратную ячейку узел проверить не может: её внутренние слои ему не открываются. Поэтому назад он
пропускает только ячейки вида "данные" со следующим по порядку counter, а любая другая закрывает
цепочку.

Выход нумерует ответы с нуля, а клиент знает смещения всех узлов и восстанавливает номер каждого
ответа. Клиент проверяет каждый ответ, фоновый и полезный одинаково, в таком порядке:

| Проверка | Что её не проходит |
|---|---|
| заголовок: версия, вид "данные", идентификатор цепочки на канале клиента | ячейка другой версии или вида, чужой идентификатор; ответ, которому вход сменил вид на "заполнение канала", до этой проверки не доходит: его отбрасывает канал (link.ReadCell), и он считается ответом, который не пришёл |
| открываются все слои | изменённое тело или counter, ячейка, которую никто не шифровал, ячейка другой цепочки, направления или позиции, негодная длина под последним слоем |
| номер ответа строго следующий | копия, пропуск, шаг назад, перестановка настоящих ответов |
| номер меньше числа ячеек, которые клиент записал в канал | ответ на ячейку, которую клиент не писал: выход отвечает на каждую ячейку один раз |

Допуска нет: первый ответ, не прошедший проверку, закрывает цепочку, и после него клиент ничего
не читает. Ответ не по порядку нельзя принять, не приняв пропуск или повтор, а лишний ответ не
отвечает ни на одну ячейку клиента. Ответ с негодным заголовком или не открывшийся номера не
занимает, и вперёд узел такую ячейку отбрасывает, а цепочку держит; клиент закрывает цепочку и
здесь: честная цепочка таких ответов не даёт, а ответ, место которого заняла такая ячейка, уже
потерян. О закрытой им цепочке клиент помнит только, какую из четырёх проверок ответ не прошёл
или что кадр на канале от входа не открылся. Ответ, который не пришёл, эти проверки не замечают.

Ответ, который не помещается в ячейку, выход заменяет фоновым ответом под тем же номером. Длина
проверяется до шифрования, поэтому nonce не используется дважды. Любой другой сбой при
шифровании ответа закрывает цепочку.

Выход отвечает на каждую ячейку данных ровно одной обратной: на сообщение ответом, на фоновую
ячейку фоновым ответом. Если бы ответ шёл только на сообщения, число и моменты обратных ячеек
показали бы любому узлу на обратном пути, какие ячейки были настоящими. Число совпадает в любом
режиме; моменты совпадают, только если доставка на выходе занимает постоянное время или узлы
отправляют по своим часам.

С -exit mailbox ответом на каждую ячейку данных служит ответ mailbox постоянной длины 396 байт,
и вместо эха выход делает ограниченную работу на заявку: один хэш, операции над картами и
списками, копию одной записи. Постоянной эта работа не является (подраздел "Хранилище"):
разница в микросекундах видна вне выхода, только когда выход пересылает сразу.

## Сквозной слой и mailbox

Хранилище на выходе (пакет mailbox, `cmd/relay -exit mailbox`), сквозной слой (пакеты noise и
e2e, CRYPTO), драйвер разговора (пакет conversation, подраздел "Разговор") и клиент, который ими
пользуется (`cmd/client -peer`, подраздел "Клиент -peer"). На стенде все relay запущены с -exit
mailbox, а оба клиента держат очереди на relay-5.

Что выход делает с полезной нагрузкой ячейки данных, задаёт флаг -exit:

| -exit | Ответ |
|---|---|
| echo (по умолчанию) | та же полезная нагрузка |
| mailbox | ответ mailbox, всегда 396 байт |
| none | фоновый ответ |

Формат ячейки не меняется. Заявка и ответ mailbox это полезная нагрузка обычной ячейки данных,
остаток тела wire заполняет случайными байтами. Клиент шлёт одну заявку на тик: забор из своей
очереди и, когда есть что класть, put в очередь собеседника. Запись это шифротекст сквозного слоя
постоянного размера 392 байта, для mailbox непрозрачный.

| Хопов | Ёмкость ячейки | Остаток после заявки 427 | Остаток после ответа 396 |
|---|---|---|---|
| 2 | 460 | 33 | 64 |
| 3 | 444 | 17 | 48 |
| 4 (только c25519) | 428 | 1 | 32 |

### Очередь и право забора

- Право забора F: 16 случайных байт владельца очереди, не все нули.
- Идентификатор очереди: `QueueID(F) = NewContext(p, "mailbox/queue", F).Sum()[0:16]`. Длина
  транскрипта 62 байта на c25519 и 60 на ГОСТ.
- Забирает тот, кто знает F; кладёт тот, кто знает идентификатор. mailbox видит F в каждой заявке,
  а хранит только идентификатор.

### Заявка, 427 байт

| Смещение | Байты | Поле |
|---|---|---|
| 0 | 1 | версия, 0x01 |
| 1 | 2 | тег, u16be: номер заявки на цепочке по модулю 2^16 |
| 3 | 16 | F; нули: забора нет |
| 19 | 16 | идентификатор очереди для put; нули: put нет |
| 35 | 392 | запись; нули без put |

### Ответ, 396 байт

Ответ есть на каждую ячейку данных, nil не бывает.

| Смещение | Байты | Поле |
|---|---|---|
| 0 | 1 | версия, 0x01 |
| 1 | 2 | тег заявки; 0, если заявка короче 3 байт |
| 3 | 1 | статус |
| 4 | 392 | запись или нули |

| Биты статуса | Значение |
|---|---|
| 0x80 | плохая заявка: длина не 427, версия не 1 или идентификатор, отличный от привязанного к цепочке; прочие биты 0, запись нули |
| 0-1 | put: 00 не просили, 01 сохранено, 10 очередь полна или достигнут общий предел записей, 11 отказ: нет места для новой очереди |
| 0x04 | в поле записи голова очереди |
| 3-6 | всегда 0 |

Клиент сопоставляет ответ с самой старой заявкой без ответа по позиции: ответы цепочки идут
строго по порядку, тег это проверка. Ответ плохой, если:

- длина не 396, версия не 1, бит из 3-6 не 0, 0x80 вместе с другим битом, ненулевая запись без
  0x04 (ParseReply);
- тег не тот, 0x80 на правильную заявку, биты put не 00 на заявку без put или 00 на заявку с put,
  0x04 на заявку без F (Reply.Answers).

Плохой ответ цепочку не закрывает: исход put неизвестен, запись отбрасывается. mailbox и так может
ронять всё, закрытие дало бы ему ещё один дешёвый рычаг.

### Хранилище

Обработка одной заявки:

1. Хэш QueueID(F) считается до проверок и до блокировки, на каждой заявке, при нулевом F и при
   плохой заявке тоже: считается ли он, от содержимого заявки не зависит.
2. Длина не 427 или версия не 1: ответ 0x80.
3. Привязка: цепочка (идентификатор на входящем канале выхода, он уникален среди живых цепочек
   узла) получает очередь забора от первого ненулевого F и очередь put от первого ненулевого
   идентификатора put. Заявка с другим идентификатором в уже заданном поле получает 0x80 целиком,
   ни put, ни забора. Честный клиент забирает из одной очереди и кладёт в одну.
4. Put: очередь полна или достигнут общий предел записей: 10. Очереди нет и очередей уже предел:
   вытесняется очередь, которую дольше всех не забирали, если её не забирали в пределах TTL,
   иначе 11. Затем очередь создаётся, запись копируется с временем прихода: 01.
5. Забор: если очередь есть, отмечается время забора, просроченные записи головы удаляются, голова
   снимается в ответ и ставится 0x04. Забор очередь не создаёт.
6. Срез полезной нагрузки зануляется, ответ собирается в новом срезе.

- Очередь живёт, пока владелец забирает. Она удержана, пока последний забор, а для очереди,
  которую ещё не забирали, её создание, было в пределах TTL, открыта ли ещё цепочка, которая это
  сделала, или нет. Удержанную очередь не вытесняет никто.
- Цепочка привязана к одной очереди забора и одной очереди put на всю жизнь, поэтому удерживает
  не больше двух. Put удержание не продлевает. Цена удержания N очередей зависит от того, сколько
  живут цепочки:
  - Цепочка, которая закрывается после своих заявок, удерживает созданную её put очередь на TTL
    от создания и очередь, из которой забирала, на TTL от последнего забора, в том числе после
    закрытия. N очередей стоят около N/2 установок цепочек за TTL. Установку ограничивает каждый
    узел по адресу источника, mailbox тоже, и у него предыдущий relay это один источник: при 0,2 в
    секунду и TTL 5 мин один источник даёт около 60 установок, то есть около 120 удержанных
    очередей, и 1024 очереди по умолчанию занимают около 9 источников.
  - Открытая цепочка удерживает свою очередь забора, пока живёт: каждый забор начинает TTL
    заново, а каждая заявка заново начинает срок простоя цепочки (-idle-timeout, 5 мин; фоновые
    ячейки не считаются), поэтому одна заявка за 5 мин держит и то и другое до -circuit-lifetime,
    24 ч. Созданная её put очередь удержана на TTL от создания, а дальше только заборами. N
    очередей стоят N открытых цепочек по одной заявке за TTL, то есть N установок за 24 ч. У
    mailbox каждая открытая цепочка это один входящий канал: не больше 32 от одного предыдущего
    relay и 512 всего (-max-links-per-source, -max-links), общих с честными цепочками.
- Таблица привязок ограничена; при переполнении вытесняется привязка, которую дольше всех не
  видели. Вытесненная честная цепочка привязывается заново теми же идентификаторами.
- Раз в 30 с удаляются просроченные записи, пустые очереди, которые не забирали в пределах TTL, и
  привязки, которых не видели дольше TTL.
- Снятие при заборе это подтверждение: повторной выдачи нет. Перезапуск узла теряет всё.
- Ответ несёт только тег, статус и запись: ни глубины очереди, ни времени, ни идентификаторов.
- Массив записи зануляется, когда её забирают, когда она просрочена, когда вытеснена её очередь и
  при остановке узла. Копии заявки остаются в теле ячейки, в буфере канала и в транскрипте хэша
  на куче, их никто не зануляет.
- Работа на заявку ограничена, но не постоянна: один хэш, операции над картами и списками, копия
  одной записи при put или снятой голове и не больше -mailbox-depth удалений просроченных записей
  в голове забираемой очереди. Ни одна заявка не перебирает очереди, перебирает только чистка по
  таймеру. Разница в микросекундах; вне выхода она видна, только когда выход пересылает сразу
  (-period 0).

| Предел | Флаг | По умолчанию |
|---|---|---|
| TTL записи и удержания очереди | -mailbox-ttl | 5 мин |
| записей в очереди | -mailbox-depth | 16 |
| очередей | -mailbox-queues | 1024 |
| записей всего | -mailbox-records | 16384, 6,1 МиБ записей |
| привязок цепочек | нет | 4096 |

mailbox видит по каждой цепочке обе её очереди, время каждой заявки и результат put, поэтому
связывает две цепочки одного разговора. Записи он прочесть не может.

Счётчики (агрегаты): mailbox_requests, mailbox_queues, mailbox_records, mailbox_bindings,
mailbox_puts, mailbox_put_full, mailbox_put_refused, mailbox_fetches, mailbox_hits,
mailbox_expired, mailbox_evicted, mailbox_bad. Они есть только в /stats на loopback и только при
-exit mailbox, в строку stdout раз в минуту не попадают: stdout уходит в журналы kubelet на диске
узла, а число очередей и записей показало бы ожидающие сообщения.

### Разговор

Пакет conversation ведёт разговор клиента с одним контактом поверх цепочки, которая кончается на
mailbox. Сессию (рукопожатие KK, ратчет, устаревание) ведёт пакет e2e (CRYPTO, раздел "Сквозной
слой"), а conversation решает, что и когда класть. Им пользуется клиент -peer (подраздел ниже).

Тик:

- Каждые rate ровно одна заявка, пока есть цепочка; во время пересборки ячеек нет.
- Каждая заявка забирает из своей очереди, до закрепления контакта и после. Тег заявки это её
  номер на цепочке по модулю 2^16; на новой цепочке счёт снова идёт с нуля.
- Put в очередь собеседника выбирается по первой подходящей строке:

| Условие | Put |
|---|---|
| в полёте уже W заявок с put | нет |
| есть залипшая запись текущей эпохи | её копия, те же байты |
| сессия предлагает запись рукопожатия (kk1 у инициатора, kk2 у ответчика) | эта запись, она становится залипшей |
| инициатор ещё не запечатал первую запись после kk2 | новая запись, она становится залипшей (подтверждающая запись) |
| режим отказа | новая запись, она становится залипшей (зонд) |
| иначе | новая запись |

- Новая запись настоящая, если есть сообщение и сессия может его запечатать (ответчик только
  после подтверждения). Иначе фиктивная, если включены покрывающие put (CoverPuts), если
  инициатор ещё не запечатал первую запись после kk2 или если с последней запечатанной записи
  прошло 30 с (keepalive). Иначе put нет. Устаревшая сессия и сессия, рукопожатие которой не
  завершено, новых записей не дают.

Окно и залипшая запись:

- Put идут конвейером: до W = 16 заявок с put без ответа, новая запись на каждом тике. Пока W x
  rate больше круговой задержки цепочки, put есть на каждом тике, и рисунок put от задержки не
  зависит.
- Отказ put (10 или 11) включает режим отказа: настоящее тело незалипшей записи возвращается в
  выходную очередь на своё место по порядку отправки, незалипшая фиктивная запись забывается,
  залипшая запись остаётся.
- В режиме отказа одна запись (зонд) кладётся копиями тех же байтов на каждом тике, пока на одну
  из копий не придёт 01; тогда режим выключается и конвейер возобновляется. Копии получатель
  отбрасывает по номеру записи.
- Запись рукопожатия тоже кладётся копиями, пока не придёт 01; тогда сессия узнаёт, что mailbox
  её хранит, и с этого момента инициатор ждёт kk2. Копии kk2 прекращаются и тогда, когда пришла
  первая запись инициатора.
- Первая запись инициатора после kk2 (подтверждающая, настоящая или фиктивная) тоже кладётся
  копиями, пока не придёт 01: только она позволяет ответчику запечатывать настоящие сообщения, а
  без CoverPuts за ней до keepalive ничего бы не последовало. В режиме отказа она и есть зонд.
  После 01 она больше не кладётся, как и любая запись (Пересборка).
- Исход копии уже снятой залипшей записи ничего не меняет.

Ответ:

- Ответ относится к самой старой заявке без ответа по позиции, тег это проверка; разбор строгий
  (раздел "Ответ, 396 байт").
- 01: залипшая запись снимается; настоящее тело, зонда, подтверждающей или незалипшей записи,
  считается доставленным в mailbox и зануляется.
- 10 и 11: режим отказа, залипшая запись остаётся и кладётся дальше.
- Плохой ответ: исход put неизвестен, это как 10, но режим отказа не включается; цепочка не
  закрывается. Запись из разобранного ответа всё равно идёт в сессию: mailbox уже снял её с
  очереди, а сессия её проверяет и отбрасывает повтор.
- Запись из ответа до закрепления держится (до 16, самая старая вытесняется) и после закрепления
  идёт в сессию по порядку; после закрепления идёт в сессию сразу.
- После закрепления разобранный ответ без открывшейся записи это отвеченный забор для правила
  устаревания; плохой ответ забором не считается.
- Открывшееся сообщение уходит вызывающему через очередь на 256; при полной очереди оно
  отбрасывается и считается.

Эпохи:

- Эпоха сессии растёт при каждом новом рукопожатии: рестарт инициатора (нет kk2 60 с после
  сохранения kk1, устаревание, кончились номера записей) и замена сессии у ответчика свежим kk1.
- При смене эпохи залипшая запись прежней эпохи выбрасывается, настоящие тела ожидающих заявок
  прежней эпохи сразу возвращаются в выходную очередь, исходы их put больше ни на что не влияют,
  и первой кладётся запись рукопожатия новой эпохи.
- Тело с неизвестным исходом отправляется снова, поэтому возможен дубликат; порядок сообщений при
  отказах не гарантирован.

Устаревание и новое рукопожатие:

- Сессия устаревает после 90 с отвеченных заборов без открывшейся записи собеседника; в сессию
  это уходит как 90 с / rate заборов, 450 при rate 200 мс (CRYPTO, раздел "Рукопожатие KK").
- Честный разговор не устаревает: с CoverPuts каждая сторона кладёт запись на каждом тике, без
  него keepalive раз в 30 с.
- Разрыв больше 64 записей в одном направлении (пачка, потерянная у mailbox) снимается новым
  рукопожатием не дольше чем за 2 x 90 с плюс 60 с ожидания kk2.

Пересборка:

- Конец цепочки: дальняя сторона закрыла её, клиент отказал ответу, отправка не удалась или самая
  старая заявка ждёт ответа дольше 10 с (тогда цепочку закрывает сам драйвер).
- Заявки без ответа получают исход "неизвестен"; залипшая запись остаётся.
- Запись, которую mailbox выдал в ответе на заявку без ответа, пропала: mailbox снимает запись при
  выдаче, а после 01 на одну из копий отправитель её больше не кладёт. Если до получателя не
  дойдёт другая сохранённая копия (при круговой задержке короче rate mailbox хранит одну),
  настоящее сообщение теряется, потеря kk1 или kk2 стоит 60 с ожидания kk2 и нового рукопожатия,
  а без подтверждающей записи ответчик запечатывает настоящие сообщения только после того, как
  откроется следующая запись инициатора: с CoverPuts на следующем тике, без них со следующим
  сообщением инициатора или его keepalive через 30 с после подтверждающей записи.
- Новую цепочку строит функция вызывающего Dial. У клиента -peer это тот же вход, свежее зеркало
  у него, сначала та же цепочка, а новые середины к тому же mailbox только тогда, когда её
  установить нельзя, и не больше 2 раз за процесс (раздел "Выбор цепочки"). Сессия, личность,
  право забора, закрепление и выходная очередь живут весь разговор, пересборка их не трогает.
- Перед первой попыткой пауза 1 с, после каждой неудачи пауза удваивается, но не больше 60 с.
  Цепочка, в ячейку которой заявка не помещается, это неудача.
- Разговор кончается, если пересборка не удаётся 10 мин, если за 10 мин три цепочки кончились
  отказом ответа клиента, или если после закрепления пришла другая карточка. Цепочка тогда
  закрывается, а ключи сессии, тела сообщений, которые ещё держит разговор, и записи, удержанные
  до закрепления, зануляются.
- О конце цепочки вызывающий узнаёт только класс: отказ ответа клиента, истёкшее ожидание ответа,
  неудавшаяся отправка или закрытие дальней стороной. Узлы не называются.

Правило параметров:

- Круговая задержка цепочки из h хопов, когда узлы отправляют по своим часам, не больше (2h - 1)
  периодов узла плюс сеть: на стенде 5 x 190 мс = 0,95 с для 3 хопов и 1,33 с для 4; в среднем
  2,5-2,8 периода, около 0,5 с.
- Окно должно покрывать максимум: W x rate > (2h - 1) x период узла. При W = 16 и rate 200 мс
  это 3,2 с.
- Ожидание ответа 10 с больше максимума в 7 раз. За это время в полёте меньше 256 заявок, а
  столько ответов вмещает очередь перед драйвером, поэтому ни один ответ не теряется до
  сопоставления.
- Глубина очереди mailbox 16 и окно ратчета 64 не меньше честного разрыва W + 16 = 32: отказанные
  записи в полёте плюс просроченные по TTL.
- Без часов узлов круг короче миллисекунды, и окно не наполняется.

| Параметр | По умолчанию |
|---|---|
| период заявок rate | задаёт вызывающий |
| окно W | 16 |
| keepalive без CoverPuts | 30 с |
| устаревание | 90 с |
| ожидание ответа | 10 с |
| пересборка | пауза 1 с, удвоение до 60 с, не дольше 10 мин |
| отказов ответа клиента | 3 за 10 мин |
| выходная очередь, записи до закрепления, полученные сообщения | 256, 16, 256 |

Что видит mailbox: с CoverPuts put на каждом тике, пока в полёте меньше W заявок с put; без них
момент и число настоящих сообщений, копии первой записи инициатора после kk2 и keepalive. Копии
залипшей записи это одинаковые байты, поэтому mailbox видит повтор. До закрепления заявки только
забирают, поэтому первый put показывает момент закрепления контакта: у инициатора сразу (kk1), у
ответчика с kk2 после прихода kk1.

### Клиент -peer

`cmd/client -peer` ведёт разговор с одним контактом через mailbox на выходе своих цепочек. Один
контакт, одна цепочка и одна очередь на процесс.

| Флаг | По умолчанию | Значение |
|---|---|---|
| -peer | выключен | режим разговора |
| -mailbox | нет | адрес mailbox, один из -nodes; выход каждой цепочки |
| -admin | 127.0.0.1:9201 | admin-порт, только IP-литерал loopback и порт |
| -cover-puts | включён | put в каждой заявке, фиктивная запись, когда сообщения нет |
| -respond | выключен | отвечать на каждое сообщение контакта его номером и текстом |
| -handshake-timeout | 60 с | сколько инициатор ждёт kk2 после того, как mailbox сохранил kk1 |
| -rate | 200 мс | период заявок |
| -interval, -count | 1 с, 1 | период и число своих сообщений; -interval 0 своих не шлёт, -count 0 без конца |
| -message | | текст своих сообщений, не больше 363 байт |

Отказ с кодом 2 до любого сетевого запроса и до создания личности: нет -mailbox или его нет в
-nodes; -hops меньше 2; -mode не fixed; -cover больше 0; -rate меньше 39,22 мс (за 10 с ожидания
ответа в полёте может быть не больше 255 заявок, на одну меньше буфера ответов в 256); -jitter не
меньше -rate; -admin не IP-литерал loopback; -message длиннее 363 байт; с -fixed-chain узел номер
-hops не mailbox; прочие ошибки флагов, списка узлов и якоря.

Порядок старта:

1. Политика памяти ключей и запрет дампов. При блокировке памяти (-keymem all, по умолчанию)
   RLIMIT_MEMLOCK должен быть не меньше 96 КиБ, иначе отказ с кодом 1 до любого ключа: на пике
   клиент держит около 19 заблокированных страниц (цепочка и канал около 9, личность и F 2,
   рукопожатие до 5, ратчет до 3). Поды клиентов получают IPC_LOCK.
2. Набор, проверка флагов, якорь.
3. Право забора F, 16 случайных байт сразу в secmem, не все нули, и личность: статический ключ
   согласования из GenerateEphemeral в secmem и карточка с адресом mailbox и очередью QueueID(F).
4. Ровно одна строка `card_hash=<64 hex>`, до любого сетевого запроса. Саму карточку журнал не
   получает: stdout уходит в журналы kubelet на диске узла, а держатель карточки может класть в
   очередь владельца и вытеснять put собеседника.
5. Первая цепочка до mailbox. Отказ: строка `refusing to build the circuit: <класс>` и код 1.
   Успех: строка `circuit of N hops among M listed nodes to the mailbox, request period R`.
6. Разговор, затем admin-слушатель и строка `admin listening on <адрес>`.

Карточка контакта, двоичная форма версии 1:

```
u8 версия = 1 | u8 набор | u8 длина адреса | адрес mailbox | очередь, 16
| статический ключ, 32 или 64
```

- Принимается только каноническое написание: разбор и сборка дают те же байты, хвоста нет.
  Набор равен набору провайдера, адрес проходит pki.ValidAddr, очередь не нули.
- С адресом стенда `relay-5.jimichi.svc.cluster.local:9000` карточка 89 байт на c25519 и 121 на
  ГОСТ. Текст `<набор>:<base64 с дополнением>`.
- card_hash это хэш транскрипта обмена e2e/card над карточкой, 32 байта, в журнале 64 hex.
  Короткого отпечатка нет.
- `jimichi keygen-card -suite S -mailbox ADDR` печатает карточку ключа, который сразу
  выбрасывается, `jimichi card-hash <текст>` печатает card_hash карточки.

Admin-порт (тело не больше 1 КиБ, заголовки за 5 с):

| Запрос | Ответ |
|---|---|
| GET /card | текст своей карточки и перевод строки |
| PUT /contact | закрепление карточки контакта, тело это её текст |

Порядок проверок PUT /contact:

1. Тело больше 1 КиБ: 413; не каноническая карточка: 400. Состояние не меняется ни до, ни после
   закрепления.
2. Контакт уже закреплён: та же карточка 204; любая другая разобранная карточка, в том числе
   чужого набора или с другим адресом, 409 и остановленное состояние.
3. Контакта нет: набор свой, адрес mailbox равен своему -mailbox, ключ и очередь не свои, ключ
   контакта принимает пробное согласование одноразовой пары (обмен e2e/check); иначе 400. Затем
   закрепление в памяти на процесс, строка `contact pinned card_hash=<хэш карточки контакта>
   role=initiator|responder` и 204.

Остановленное состояние:

- Ответ 409 уходит раньше, чем останавливается разговор. Затем закрываются разговор и цепочка,
  освобождаются ключи сессии, ключ личности и F, и пишется строка `contact card changed,
  refusing: pinned card_hash=<хэш закреплённой>` без байтов новой карточки.
- Процесс не завершается и на любой следующий запрос admin-порта отвечает 409, строка счётчиков
  несёт state=stopped.
- Выходит из него только перезапуск оператором (scripts/introduce.sh). Выход из процесса дал бы
  оркестратору перезапустить клиента с новой личностью и открыл бы новое окно доверия при
  первом использовании.

Свои сообщения:

- Тело на стенде: `u8 вид (1 сообщение, 2 ответ) | u32be номер | текст`.
- После закрепления клиент шлёт сообщение каждые -interval, не больше -count. После последнего
  он продолжает забирать и отвечать: выход унёс бы личность.
- На первый ответ с тем же номером строка `e2e round trip in <время>`, повторы номера не пишутся.
  С -respond на сообщение уходит ответ вида 2 с тем же номером и текстом. Ни текст, ни номер в
  журнал не попадают.

Журнал:

| Строка | Когда |
|---|---|
| `card_hash=<хэш>` | один раз при старте |
| `circuit of N hops among M listed nodes to the mailbox, request period R` | первая цепочка |
| `admin listening on <адрес>` | admin-порт открыт |
| `contact pinned card_hash=<хэш> role=<роль>` | контакт закреплён |
| `e2e round trip in <время>` | ответ на своё сообщение |
| `circuit closed`, `circuit closed: <класс>` | конец цепочки: закрыла дальняя сторона, отказ ответа, нет ответа 10 с, отправка не удалась |
| `circuit rebuilt through the same entry` | пересборка удалась |
| `the chain could not be dialled again, new middle hops drawn, redraw i of 2` | новые середины (раздел "Выбор цепочки") |
| `circuit rebuild failed: <класс>` | попытка пересборки не удалась |
| `e2e state=... requests= puts= ...` | раз в минуту: состояние (unpaired, handshaking, established, confirmed, stale, stopped) и счётчики разговора и сессии |
| `e2e peer not reachable for <время>, pinned card_hash=<хэш>` | раз в минуту, пока от контакта больше минуты не открылось ни одной записи: контакт с новой личностью требует нового знакомства |
| `contact card changed, refusing: pinned card_hash=<хэш>` | остановленное состояние |
| `conversation ended: <причина>` | конец разговора перед выходом |

Хэши карточек есть только в строках с card_hash. Ключей, карточек, F, текстов сообщений и
адресов узлов нет ни в одной строке.

Коды выхода: 0 по SIGTERM; 1, если пересборка не удалась 10 мин или иной сбой; 2, если флаги не
прошли проверку; 3, если за 10 мин три цепочки кончились отказом ответа. Смена карточки выхода
не даёт.

## Установка цепочки

Установка идёт одной служебной ячейкой того же размера 512 байт, без дополнительных обменов.

- Клиент знает адреса узлов и их онион-ключи из проверенных дескрипторов.
- Для каждого узла клиент генерирует эфемерную пару и согласует общий секрет с онион-ключом
  узла. Секрет привязан к транскрипту установки этого хопа: версия формата, номер узла в
  цепочке, идентификатор канала в этот узел, онион-ключ узла, эфемерный ключ клиента и, при
  аутентификации узлов, ключ личности узла из его сертификата (CRYPTO, раздел "Вывод ключей").
  Узел собирает тот же транскрипт из заголовка ячейки, своего онион-ключа, начала слоя и своего
  ключа личности, поэтому слой открывается только у узла, для которого он собран.
- Из общего секрета под тем же транскриптом выводятся два ключа, для служебной ячейки и для
  ячеек данных, и два смещения counter, а на узле ещё и метка повтора.
- Привязка не занимает ни байта в ячейке: служебная ячейка вмещает четыре узла на c25519 и три
  на ГОСТ.
- Служебная ячейка вложена так же, как ячейка данных: слой каждого узла содержит его эфемерный
  открытый ключ, адрес следующего узла, идентификатор следующего канала и слой для следующего узла.
- Номер узла в цепочке едет в поле counter служебной ячейки: узел должен знать свою позицию
  раньше, чем сможет определить длину своего слоя.
- Сняв свой слой, узел дополняет ячейку случайными байтами до 512 и пересылает дальше.
- Узел с ростером пересылает служебную ячейку только узлу ростера, по каналу,
  аутентифицированному ключом канала этого узла (раздел "Канальное шифрование"). Установка с
  другим адресом или с узлом, который не прошёл рукопожатие канала, на этом узле заканчивается,
  и канал, по которому она пришла, закрывается.
- Узел помнит метку каждой открытой служебной ячейки, пока держит онион-ключ, которым она
  открыта, и отбрасывает её копию, в том числе после закрытия исходной цепочки. Иначе копия
  заново создала бы ключ хопа, и счётчики пошли бы с нуля под тем же ключом. Метка выводится из
  общего секрета под отдельным purpose KDF. Копия, в которой эфемерный ключ записан иначе (ключ,
  сдвинутый на точку малого порядка, которых 8 у X25519 и 4 у ГОСТ, или запись X25519 с
  поднятым старшим битом), слой не открывает: байты ключа входят в транскрипт, и секрет
  получается другим. Метку получает только точная копия слоя.
- У каждого онион-ключа свой кэш меток, ограниченный -setup-cache. Заполненный кэш отказывает в
  новых установках под своим ключом, а не забывает метки, и только под этим ключом: отказ
  кончается, когда узел публикует следующий онион-ключ. Служебная ячейка на канале, который уже
  несёт цепочку, отбрасывается до согласования ключа и метку не занимает.
- Кэш защищает только потому, что метки и онион-ключ уходят вместе: освобождённый ключ уносит
  свои метки, перезапуск очищает и то, и другое. Поэтому онион-ключ живёт только в памяти
  процесса, и узел не пишет его ни в один файл. Блокировка памяти покрывает только его буфер
  secmem: копии, которые библиотеки оставляют на куче Go (CRYPTO, известные дыры), на хосте со
  swap могут быть выгружены на диск. Блокировка всей памяти процесса в плане
  ([#36](https://github.com/jimichi-org/jimichi/issues/36)). Ключ подписи узла только
  подписывает дескриптор с этим ключом и сам в согласовании слоёв не участвует.

Пустой адрес следующего узла означает, что это выходной узел. Следующего канала у выхода нет, и
поле его идентификатора в слое выхода несёт counter первой прямой ячейки, поэтому служебная
ячейка не растёт.

Эпохи онион-ключа:

- С -onion-rotate (1 ч по умолчанию и на стенде) узел открывает слои установки отдельным
  онион-ключом, не ключом канала, и меняет его каждый период: генерирует новую пару в буфере
  secmem, увеличивает эпоху на единицу и сразу подписывает дескриптор с новым ключом, не
  дожидаясь таймера подписи. Ключ канала остаётся прежним на всё время жизни процесса.
- Заменённый ключ узел держит льготный период после ротации: срок дескриптора плюс допуск часов
  (-descriptor-ttl + Skew, 22 мин на стенде). К этому моменту истёк каждый дескриптор, который
  его называет, в том числе для проверяющего, чьи часы отстают на допуск, и в зеркале узла,
  который не смог скачать новый. Затем ключ освобождается, его буфер зануляется, а метки
  забываются. Если не считать копий, оставленных библиотеками на куче (LIMITATIONS; CRYPTO,
  известные дыры), служебная ячейка, записанная под этот ключ, больше не открывается ничем, что
  держит узел.
- Узел держит не больше двух онион-ключей, и ротация ждёт, пока заменённый ключ не освобождён.
  Поэтому время между ротациями равно -onion-rotate или льготному периоду, если он длиннее:
  1 ч на стенде, 1 ч 2 мин при сроке дескриптора по умолчанию, 1 ч. -onion-rotate не может быть
  короче -descriptor-ttl.
- Пока ключей два, узел пробует оба на каждой установке, в одном порядке и до конца: два
  согласования и две попытки открыть слой, каким бы ключом ни пользовался клиент, поэтому время
  установки не показывает эпоху. Слой открывает не больше одного ключа, и метка идёт в кэш этого
  ключа.
- Ни один ключ не освобождается, пока им открывается установка: освобождение её ждёт.
- Узел смотрит на часы раз в секунду и отсчитывает момент ротации и момент освобождения дважды:
  по настенным часам и по времени работы хоста (монотонным часам). Он действует, как только
  любые из них показывают, что момент настал. Время работы стоит, пока хост спит, поэтому после
  сна первый же взгляд на часы освобождает ключ, чей льготный период кончился по настенным
  часам, и затем делает одну ротацию. Настенные часы, переведённые назад, не откладывают ни
  один из моментов: его приносит время работы. Настенные часы, переведённые вперёд, приближают
  оба, и это стоит клиентам отклонённой установки, но не секретности. Дескриптор всегда
  подписывается для ключа, который в этот момент текущий.
- published дескриптора внутри процесса не уменьшается: Identity.Refresh берёт published =
  max(now, прежний published, пол), а expires = min(published + ttl, not_after). При верных часах
  это ничего не меняет. После перевода настенных часов назад собственный /descriptors узла ждёт,
  пока часы не дойдут до published, как и сегодня, самое позднее до published ротации.
- Первый дескриптор эпохи опубликован не раньше чем через Skew после expires последнего дескриптора
  эпохи перед заменяемой: удавшаяся ротация к e+2 ставит пол published в expires(e) + Skew. При
  верных часах освобождение ключа e приходит по настенным часам через ttl + Skew после ротации к
  e+1, пол ниже now, и ничего не меняется; пол работает, когда освобождение пришло по времени
  работы или часы переведены назад (раздел "Согласованность дескрипторов").
- Неудавшаяся ротация, когда нет памяти под новый ключ, его страницу не удалось
  заблокировать или не прошла проверка его пары (CRYPTO), оставляет опубликованный ключ на
  месте. Узел пробует снова каждую секунду и считает попытки (onion_rotate_failed). Между
  ротациями он держит четыре страницы под ключи, когда хватает памяти, и отдаёт их прямо перед
  созданием следующего ключа, чтобы ключу и проверке его пары нашлось место, когда
  заблокированная память исчерпана. Он берёт их после каждой ротации, а если тогда места не
  нашлось, то снова после освобождения заменённого ключа.
- Уже построенная цепочка ротации не замечает: её ключи ячеек получены при установке и живут до
  разрыва цепочки.
- -onion-rotate 0 это база измерений: слои установки открывает тоже ключ канала, всё время
  жизни процесса, под эпохой 0, а узел при старте печатает одну строку WARNING. Так запускает
  свои узлы обвязка lab.
- Без аутентификации узлов у дескриптора нет срока. После ротации узел отдаёт неподписанный
  комплект с новым ключом и эпохой, остальные узлы скачивают его заново в течение минуты, а
  заменённый ключ держится тот же льготный период.

Разрыв цепочки:

- Цепочка привязана к каналу, по которому пришла её служебная ячейка. Ячейка с тем же
  идентификатором из другого канала отбрасывается, повторная служебная ячейка с занятым
  идентификатором тоже.
- Закрытие канала в любом звене закрывает соседние каналы этой цепочки в обе стороны, разрыв
  доходит до клиента и до выходного узла.
- Узел закрывает цепочку сам, если ячейка пришла не по порядку, назад пришла ячейка другого вида
  или такая, которую он не может обернуть, ячейке не нашлось места в очереди, ячейку не удалось
  записать в канал к одному из соседей или выход не смог зашифровать ответ. Закрытие идёт тем же
  путём, что и закрытие канала, и учитывается в счётчике закрытых цепочек.
- Канал, который к сроку установки после рукопожатия не открыл цепочку, закрывается.
- Кадр, который не удалось записать за срок записи, это такая же неудавшаяся запись: сосед
  перестал читать, и узел, отправляющий по своим часам, иначе ждал бы его. Она учитывается и в
  закрытых цепочках, и в истёкших сроках.
- Цепочка, по которой ни в одну сторону не прошло ни одной ячейки за время простоя, или
  достигшая предельного срока жизни, разрывается закрытием входящего канала и учитывается в
  истёкших цепочках, а не в закрытых. Заполнение канала трафиком не считается.
- Ключи цепочки освобождаются после остановки всех горутин, которые ими пользуются.
- Клиент видит разрыв как закрытие канала ответов и завершается. Оркестратор поднимает его
  заново, и он выбирает новую цепочку. Какая бы сторона ни оборвала канал, клиент закрывает своё
  соединение, и после того как конец цепочки записан, ни одна ячейка не запечатывается: Send в
  обоих режимах возвращает client.ErrCircuitClosed и не ставит сообщение в очередь, расписание
  постоянной скорости останавливается. Отправка, которая уже запечатывала свою ячейку,
  доводит её до конца и получает ошибку на закрытом канале. После собственного Close
  вызывающего Send возвращает свою ошибку закрытия.
- Когда клиент сам закрыл цепочку из-за ответа или кадра, он завершается с кодом 3 и строкой
  `circuit closed: client: reply refused: <проверка>`, где проверка одна из пяти: `bad header`,
  `did not open`, `out of turn`, `more replies than cells written` и `link: frame did not open`
  для кадра на канале от входа, который не открылся под ключами канала, был ли в нём ответ или
  заполнение. Такой кадр может сделать любой, кто стоит на проводе между клиентом и входом, поэтому
  он не указывает на вход и не должен засчитываться против него. Эта строка не называет ни узла,
  ни номера ячейки. Любой другой разрыв даёт код 1 и строку `circuit closed` либо `send:` с
  причиной. Код 1 не значит, что путь был честным: копия, пропуск или перестановка, сделанные
  узлом дальше входа, закрывают цепочку на предыдущем узле, если тот уже принял обратную ячейку,
  испорченный кадр к входу или между узлами закрывает этот канал, а узел может просто закрыть
  соединение. До первой обратной ячейки узлу сравнивать не с чем: каждый узел на
  обратном пути берёт первый обратный counter как пришло, поэтому, когда узел дальше входа
  пропускает первые ответы, более поздний ответ проходит все узлы, и отклоняет его только клиент,
  как `out of turn`, с кодом 3.

## Ограничения узла

Каждое ограничение в таблице ниже, кроме постоянных 5 с на следующий узел, это параметр узла со
значением по умолчанию. Отрицательное значение выключает ограничение, чтобы его цену можно было
измерить отдельно, с двумя исключениями: размер пачки не может быть отрицательным, такой запуск
отклоняется (ограничение выключает частота), а ограничение рукопожатий с одного адреса остаётся
включённым, равным 4, когда общий предел выключен, если только само не задано как -1.

| Ограничение | По умолчанию | Зачем |
|---|---|---|
| срок рукопожатия, -handshake-timeout | 2 с | инициатор шлёт своё приветствие сразу, поэтому молчащий сосед держит место недолго |
| соединение и рукопожатие со следующим узлом | 5 с, постоянный | молчащий следующий узел не держит ни установку, ни остановку узла |
| срок установки, -setup-timeout | 10 с | клиент и предыдущий узел шлют служебную ячейку сразу после рукопожатия |
| срок записи, -write-timeout | 4 периода, не меньше 1 с; 5 с без отправки по своим часам | сосед, переставший читать, не останавливает отправителя |
| простой цепочки, -idle-timeout | 5 мин | брошенная цепочка перестаёт слать заполнение; клиент стенда шлёт каждые 200 мс |
| срок жизни цепочки, -circuit-lifetime | 24 ч | ограничивает время жизни одного набора ключей цепочки |
| одновременные рукопожатия, -max-handshakes | 32 | больше только встали бы в очередь к процессору |
| одновременные рукопожатия с одного адреса, -max-handshakes-per-source | восьмая часть -max-handshakes, не меньше 1, то есть 4; тоже 4, когда -max-handshakes выключен | один адрес не занимает все места рукопожатий |
| открытые входящие каналы, -max-links | 512 | память их цепочек остаётся в пределах пода на 128 МиБ |
| каналы с одного адреса, -max-links-per-source | 32 | один сосед не занимает все места; предыдущий relay это один адрес для всех цепочек, которые он пересылает. Клиент держит одну цепочку, по цепочке на контакт в плане ([#96](https://github.com/jimichi-org/jimichi/issues/96)) |
| новые каналы с одного адреса, -source-link-rate, -source-link-burst | 10 в секунду, пачками до 50 | каждый канал стоит пары ключей и согласования |
| установки с одного адреса, -source-setup-rate, -source-setup-burst | 0,2 в секунду, пачками до 10 | каждая установка стоит согласования с каждым онион-ключом, который держит узел, соединения дальше и метки на время жизни её ключа |

- Соединение принимается или отклоняется при приёме, до любого согласования ключей.
  Служебная ячейка проверяется после рукопожатия канала и до согласования с онион-ключами.
  Отклонённое соединение закрывается без ответа.
- Заполненный кэш меток (-setup-cache) отказывает в установках только под тем онион-ключом,
  которому принадлежит. С ротацией отказ кончается, когда опубликован следующий ключ, не позже
  чем через время между ротациями (-onion-rotate или льготный период, если он длиннее), если
  ротация удалась; без ротации он кончается перезапуском.
- Каждое соединение, принятое или отклонённое, стоит своему адресу жетон частоты каналов, а
  ограничения одного адреса проверяются раньше общих: повторы против заполненного узла тратят
  собственный запас адреса и оставляют общие места другим.
- Входом может быть любой узел, поэтому каждый узел стенда держит ограничения на один адрес со
  значениями по умолчанию. Узел, который пересылает для многих клиентов, для следующего узла
  один адрес, и цепочки, которые он пересылает, делят там запас одного адреса (LIMITATIONS).
  Сетевая политика (deploy/base/network.yaml) пускает к порту ячеек каждого relay поды клиентов
  и поды relay и никакие другие; информационный порт открыт для пространства имён.
- Один адрес это адрес IPv4 или префикс IPv6 длиной /64. Таблица адресов живёт только в памяти,
  держит не больше 16384 адресов и забывает адрес, как только у него нет открытых каналов и его
  корзины снова полны. Новый адрес сверх предела отклоняется и учитывается вместе с отказами по
  одному адресу, известные адреса обслуживаются дальше.
- Каждая служебная ячейка тратит жетон установки до того, как её открыть, поэтому адрес, чьи
  каналы закрылись, остаётся в таблице, пока его корзина установок не наполнится: до 50 с при
  частоте и пачке по умолчанию.
- Отказы и истёкшие сроки добавляются в агрегированные счётчики, без адресов и идентификаторов.
- Временная ошибка приёма, например исчерпание файловых дескрипторов, повторяется с паузой от
  5 мс, удваиваясь до 1 с. Если приём прекратился насовсем, узел завершается с ошибкой и
  оркестратор поднимает его заново; проверка готовности проходит, только пока узел принимает
  соединения.

## Аутентификация узлов

Клиент берёт ключи узла только из комплекта, проверенного по якорю доверия, и узел берёт ключ
канала следующего узла только из такого комплекта. Пакет pki реализует цепочку доверия от ключа
УЦ до ключей узла, выдачу сертификатов и их проверку; им пользуются cmd/relay, cmd/client и
cmd/jimichi. Проверку комплектов зеркала клиентом и комплекта соседа узлом ведёт поверх pki пакет
internal/verify, общий для cmd/client и cmd/relay. Ключ УЦ только подписывает сертификаты и в
согласовании слоёв не участвует.

### Цепочка доверия

| Звено | Что связывает | Чем подписано |
|---|---|---|
| Якорь доверия | открытый ключ УЦ в виде строки `<набор>:<base64>`; ca_id это первые 8 байт Hash(ключ) | ничем, приходит к клиенту как конфигурация (ConfigMap jimichi-ca) |
| Сертификат узла | набор, серийный номер, ca_id, срок, имя, адрес, ключ подписи узла | ключом УЦ |
| Дескриптор узла | хэш сертификата, ключ канала, онион-ключ, эпоха, срок | ключом подписи узла |
| Запрос сертификата | nonce, выбранный УЦ, имя, адрес, ключ подписи узла | ключом подписи узла |

- Адрес в сертификате это ровно тот host:port, по которому клиент соединяется с узлом или который
  пишет в адрес следующего узла.
- Онион-ключ идёт в установку цепочки, ключ канала в канал, который ведёт к узлу: от клиента ко
  входу, от узла к следующему узлу. С -onion-rotate онион-ключ это отдельная пара, которая
  меняется по эпохам, а ключ канала остаётся (раздел "Установка цепочки", эпохи онион-ключа).
  С -onion-rotate 0 узел публикует в обоих полях один ключ согласования.
- Ключ подписи узла, который заверяет сертификат, это личность узла: он входит в транскрипт
  установки этого узла и в транскрипт каждого аутентифицированного канала к нему, у обеих
  сторон (CRYPTO, раздел "Транскрипт"). Узел с -auth привязывает его с самого старта; до
  сертификата он не отдаёт дескриптора и никуда не продлевает цепочки.
- Запрос нужен только при выдаче и клиенту не показывается. Он доказывает владение ключом подписи,
  а nonce, выбранный УЦ, доказывает свежесть. Request.Check принимает запрос, только если nonce
  совпадает, а имя и адрес совпадают с ростером оператора.
- Identity.Install устанавливает сертификат, только если совпадают ключ подписи, набор, имя, адрес
  и срок. Подпись УЦ узел не проверяет: якоря у него нет. Поэтому тот, кто выдаёт сертификат,
  обязан после установки проверить комплект узла по якорю так же, как pki.Verify проверяет его для
  клиента; jimichi enroll так и делает.
- Ключ УЦ и ключ подписи узла генерируются через CryptoProvider прямо в буферы secmem. Close их
  освобождает, вызывающий код откладывает его через defer.

### Форматы

Форматы двоичные: целые big-endian, поля переменной длины с префиксом длины в один байт и жёстким
максимумом, время в секундах unix (int64). Подпись идёт последним полем. Подписывается строка
домена, за которой следует тело без подписи; в самом объекте строка домена не передаётся.

| Объект | Тело | Строка домена |
|---|---|---|
| Сертификат v1 | версия 1, набор, serial 16, ca_id 8, not_before, not_after, имя, адрес, ключ подписи | `jimichi/cert/v1\x00` |
| Дескриптор v1 | версия 1, набор, эпоха u32, published, expires, cert_hash 32, ключ канала, онион-ключ | `jimichi/descriptor/v1\x00` |
| Запрос v1 | версия 1, набор, nonce 16, имя, адрес, ключ подписи | `jimichi/csr/v1\x00` |

- Имя: от 1 до 32 символов из `a-z`, `0-9` и `-`.
- Адрес: от 1 до 64 байт (размер поля адреса в служебной ячейке), только печатный ASCII
  0x21..0x7e, разбирается как host:port с непустым хостом; порт десятичный, без знака и ведущих
  нулей, от 1 до 65535. wire отбрасывает нули в конце адреса, поэтому адрес с нулём, пробелом или
  байтом вне ASCII мог бы назвать один узел, а привести к другому. У хоста и порта по одной записи
  (имя в нижнем регистре без точки в конце, IP-адрес в канонической форме, адрес IPv4 только как
  IPv4, а не как ::ffff:a.b.c.d), потому что Verify сравнивает адреса байт в байт. Хост это
  IP-адрес без зоны или метки DNS из a-z, 0-9 и дефиса через точку, ни одна метка не пуста и не
  начинается и не кончается дефисом, последняя метка не состоит из одних цифр и не начинается с 0x
  (некоторые резолверы читают такое имя как адрес): в адресе нет ничего, что URL прочёл бы как
  путь, запрос, данные пользователя или другой порт.
- Ключи и подписи не длиннее 128 байт. cert_hash это Hash всего сертификата вместе с подписью.
- Разбор отвергает неизвестную версию (ErrVersion), неизвестный набор (ErrSuite), поле длиннее
  максимума, лишние байты в конце и любой вход, который не собирается обратно в себя же
  (ErrFormat). У каждого объекта одна каноническая запись. Набор, отличный от набора провайдера,
  отвергается сразу после разбора (ErrSuite).
- Комплект узла (bundle) для клиента: JSON
  `{"v":1,"suite":"c25519","cert":"<base64>","descriptor":"<base64>"}`. Разбор принимает только
  ту запись, которую пишет Bundle.Marshal: ключи в нижнем регистре и в этом порядке, без пробелов,
  повторов, пропусков и лишних данных, base64 в канонической записи. Набор и дескриптор не пустые.
- Комплект без подписи (pki.Unsigned) отдаёт узел, запущенный с -auth=false: пустой сертификат,
  нулевой cert_hash, пустая подпись. Пустой сертификат допустим только в нём, Verify такой
  комплект отвергает (ErrFormat).
- Ростер, который узел получает после сертификата: JSON
  `{"anchor":"<набор>:<base64>","nodes":[{"name":"<имя>","addr":"<host:port>"},...]}`. Разбор
  принимает только ту запись, которую пишет Roster.Marshal, не длиннее 4 КиБ (pki.MaxRoster);
  имена и адреса корректны, а имена и хосты адресов попарно различны (ErrFormat, ErrDuplicate).
  Узел скачивает каждого соседа с хоста его адреса на одном для всех -peer-info-port, поэтому
  второй адрес на том же хосте вёл бы к узлу первого, а на хосте самого узла к его собственному
  информационному порту. Хосты сравниваются в их единственной записи, и у адреса IPv4 нет записи
  IPv6, но один хост под двумя именами или под именем и IP-адресом не обнаруживается.
- Зеркало дескрипторов: JSON `[{"addr":"<host:port>","bundle":{...}},...]`, записи отсортированы
  строго по адресу, каждый комплект в своей канонической записи; разбор принимает только её.
  Элемент несёт либо `bundle`, либо `proof`: `{"addr":...,"proof":[lo,hi]}` это доказательство
  несогласованности узла, два его комплекта, первый побайтно меньше второго (раздел
  "Согласованность дескрипторов"). Разбор отвергает элемент с обоими ключами или без обоих,
  доказательство не из двух элементов, элемент, не проходящий разбор комплекта, равные или
  переставленные элементы, беспорядок адресов и любой вход, который не собирается обратно байт в
  байт (ErrFormat), а повтор адреса даёт ErrDuplicate. Зеркало без доказательств кодируется ровно
  как раньше. Своей подписи у зеркала нет: каждый комплект в нём проверяется как любой другой, а
  доказательство каждый читатель проверяет по своему якорю, поэтому вход не может его подделать.
- Предел ростера ограничивает число узлов: в 4 КиБ помещается 58 узлов с именами и адресами
  вида стенда (relay-N, relay-N.jimichi.svc.cluster.local:9000) на c25519 и 57 на ГОСТ. Зеркало
  пяти узлов занимает около 3 КиБ на c25519 и 3,6 КиБ на ГОСТ, зеркало наибольшего ростера
  около 35 и 41 КиБ, при 256 КиБ, которые принимает клиент.

Сроки:

- Допуск часов Skew = 2 мин применяется только к нижним границам (not_before, published), поэтому
  ни одно окно не продлевается за свой конец.
- Сертификат, у которого not_after не позже not_before, отвергается (ErrCertTime), как и при
  выдаче.
- Дескриптор истекает не позже сертификата (expires <= not_after) и живёт не больше 24 ч.
- Identity.Refresh подписывает новый дескриптор с published = max(now, прежний published, пол) и
  expires = min(published + ttl, not_after) (раздел "Установка цепочки", эпохи онион-ключа). Без
  сертификата он возвращает ErrNoCert, после not_after снимает комплект.
- Политика проверки (pki.Policy) может задавать нижнюю границу срока MinLife: дескриптор, который
  живёт меньше, отвергается (ErrDescLife), если только его не обрезал сертификат (expires ==
  not_after). Узел и клиент с -consistency ставят MinLife = pki.MinDescriptorLife, 16 мин, столько
  же, сколько наименьший -descriptor-ttl, поэтому честный узел границы не нарушает.

### Порядок проверки

pki.Verify проверяет комплект узла по якорю, по адресу, с которым идёт соединение, и по текущему
времени. Первая же ошибка прерывает проверку; у каждой проверки после разбора свой код:

1. набор якоря, разбор комплекта, его версия и набор (ErrFormat, ErrVersion, ErrSuite): набор
   сверяется раньше, чем любой ключ разбирается как точка кривой;
2. разбор сертификата (ErrFormat, ErrVersion, ErrSuite);
3. ca_id (ErrUnknownCA) и подпись УЦ (ErrCertSignature);
4. срок сертификата (ErrCertTime);
5. адрес сертификата байт в байт равен адресу соединения (ErrWrongAddr);
6. разбор дескриптора и cert_hash (ErrFormat, ErrVersion, ErrSuite, ErrCertMismatch);
7. подпись ключом подписи узла (ErrDescSignature);
8. срок дескриптора, expires <= not_after, срок жизни не больше 24 ч (ErrDescTime);
9. длина ключа канала и онион-ключа равна длине ключа согласования набора (ErrKeySize).

- Клиент и узел для дескриптора соседа вызывают pki.Verify для каждого комплекта отдельно.
- pki.VerifyStatement проверяет то же без часов: якорь, обе подписи, cert_hash, адрес, набор,
  not_after > not_before, expires > published, expires <= not_after, срок не больше MaxLife и не
  меньше MinLife, если не обрезан, длины ключей. Окна сертификата и дескриптора против now не
  проверяются, поэтому и истёкшая пара остаётся доказательством. Verify и VerifyStatement это одна
  функция с флагом проверок по часам, и порядок ошибок Verify прежний.
- pki.Compare применяет правила согласованности C0..C6 к двум заявлениям одного адреса (раздел
  "Согласованность дескрипторов"): 0, когда они согласованы, иначе первое нарушенное правило в
  порядке личность, хэш сертификата, ключ канала, затем в одной эпохе онион-ключ, в разных эпохах
  равный онион-ключ, затем, если lo меньшая эпоха, published(hi) < published(lo) и, при разнице
  эпох не меньше 2, published(hi) < expires(lo) + Skew. Compare симметрична, Skew в ней это
  константа pki.Skew. Тексты семи правил: `two identities at one address`, `two certificates for
  one identity`, `two link keys`, `two onion keys in one epoch`, `one onion key in two epochs`,
  `an older epoch published after a newer one`, `epochs two apart overlap`.
- pki.VerifyConflict проверяет оба комплекта доказательства VerifyStatement по адресу узла и
  возвращает несогласованность, которую находит Compare: ErrNoConflict
  (`pki: not a proof of inconsistency`), когда её нет, иначе ошибку pki первого комплекта, который
  не прошёл. Эту проверку делает каждый читатель доказательства. Узел с отказом виден как
  ErrConflict (`pki: the node signed descriptors that contradict each other`) с текстом правила.
- pki.VerifyChain проверяет так каждый узел ростера при enroll и требует, чтобы адреса, ключи
  подписи и онион-ключи узлов попарно различались (ErrDuplicate): оператор видит оба имени и
  может исправить ростер.
- pki.Unverified читает один комплект, проверяя только формат, набор и длину ключей, без
  подписей, сроков и адресов, и личности не даёт. Это конфигурация без аутентификации узлов, она
  оставлена, чтобы вклад меры можно было измерить; ни один блок экспериментов такого измерения
  не делает.
- Request.Check при выдаче сверяет набор (ErrSuite), nonce (ErrNonce), имя и адрес с ростером
  (ErrRoster) и подпись запроса (ErrRequestSignature).

### Проверка на клиенте

- До любого запроса по сети: с -auth (по умолчанию) пустой -ca фатален, набор якоря должен
  совпадать с -suite.
- Клиент запрашивает /descriptors у своего входа, узла, выбранного первым (с -fixed-chain это
  первый узел из -nodes), и ни у какого другого узла: таймаут 5 с на запрос, предел 256 КиБ, до
  30 попыток с паузой 1 с, повтор только при ошибке соединения или ответе 503; разбор строгий.
  При неудачном запросе клиент завершается с
  `refusing to build the circuit: the entry: <вид причины>`, а с -fixed-chain с
  `refusing to build the circuit: node <адрес>: <ошибка>`.
- pki.Verify проверяет комплект каждого узла списка, который отдал вход, отдельно, в порядке
  списка, войдёт узел в цепочку или нет. Комплект, который не прошёл проверку, считается
  отсутствующим. Если в ответе нет комплекта самого входа, клиент завершается с
  `refusing to build the circuit: the entry: the entry holds no bundle for it`, если комплект
  входа не прошёл проверку, с `refusing to build the circuit: the entry: <вид причины>`, если
  отсутствующих и не прошедших проверку узлов списка больше, чем допускает -missing, с
  `refusing to build the circuit:` и далее
  `too many listed nodes left out by the entry or not passing the check: <k> of <N> listed nodes, at most <m> may be`,
  а с -fixed-chain, если комплекта узла цепочки нет или он не прошёл проверку, с
  `refusing to build the circuit: node <адрес>: <причина>`.
  Запасного пути к непроверенным ключам нет, а при случайной цепочке список бывает частичным
  только в пределах -missing (раздел "Ростер, дескрипторы соседей и зеркало"). После успеха в
  журнал идёт по строке на проверенный узел: имя, отпечаток ключа подписи и срок сертификата, с
  -fixed-chain ещё и срок дескриптора (при случайной цепочке его в журнале нет: собственный
  дескриптор входа самый свежий в его зеркале и указал бы на вход), и одна строка с числом
  проверенных узлов и узлов списка.
- Элемент зеркала может быть доказательством несогласованности узла (раздел "Согласованность
  дескрипторов"). С -consistency (по умолчанию) клиент проверяет его сам по своему -ca
  (pki.VerifyConflict) и отказывает узлу: тот не входит в цепочку и считается отдельно от
  -missing: узлов списка становится на один меньше, а отсутствующие и не прошедшие проверку
  считаются против -missing среди оставшихся (client.JudgeMirrorAmong); в выбор узел с отказом не
  попадает никогда. Доказательство, которое не содержит противоречия или не проверяется, это узел,
  которого вход не отдал, в пределах -missing. Доказательство о самом входе означает отказ от
  цепочки, как и отсутствие его комплекта; доказательство о mailbox у клиента -peer даёт прежний
  отказ `the entry holds no bundle for the mailbox`. Строка о проверенных узлах при отказе
  становится `<n> of <N> listed nodes verified, <k> refused by proof`, без адресов; с -fixed-chain
  узел цепочки, получивший отказ, останавливает клиента с `refusing to build the circuit: node
  <адрес>: pki: the node signed descriptors that contradict each other: <правило>`. С
  -consistency=false элемент-доказательство это узел, которого вход не отдал, в пределах -missing,
  а нижней границы срока дескриптора нет.
- Клиент -peer ведёт себя иначе: строк по узлам списка в журнале нет, отказы пишутся только
  видом причины, а сбой при пересборке клиент не останавливает (раздел "Выбор цепочки").
- Онион-ключ из дескриптора идёт в установку цепочки, ключ канала входного узла в link.Dial, а
  ключ личности из сертификата каждого узла в оба транскрипта этого узла.
  client.Dial отвергает узел с пустым ключом или ключом не того размера: пустой ключ канала
  сделал бы канал до входа анонимным.
- С -auth=false клиент так же берёт комплекты у входа, читает их через pki.Unverified и пишет
  одну строку WARNING. Непроверенные ключи каждого хопа при этом приходят только от входа: их
  выбирает тот, кто отвечает за вход. Узел с -auth=false отдаёт комплект без подписи
  (pki.Unsigned). Личности нет ни у одной стороны, и транскрипты идут без неё; клиент с
  -auth=false и узел с -auth не согласуют ни одного ключа (CRYPTO, раздел "Транскрипт"). Это
  конфигурация без меры; ни один блок экспериментов не сравнивает её с конфигурацией с
  аутентификацией.

### Выдача сертификатов

Сертификаты выдаёт `jimichi enroll` (cmd/jimichi) вне кластера: на машине оператора или на
раннере CI. scripts/enroll.sh запускает его для всех relay стенда, которые находит по метке их
Deployment (app=relay).

1. Оператор передаёт ростер: для каждого узла имя и адрес для сертификата, два локальных адреса,
   через которые достижимы служебный порт и порт дескриптора узла, и хэш ключа подписи узла.
   Узел печатает этот хэш один раз при старте, до того как начнёт обслуживать порты
   (identity_hash=). scripts/enroll.sh читает его из журнала текущего контейнера pod через kube API
   (kubectl logs) и требует ровно одну такую строку. Имена, адреса, локальные адреса и хэши должны
   быть корректны и попарно различны, как и хосты адресов: ростер, который называет хост дважды,
   узел не принимает.
2. Процесс задаёт политику secmem (-keymem, -harden). Если блокировка памяти запрошена, но не
   работает, выдача не начинается.
3. Каждому узлу уходит POST /csr со свежим nonce 16 байт, узел отвечает запросом, подписанным
   ключом подписи. Request.Check сверяет nonce, имя и адрес с ростером, хэш ключа из запроса
   должен совпасть с хэшем из журнала, ключи подписи узлов должны попарно различаться. Узел,
   который уже принял сертификат, действующий или истёкший, отвечает на POST /csr 409, и enroll
   печатает команду его перезапуска.
4. Только когда прошли все запросы и ростер прогона укладывается в 4 КиБ, которые принимает
   узел (pki.MaxRoster), создаётся ключ УЦ в буфере secmem. УЦ выдаёт все сертификаты, и его
   ключ сразу освобождается (Close): он живёт только на время выпуска.
5. Каждый сертификат уходит на свой узел через PUT /cert. Узел принимает сертификат, только
   если ещё не принимал ни одного, в течение 60 с после POST /csr (pki.InstallWindow), один раз
   на запрос и только с not_before не раньше времени запроса минус Skew; иначе он отвечает 409 с
   классом ошибки. Затем он устанавливает сертификат, подписывает дескриптор и отвечает 204, при
   отказе установки 400. Повторная отправка установленного сертификата, пока он действует,
   получает 204, поэтому повтор после потерянного ответа проходит.
6. enroll читает /descriptor каждого узла и проверяет всю цепочку pki.VerifyChain по новому
   якорю, то есть ровно так, как клиент.
7. enroll отправляет каждому узлу ростер через PUT /roster: якорь, имя и адрес каждого узла этого
   прогона, всем одни и те же байты (раздел "Ростер, дескрипторы соседей и зеркало").
8. Только когда ростер приняли все узлы, якорь печатается в stdout. При любой ошибке stdout пуст,
   код выхода 1.

- Сертификат устанавливается один раз на процесс узла: установленный сертификат не заменяется, даже
  истёкший, повторная выдача требует перезапуска узла, а с ним новой личности. Install не проверяет
  подпись УЦ, поэтому без этого правила любой, кто достаёт до служебного порта, заменил бы рабочий
  сертификат своим.
- Установка на узлы не атомарна. Если выдача упала после первого PUT /cert, узлы, которые уже
  приняли сертификат, держат его под выброшенным УЦ до перезапуска, и клиенты их отвергают.
  enroll перечисляет в stderr такие узлы, а также узлы, чей ответ потерян или был 5xx (may hold),
  и печатает команду `kubectl rollout restart` для них; enroll.sh печатает ту же подсказку. Сбой
  ростера на каком-то узле сообщается так же: перечислены узлы, которые держат или могут держать
  ростер выброшенного УЦ, и команда их перезапуска. После перезапуска выдачу запускают снова.
- -timeout у enroll не больше 60 с, поэтому весь прогон укладывается в окно, в течение которого
  узел ждёт свой сертификат.
- Запрос, сертификат и ростер идут через `kubectl port-forward` к конкретному pod на служебный
  порт узла 127.0.0.1:9101, тот же, что для счётчиков. kube API пускает к pod и к его журналу по
  kubeconfig оператора и правам pods/portforward и pods/log. Port-forward приводит к любому
  процессу, который слушает loopback pod, поэтому запрос привязан к узлу хэшем ключа из журнала
  контейнера: запрос под другим ключом отвергается, и ни один сертификат не выпускается. С -auth
  узел не стартует, если адрес -stats не loopback IP. Тела запросов на этот порт ограничены
  4 КиБ.
- Якорь попадает в ConfigMap jimichi-ca (ключ anchor), оттуда в переменную JIMICHI_CA и флаг
  клиента -ca. После новой выдачи enroll.sh перезапускает клиента.
- На хосте Windows нет mlock и prctl: enroll.sh передаёт `-keymem zero -harden=false`, и enroll
  предупреждает, что ключ УЦ на время выпуска остаётся в незаблокированной памяти. Путь с
  блокировкой работает в Linux: WSL2 и CI.
- `jimichi keygen-ca` печатает якорь ключа, который тут же выбрасывается. Им e2e проверяет, что
  клиент с чужим якорем отказывается строить цепочку.

### Ростер, дескрипторы соседей и зеркало

- Узел принимает один ростер на процесс: только после сертификата, в течение 60 с после его
  установки (pki.InstallWindow) и только на служебном порту. Ростер, в котором нет собственных
  имени и адреса узла, отклоняется (400), как и ростер, по якорю которого не проверяется
  собственный комплект узла (pki.Verify по своему адресу): ростер называет якорь того УЦ,
  который сертифицировал узел. Список узлов в ростере не аутентифицирован; он только сужает
  множество узлов, сертифицированных этим УЦ, потому что сосед считается только с дескриптором,
  проверенным по этому якорю. Ростер до сертификата, после окна, после другого ростера или пока
  узел не отдаёт действующий дескриптор получает 409. Те же байты повторно получают 204,
  поэтому повтор после потерянного ответа проходит.
- По ростеру узел держит дескрипторы соседей: он скачивает /descriptor с информационного порта
  каждого другого узла ростера (хост из адреса в ростере, порт из -peer-info-port, по умолчанию
  9100) с таймаутом 5 с, пределом 16 КиБ на тело и 4 КиБ на строку состояния и заголовки, без
  перенаправлений и со строгим разбором и проверяет комплект pki.Verify по якорю ростера и
  адресу из ростера. Кэш содержит открытые данные и живёт только в памяти.
- Узел скачивает запись заново, когда её возраст по настенным часам достигает половины срока её
  дескриптора: с этого момента запись пора обновить. Таймер спит до ближайшего такого момента,
  не дольше 1 мин и не меньше 5 с. За проход узел спрашивает каждого соседа, которого нет в кэше
  или запись которого пора обновить, кроме соседа на паузе после истечения его сертификата
  (ниже), и никого больше, по очереди, каждого одним запросом с таймаутом 5 с, и пока такой сосед
  остаётся, следующий проход начинается через 5 с после конца этого. Запись пора обновить до тех
  пор, пока узел не скачает дескриптор, подписанный позже, поэтому с паузой 5 с между проходами
  узел продолжает спрашивать и соседа, который не отвечает, и соседа, чей комплект не проходит
  проверку, и соседа, который всё ещё отдаёт дескриптор, не подписанный заново. Последнее обычно:
  оно начинается в середине срока дескриптора и кончается первым проходом после того, как сосед
  подписывает дескриптор заново. Таймер соседа делает это в пределах одного своего периода,
  min(ttl/4, 1 мин), если настенные часы двух узлов совпадают, а ротация его онион-ключа сразу,
  смотря что раньше (раздел "Жизнь ключей и отзыв"). Дескриптор, expires которого обрезан по
  not_after сертификата, обновлять не пора до его истечения: сосед не подпишет дескриптор, который
  кончается позже, а заменённый онион-ключ он держит, пока не истекут все дескрипторы, которые его
  называют, поэтому запись служит до конца. После истечения сертификата сосед отвечает 503; если не
  удаётся скачивание у соседа, чья запись кончилась вместе с сертификатом, его спрашивают снова
  через 1 мин вместо паузы 5 с, и так, пока скачивание не удаётся: узел принимает один сертификат
  на процесс, а enroll выбрасывает ключ УЦ, поэтому нового комплекта этого соседа, который проходит
  проверку по якорю ростера, не ожидается. Запись заканчивается в момент expires её дескриптора.
  Комплект, который не удалось скачать или проверить, не принимается, а прежняя запись остаётся до
  своего истечения. В журнал идёт одна строка на вид причины: нет ответа, код состояния или
  непройденная проверка, без единого байта, присланного соседом. Ни запрос, ни установка цепочки
  скачивания не вызывают.
- Цепочка продолжается только по этому кэшу: следующий адрес должен быть узлом ростера с
  действующей записью, и канал до него аутентифицируется ключом канала из этой записи. Узел с
  -auth не продолжает ни одной цепочки, пока не получил ростер.
- GET /descriptors на информационном порту это зеркало: собственный комплект узла и комплекты
  соседей по ростеру из кэша. Оно кодируется при установке ростера, при обновлении кэша и когда
  узел подписывает свой дескриптор. Запрос копирует готовые байты; только первый запрос после
  того, как комплект вышел из зеркала или может в него войти, кодирует его заново. Ответ 503,
  пока у узла нет ростера или нет собственного действующего дескриптора, а также пока его
  собственный комплект не может войти в зеркало (ниже).
- Клиент проверяет комплекты по своим часам и читает их, когда зеркало уже получено, после
  всех повторов, поэтому комплект входит в зеркало, только пока его считают действующим в
  момент получения часы, которые расходятся с часами узла в пределах допуска: с более позднего
  из моментов published дескриптора и not_before сертификата по часам узла и до момента за
  2 мин 6 с до его expires, на какой бы срок сосед его ни подписал. Запас складывается из
  Skew, 2 мин, 5 с, которые может занять запрос, и 1 с, потому что узел сравнивает целые
  секунды. Сосед, комплекта которого у узла нет или чей комплект вне этого окна, в зеркало не
  входит и считается одним из узлов, которые допускает -missing клиента; запись в кэше и
  продолжение цепочек к этому соседу действуют по-прежнему до expires. Скачанный комплект,
  который в зеркало ещё не входит, не вытесняет тот, что в нём есть, и соседа спрашивают снова
  после паузы в 5 с.
- Собственный комплект узла начинается так же: сертификат может начинаться на величину до
  Skew позже часов узла, и пока эти часы не дошли до более позднего из published и not_before,
  /descriptors отвечает 503. /descriptor отдаёт комплект сразу после подписи: сосед включает
  его в своё зеркало только с этого начала, а enroll проверяет его по часам, которые задали
  not_before.
- -descriptor-ttl не меньше 16 мин и не больше 24 ч, поэтому сосед, который переподписывает
  вовремя, остаётся в зеркале, пока его часы расходятся с часами узла не больше чем на Skew:
  следующий дескриптор подписан раньше, чем возраст прежнего достигнет ttl/2 + 1 мин, и взят
  первым проходом после подписи, как только по часам узла наступил его published (кроме случая,
  когда прежний дескриптор обрезан по not_after: его узел держит до истечения и более поздним не
  заменяет), а прежний остаётся в зеркале, пока его возраст не достигнет ttl - 2 мин 6 с. Если часы
  соседа отстают до 2 мин, на паузу в 5 с и один проход по соседям остаётся ttl/2 - 1 мин - Skew -
  2 мин 6 с: 2 мин 54 с при наименьшем сроке и 4 мин 54 с при 20 мин стенда. Дескриптор, срок
  которого обрезан по not_after сертификата, выходит из зеркал соседей за 2 мин 6 с до not_after;
  сам узел отдаёт свой дескриптор и своё зеркало и принимает цепочки до not_after.
- Клиент (-missing, по умолчанию 1, не больше числа узлов списка сверх -hops) принимает зеркало,
  в котором есть проверенный комплект самого входа и проверенные комплекты всех узлов списка,
  кроме не более чем этого числа, проверяет каждый комплект отдельно и выбирает остальные хопы
  среди узлов, комплекты которых прошли проверку. Комплект, который в зеркале есть, но проверку
  не прошёл, считается отсутствующим. Фиксированной цепочке нужны проверенные комплекты её
  собственных узлов.
- Комплект в кэше может называть онион-ключ, который его узел уже заменил. Узел держит этот
  ключ, пока комплект не истёк (раздел "Установка цепочки", эпохи онион-ключа), поэтому клиент,
  взявший комплект из зеркала, всё равно строит цепочку.
- Благодаря зеркалу клиент обращается только ко входу. Входу при этом клиент не доверяет ничего:
  каждый комплект он проверяет по своему якорю, поэтому вход может не отдать комплекты, а
  изменённый комплект равен неотданному.
- Узел с -auth=false ростер не принимает. В /descriptors он указывает себя под адресом -advertise
  вместе с неподписанными комплектами узлов из -peers, прочитанными без проверки, и продолжает
  цепочки на любой адрес. Хосты -advertise и -peers попарно различны, как в ростере. Эти
  комплекты узел держит такими же проходами: у неподписанного комплекта нет сроков, поэтому
  запись пора обновить через минуту после прохода, который её взял. Соседа, которого нет в кэше,
  который не отвечает или отдаёт некорректный комплект или комплект другого набора, спрашивают
  снова после той же паузы 5 с, а прежняя запись остаётся, потому что эти записи не истекают:
  ушедший сосед остаётся в зеркале со своим последним комплектом. Без -advertise узел отвечает
  на /descriptors 503 и называет оба флага.
- scripts/e2e.sh проверяет, что клиент обращается только к своему входу. Он ждёт, пока два
  прохода подряд покажут каждый relay со всеми соседями по ростеру и с неизменным
  descriptor_requests, и запускает клиентов. Между двумя чтениями счётчиков mirror_requests
  должен вырасти у одного relay на каждый запуск клиента, сначала client-a и client-b (их
  пересборка идёт через тот же вход и ничего не добавляет, а у relay-5, их mailbox, не растёт
  вовсе), затем клиента с чужим якорем, и ни у какого другого; descriptor_requests каждого relay
  должен остаться таким, каким был до клиентов.

### Согласованность дескрипторов

Узел публикует свои дескрипторы сам, каталога нет, и без проверки он мог бы отдать каждому соседу
свой действующий подписанный онион-ключ: ключ, открывший служебную ячейку, назвал бы ему зеркало,
которым пользовался клиент, то есть вход. Поэтому с -consistency (по умолчанию) узлы проверяют
дескрипторы друг друга на согласованность: каждый читает зеркала других узлов ростера, сравнивает
все заявления каждого узла между собой и отказывает узлу, два дескриптора которого нарушают
правило. Пара таких дескрипторов это доказательство, которое проверяет каждый, у кого есть якорь.

| Термин | Значение |
|---|---|
| узел | одна личность под одним якорем по одному адресу ростера: сертификат связывает личность с именем и адресом, процесс принимает один сертификат, а перезапуск это новая личность и новая выдача для всех |
| заявление узла | комплект, сертификат которого проверяется по якорю по этому адресу и дескриптор которого подписан этой личностью, каким бы ни было его окно времени: окно говорит, когда клиент может им пользоваться, подпись говорит, что узел это сказал |
| несогласованность | два заявления одного адреса под одним якорем, которые нарушают правило; доказательство самодостаточно: любой с якорем проверяет обе подписи и читает два дескриптора |

Правила. a и b это два заявления одного адреса под одним якорем с полями identity, cert_hash, epoch,
published, expires, link, onion. Правила симметричны; C7 относится к одному заявлению. Skew это
pki.Skew, 2 мин, константа протокола.

| Правило | Утверждение | Почему честный узел его не нарушает |
|---|---|---|
| C0 одна личность | a.identity == b.identity | одна личность на процесс; вторая личность по тому же адресу требует второго сертификата от УЦ, ключ которого enroll выбрасывает; перезапуск даёт и новый якорь |
| C1 один сертификат | a.cert_hash == b.cert_hash | узел отклоняет второй сертификат на процесс; enroll выдаёт один на адрес за прогон |
| C2 один ключ канала | a.link == b.link | ключ канала задаётся один раз на процесс и входит в каждую подпись тем же; часы не участвуют |
| C3 один онион-ключ на эпоху | a.epoch == b.epoch влечёт a.onion == b.onion | ротация делает один ключ на эпоху, каждая подпись читает текущую пару (эпоха, ключ) кольца, неудавшаяся ротация не меняет ни того, ни другого; с -onion-rotate 0 эпоха 0 называет статический ключ всё время процесса; часы не участвуют |
| C4 одна эпоха на онион-ключ | a.onion == b.onion влечёт a.epoch == b.epoch | ротация отказывается от открытого ключа, равного текущему, а каждый ключ приходит свежим из GenerateEphemeral (совпадение двух ключей случайно: 2^-256); ни одна граница от этого правила не зависит |
| C5 эпохи опубликованы по порядку | a.epoch < b.epoch влечёт a.published <= b.published | эпоха только растёт, и подпись большей эпохи идёт в реальном времени позже любой подписи меньшей. Равенство допустимо: таймер может подписать e в ту же секунду, в которую ротация подписывает e+1. Настенные часы, переведённые назад между двумя подписями, уменьшили бы поле; это исключает зажим 1 |
| C6 эпоха кончается за Skew до начала эпохи через одну | a.epoch + 2 <= b.epoch влечёт b.published >= a.expires + Skew | ротация к e+2 ждёт освобождения ключа e, через льготный период ttl + Skew после ротации R1 к e+1. Последний дескриптор e подписан не позже R1, поэтому expires(e) <= R1 + ttl, а когда освобождение приходит по настенным часам, на ротации к e+2 они показывают не меньше R1 + ttl + Skew >= expires(e) + Skew. Когда оно приходит по времени работы или настенные часы переведены назад после R1, зажим 2 ставит published(e+2) не ниже expires(e) + Skew. Равенство допустимо |
| C7 срок не меньше 16 мин, если его не обрезал сертификат | expires - published >= 16 мин или expires == not_after | -descriptor-ttl не меньше 16 мин (pki.MinDescriptorLife); Refresh подписывает expires = min(published + ttl, not_after); с зажимом 1 срок считается от published и остаётся равным ttl |

Почему этого достаточно. C3 и C4 делают онион-ключ функцией эпохи. По C5 и C6 любые одни часы с
допуском Skew (дескриптор принят, когда published <= t + Skew и expires > t) принимают в момент t
не больше двух соседних эпох узла: будь приняты e и e+k при k >= 2, published(e+k) >= expires(e) +
Skew > t + Skew. Поэтому у любого проверяющего в любой момент не больше двух ключей одного узла.
C7 ограничивает, как часто появляется новая эпоха: published(e+2) >= expires(e) + Skew >=
published(e) + 16 мин + Skew, то есть не больше двух новых эпох за 16 мин; заодно узел не может
заставить соседей скачивать его каждую минуту короткими дескрипторами. Без C6 узел подписал бы e,
e+1, e+2, e+3 в одну секунду и отдал каждому из четырёх зеркал свою эпоху, и ключ, открывший
установку, назвал бы зеркало прямо. Без зазора Skew в C6 проверяющий с допуском принимал бы e и
e+1, кончающиеся в T, вместе с e+2 и e+3, начинающимися в T, на протяжении Skew до T: четыре ключа,
два бита на цепочку у каждой границы. Без C5 узел подписывал бы e+1 одному соседу и свежий e другому
без конца, и оба оставались бы действующими. Без C7 он шагал бы эпохами так часто, как позволяет
запас зеркала, и так же часто открывал окно. Правила "эпоха e+1 опубликована не раньше чем через
16 мин после e" нет: оно верно только против первого дескриптора e, а проверяющий пары не знает,
какой дескриптор e был первым; на стенде (ttl 20 мин, ротация 1 ч) последняя переподпись e идёт за
10 мин до ротации, и такое правило отказало бы каждому честному узлу.

Два зажима на узле, бездействующие при верных часах. Честные нарушения C5 и C6 возможны только при
настенных часах, переведённых назад, поэтому published вычисляется с двумя зажимами:

| Зажим | Где | Действие |
|---|---|---|
| 1. published не уменьшается внутри процесса: published = max(now, прежний published, пол), expires = min(published + ttl, not_after) | Identity.Refresh | C5 держится при переводе часов назад на любую величину. Соседи с верными часами принимают комплект: published это реальный прошедший момент |
| 2. пол на ротации: после удавшейся ротации и перед публикацией нового дескриптора пол ставится в expires последнего дескриптора заменяемой эпохи плюс Skew, затем запоминается expires дескриптора, который сейчас в обслуживании | rotateIfDue | C6 держится при переводе часов назад. При верных часах освобождение по настенным часам даёт now >= R1 + ttl + Skew >= expires заменяемой эпохи + Skew, пол ниже now, и ничего не меняется. Моменты освобождения ключа и ротации не трогаются |

Expires заменяемой эпохи запоминается только в той попытке, чья ротация удалась: ротация, которая не
удаётся и повторяется каждую секунду, не двигает ни его, ни пол. Иначе удавшаяся попытка поставила
бы published(e+1) в expires(e) + Skew, до ttl впереди часов узла, и соседи, отставшие больше чем на
Skew, отказали бы живому комплекту (ErrDescTime). Дескриптор в обслуживании на ротации это последний
подписанный, он называет текущую эпоху или более старую, когда каждая подпись после прошлой ротации
не удалась; пол тогда ограничивает каждую старую эпоху, как требует C6, потому что дескриптора
пропущенной эпохи не существует.

Что стоит перевод часов назад и что из этого добавляют зажимы. После перевода на s собственный
/descriptors узла отвечает 503, пока его часы не дойдут до последнего published, а таймер
переподписи, который считает возраст от published, срабатывает на s позже; и то и другое происходит
и без зажима 1, потому что дескриптор, подписанный до перевода, уже несёт этот published. Зажим 1
добавляет только одно: ротация, которая приходит по времени работы при отставших настенных часах,
подписывает published = max(прежний published, пол), а не настенное время, поэтому 503 длится, пока
часы не дойдут до этого значения, а не до ротации. Соседи выводят узел из своих зеркал, когда s
превышает около ttl/2 минус запас зеркала минус период таймера (6 мин 54 с на стенде, 4 мин 54 с при
ttl 16 мин), с expires минус запас зеркала удержанного комплекта до поздней переподписи; тем
временем они спрашивают его каждые 5 с и ничему не отказывают. /descriptor отвечает всё это время.

Кого спросить, выбирает узел, поэтому сам запрос ничего о записях не говорит. Соседей, получивших
отказ, не спрашивают. Ни один запрос, пришедший узлу, скачивания не вызывает. Обновление записей
идёт перед проходом, по очереди и с таймаутом 5 с на соседа, поэтому сосед, которого пора обновить
и который молчит, задерживает проход на 5 с.

Запись заявлений. По каждому соседу X кэш держит, кроме прежней записи (комплект, relay.Peer, from,
due, expires, final), запись заявлений (internal/verify Record) и, после отказа, саму
несогласованность:

| Состояние | Содержимое | Граница |
|---|---|---|
| запись заявлений | личность и хэш сертификата первого заявления; ключ канала и его первый комплект; на каждую виденную эпоху онион-ключ и до трёх комплектов: с наименьшим published, с наибольшим published и с наибольшим expires | эпоха забывается, когда прошло её наибольшее expires + Skew + 8 x -consistency-every: дескриптор, истёкший для любых часов, ничего не открывает, а 8 проходов дают доказательству против него дойти до каждого узла при 58 узлах. Предел MaxEpochs = 8 это защита памяти: девятая эпоха сначала сравнивается, затем выбрасывается наименьшая эпоха, кроме эпохи удержанной записи. При правиле допуска и периоде по умолчанию одновременно держатся не больше четырёх попарно согласованных эпох (у e+4 published >= expires(e+2) + Skew >= expires(e) + 16 мин + Skew, выше now + Skew, пока e не забыта), поэтому предел достигается только при периоде больше примерно 5 мин. Не больше 25 комплектов, около 15 КиБ на соседа на c25519; у честного соседа 1 или 2 эпохи |
| отказ | pki.Conflict: правило и каноническое доказательство | один на соседа, до конца процесса: личность под этим якорем не сменить без перезапуска всего |

Заявления попадают в запись из трёх мест: из прямого скачивания /descriptor узла X, из элемента X в
любом зеркале, прочитанном за проход (в том числе в зеркале самого X), и из обоих комплектов
доказательства об X. Каждое заявление проходит pki.VerifyStatement по якорю ростера и адресу X из
ростера; что не прошло, даёт класс в журнале и больше ничего.

Правило допуска: комплект из зеркала или из прямого скачивания входит в запись, только когда его
published <= now + Skew по часам читателя, то есть нижняя граница, которую pki.Verify применяет к
живым комплектам; комплект, опубликованный дальше вперёд, пишется в журнал под прежним классом
`descriptor outside its validity` и не записывается. Без этого узел мог бы скормить каждому читателю
восемь попарно согласованных заявлений будущих эпох, вытеснить живую эпоху из записи и затем отдать
два ключа живой эпохи разным читателям недоказанно. Оба комплекта доказательства, которое принял
VerifyConflict, входят безусловно: несогласованность уже найдена; комплекты доказательства, в
котором противоречия нет, это два обычных комплекта под тем же правилом. Record.Take сравнивает
допущенное заявление с каждым удержанным комплектом (не больше 25 сравнений) и возвращает первое
противоречие.

Выбор записи и принятие:

- Запись о X это самое новое живое заявление: новее значит больше по паре (эпоха, published)
  лексикографически, живое значит проходит pki.Verify сейчас. Заявление не новее удержанного не
  берётся, ни из прямого скачивания, ни из зеркала; соседа по-прежнему пора обновить, и его
  спрашивают снова после паузы, ровно как сегодня скачанный заново неизменённый комплект.
- Более новое заявление вытесняет удержанное по прежнему правилу зеркала: не пока удержанное в
  зеркале, а новое в него войти ещё не может (его published впереди часов этого узла). due и
  expires берутся из нового, поэтому прямое скачивание X приходит позже, никогда раньше:
  descriptor_requests из-за принятия не растёт.
- Узел принимает заявление и в пустую запись: сосед без записи (никогда не отвечал или его
  скачивание не удалось) получает живое, годное для зеркала заявление, которое несёт зеркало.
  Прямое скачивание всё равно идёт, пока соседа нет или его пора обновить, поэтому старт на стенде,
  где каждый сосед отвечает, не меняется.
- Принимать безопасно: комплект подписан самим X и проверен здесь; ключ канала тот же по C2, поэтому
  relay.Peer для X не меняется; заменённый онион-ключ X держит льготный период, поэтому клиент,
  взявший старый комплект, всё равно строит цепочку.
- Принятие и укорачивает законную разницу между честными зеркалами. Сегодня зеркало, скачавшее e
  перед самой ротацией X, держит e, пока его не пора обновить, через ttl/2, а если X затем не
  отвечает, до expires минус запас зеркала: до 17 мин 54 с на стенде. С принятием разница длится не
  дольше W после того, как первое честное зеркало показало новую эпоху.

Окно W = -consistency-every + Skew + k x таймаут скачивания + 1 с, считая с первой секунды, в
которую любое честное зеркало показывает новое заявление, плюс один таймаут скачивания на каждого
соседа, которого пора обновить и который молчит на прямом запросе перед проходом. На стенде 60 + 120
+ 4 x 5 + 1 = 201 с при честных соседях, 206 с при одном молчащем. Skew в W это отставание часов
принимающего узла от часов подписавшего, которое допускает pki.Verify: заявление входит в зеркало,
когда часы принимающего дойдут до его published, поэтому при большем отставании окно растёт на
разницу (тест cmd/relay с часами, расходящимися на 238 с, считает границу попарно). До того как
первое честное зеркало покажет новую эпоху, все честные зеркала согласны на старой: ни один сосед
не скачивает узел раньше, чем его запись пора обновить, через половину срока после published,
поэтому новая эпоха может идти до первого зеркала минуты, и это не окно.

Что происходит при обнаружении:

| Действие | Где | Подробности |
|---|---|---|
| X выходит из кэша | peerCache.refuse | запись удалена, отказ записан; ожидание пропускает соседей с отказом, иначе пустая запись возвращала бы паузу 5 с без конца |
| к X не продлевают | relay.Config.Peers не возвращает X | relay считает RefusedExtend и отказывает без соединения, как адресу вне ростера; пакет relay не меняется |
| X выходит из зеркала, доказательство входит | publish | элемент становится `{"addr":...,"proof":[lo,hi]}`; зеркало кодируется заново сразу; until считается только по комплектам |
| X больше не скачивают | обновление записей и выбор пропускают соседей с отказом | ничего, что отдаёт X, взято не будет |
| одна строка журнала | `peer <адрес ростера>: refused: <текст правила>` | один из семи фиксированных текстов; ни байта, присланного X |
| счётчики | peers_refused (текущее число), peer_mirror_requests (отвеченных GET /descriptors/peer) | в /stats и в строке счётчиков; peers соседа с отказом не считает |
| как долго | до конца процесса | личность под этим якорем не сменить без перезапуска всего |

Узел, прочитавший доказательство в зеркале соседа, сам проверяет оба комплекта (pki.VerifyConflict)
и кладёт их в запись X; противоречие выходит из записи так же, как если бы узел скачал оба, поэтому
он публикует доказательство, которое проверил, а не скопировал. Элемент-доказательство, комплекты
которого не противоречат друг другу или не проверяются, пишется в журнал один раз как
`peer <адрес>: mirror: not a proof of inconsistency` и считается тем, что это зеркало X не отдаёт;
два комплекта, которые проверяются, всё равно идут в запись по правилу допуска. Элемент о
собственном адресе читателя игнорируется.

Клиент проверяет улику сам: две подписи по якорю и сравнение двух разобранных дескрипторов. Второго
зеркала он не скачивает и состояния между процессами не держит; клиент -peer не держит записи и
между пересборками: честный вход с включённой проверкой отказал бы X раньше, чем клиент увидел через
него два заявления X, а вход без проверки это смешанное развёртывание, для которого есть
переключатель.

Цена. Комплект около 600 байт на c25519 и 720 на ГОСТ; зеркало 5 узлов около 3 КиБ, 58 узлов около
35 КиБ (41 КиБ на ГОСТ).

|---|---|---|---|---|
| 5 | 5 x 4 = 20 | 60 КиБ / 72 КиБ | 4 запроса, 12 КиБ | 5 x 4 = 20 запросов за 10 мин при ttl 20 мин |

| Флаг | Где | По умолчанию | Значение |
|---|---|---|---|
| -consistency | cmd/relay | true | читать зеркала соседей ростера, вести запись заявлений каждого соседа, отказывать соседу, дескрипторы которого противоречат друг другу, нести доказательство в /descriptors, применять pki.MinDescriptorLife к дескрипторам соседей. С -auth=false одна строка `WARNING: -consistency needs -auth, the check is off`, и проверка выключена |
| -consistency-every | cmd/relay | 1m | период прохода, от 30 с до 1 ч (нижняя граница выше k x таймаут = 20 с, поэтому проход не длиннее периода); с -consistency=false отклоняется, только если задан явно |
| -consistency | cmd/client | true | проверять доказательства в зеркале входа, отказывать названным в них узлам, считая их отдельно от -missing; применять pki.MinDescriptorLife. false: элемент-доказательство это узел, которого вход не отдал, в пределах -missing; нижней границы срока нет |

Строка старта узла несёт consistency=<значение>. Базовая линия (узлы с -consistency=false): нет
проходов, записей и доказательств, зеркала как раньше, узел с двумя ключами остаётся соседом везде;
/descriptors/peer всё равно отвечает. Манифесты стенда (deploy/base/relay.yaml) задают
-consistency=true явно, как -onion-rotate. Обвязка lab ничего не меняет: -auth=false, ростеров нет.

Что остаётся узлу, нарушающему правила, собрано в LIMITATIONS: не больше двух онион-ключей, принятых
одним проверяющим в один момент, и трёх у клиентов с расходящимися часами около границы эпох; окно
двух ключей не дольше W и не чаще двух раз за 16 мин, на стенде не больше 402 с из каждых 960 с;
по биту о входе на каждую цепочку, установленную внутри окна, и эти биты mailbox может собирать по
пересборкам одного клиента -peer; узел с отказом уменьшает список каждого клиента на один.

scripts/e2e.sh (пункт о зеркале выше) различает трафик соседей и клиентов по пути: клиенты скачивают
GET /descriptors (mirror_requests), узлы GET /descriptors/peer (peer_mirror_requests), а
descriptor_requests принятие не трогает (прямое скачивание оно может только отложить), поэтому обе
прежние проверки сохраняют смысл. Сверх них после цикла ожидания скрипт читает peer_mirror_requests
и требует peers_refused равным 0 у каждого relay (иначе `a relay refuses a roster peer before the
clients started`), а при последнем чтении счётчиков требует, чтобы peer_mirror_requests вырос у
каждого relay (иначе `the consistency check made no request at <relays>`) и peers_refused остался
0, и печатает `consistency: every relay cross-read its peers, none refused`. Отрицательный случай,
узел с двумя ключами на стенде kind, не шаг e2e: ему нужен relay, который подписывает два ключа, а
такой живёт в тестах Go, не в двоичном файле стенда.

### Жизнь ключей и отзыв

| Ключ | Где создаётся | Где хранится | Сколько живёт |
|---|---|---|---|
| Ключ УЦ | `jimichi enroll`, pki.NewCA, после проверки всех запросов | secmem процесса enroll | только выпуск сертификатов; Close освобождает его на любом пути выхода |
| Якорь | тот же процесс | stdout, ConfigMap, окружение клиента | до следующей выдачи, открытые данные |
| Ключ подписи узла | cmd/relay при старте, до открытия портов | secmem; узел, которому велено блокировать память, без блокировки не стартует | до конца процесса |
| Ключ канала | cmd/relay при старте, GenerateEphemeral | secmem | до конца процесса; с -onion-rotate 0 он же онион-ключ |
| Онион-ключ | cmd/relay при старте и при каждой ротации, GenerateEphemeral | secmem; при включённой блокировке памяти незаблокированный ключ не принимается | с -onion-rotate один период как опубликованный ключ и льготный период после него, на стенде 1 ч 22 мин; при неудавшейся ротации опубликованный ключ остаётся до первой удавшейся; освобождается в конце льготного периода и при завершении процесса |
| Сертификат, дескриптор | УЦ, узел | куча узла, открытые данные; комплект хранится уже закодированным | сертификат до not_after или перезапуска узла; дескриптор 1 ч по умолчанию (-descriptor-ttl), 20 мин на стенде |
| Ростер, дескрипторы соседей | enroll, остальные узлы | куча узла, открытые данные | ростер до перезапуска узла; дескриптор соседа до его expires; запись заявлений соседа и отказ ему по доказательству несогласованности до перезапуска узла |

- Перезапуск узла даёт новый ключ подписи, без сертификата и без ростера. Узел готов (readiness
  по /healthz), но /descriptor и /descriptors отвечают 503, цепочек он не продолжает, и клиенты
  отказываются строить через него цепочку, пока не выполнен scripts/enroll.sh. make deploy, make
  start и scripts/e2e.sh вызывают его сами.
- Новая выдача требует свежих процессов узлов. scripts/redeploy.sh сам перезапускает узлы, make
  start после make stop поднимает их заново, а повторный make deploy, make start без make stop или
  scripts/e2e.sh на уже сертифицированных узлах останавливается с подсказкой перезапуска.
  Сертификаты прежнего УЦ умирают, когда узлы перезапускаются с новыми личностями, а клиенты с новым
  якорем: отзыв забыванием. Другого отзыва нет.
- Сосед, получивший отказ по доказательству несогласованности (раздел "Согласованность
  дескрипторов"), остаётся с отказом до конца процесса: сменить личность под этим якорем он может
  только перезапуском, а перезапуск одного узла требует новой выдачи для всех. Снимается отказ тем
  же забыванием.
- Срок сертификата задаёт -cert-ttl: 72 ч на стенде, 1 ч в CI.
- Дескриптор подписывается при установке сертификата, при каждой ротации онион-ключа и в
  остальное время только по таймеру; запрос /descriptor отдаёт готовый комплект и подписи не
  вызывает. Таймер срабатывает раз в
  min(ttl/4, 1 мин), где ttl это -descriptor-ttl, и подписывает заново, когда возраст
  дескриптора по настенным часам достигает половины ttl или меняется состояние сертификата.
  Настенные часы нужны потому, что таймер идёт по монотонным, а они стоят, пока хост спит.
- После expires дескриптора или not_after сертификата узел отвечает 503. Узел с истёкшим
  сертификатом возвращается в строй только перезапуском и новой выдачей.

### Компрометация УЦ

Ключ УЦ в согласовании ключей не участвует. Тот, у кого он есть, то есть оператор или укравший
ключ за время выпуска, может сертифицировать свою личность на любые имя и адрес и, заняв позицию
в сети, подменить узел. Ключей слоёв прошедших цепочек это не даёт: они выведены из ключей
согласования узлов, которых УЦ не видит.

## Что снимается при измерениях

| Источник | Данные |

## Контейнер клиента

Статус: пакеты vault и vault/profile и команды `jimichi vault init` и `jimichi vault show`
реализованы. Клиент -peer с контейнером (-vault) и измерение свойства (EXPERIMENT, блок 5) в
плане ([#20](https://github.com/jimichi-org/jimichi/issues/20)).

Контейнер это файл клиента постоянного размера с одним или двумя томами, каждый под своим
паролем. Записанный том хранит закрепление, то есть карточку контакта, и больше ничего. В файле
нет ключевого материала ни в каком виде, даже зашифрованного: ключ личности и право забора F
выводятся из ключа тома при каждом открытии (CRYPTO, "Контейнер"). При этом файл и пароль тома
воспроизводят ключ личности и F, поэтому против изъятия файла вместе с паролем стойкость та же,
что у ключа, хранимого под паролем. Истории сообщений в томе нет
([#159](https://github.com/jimichi-org/jimichi/issues/159)).

### Формат

```
файл       = соль[32] | область 0 [4096] | область 1 [4096]             ровно 8224 байта
область    = r[32] | Seal(K_b, nonce 0, открытый текст[4048], ad = th_b) [4048 + тег 16]
открытый   = u16be L | содержимое[L] | нули                              L от 0 до 4046
содержимое = u8 версия = 1 | карточка контакта[L-1]                      не больше 339 байт
```

| Смещение | Байты | Поле |
|---|---|---|
| 0 | 32 | соль |
| 32 | 4096 | область 0 |
| 4128 | 4096 | область 1 |
| область + 0 | 32 | r |
| область + 32 | 4048 | шифротекст |
| область + 4080 | 16 | тег |
| открытый текст + 0 | 2 | L |
| открытый текст + 2 | L | содержимое: версия 1, затем каноническая карточка контакта |
| открытый текст + 2 + L | 4046 - L | нули |

- Заголовка, версии формата, набора, цены растяжения и nonce в файле нет. Формат задаётся
  размером: файл другого размера это ErrNotVault, а другой набор неотличим от неверного пароля.
- Область без тома это пустой том: L = 0 под ключом из 32 байт crypto/rand, запечатанный тем же
  кодом; ключ сразу выбрасывается. Место тома случайно: том i ложится в область b xor i, где b
  случайный бит.
- Каждая запечатка берёт свежее r из crypto/rand, а ключ области K_b выводится из ключа тома и
  r, поэтому каждый K_b служит одной Seal, и нулевой nonce безопасен. nonce не хранится, поэтому
  области в обоих наборах устроены одинаково: размер и вид файла набор не выдают.
- Содержимое vault хранит как непрозрачные байты, раскладку знает vault/profile. Своей карточки
  в томе нет: её строят из выведенного открытого ключа, QueueID(F) и адреса mailbox карточки
  контакта.
- Другой формат (история, другая цена растяжения, другой вывод личности) это другой размер файла.

### Ключи

```
W           = PasswordKey(пароль, NewContext(p, "vault/password", соль))
k_s         = DeriveKey(W, "vault/volume", NewContext(p, "vault/volume", соль, [s]), 32)   s = 0, 1
K_b         = DeriveKey(k_s, "vault/block", NewContext(p, "vault/block", [s], r), 32)
ctx_id      = NewContext(p, "vault/identity", соль, [s])
(priv, pub) = DerivePair(k_s, ctx_id)                                        ключ личности
F           = DeriveKey(k_s, "vault/fetch", ctx_id, 16)                      право забора
```

- Соль одна на файл и общая для двух томов: Open растягивает пароль один раз, а ключи двух
  областей разводит номер области s.
- Номер области и соль входят в ключ тома, r в ключ области и в связанные данные: перестановка
  областей, другая соль или любой изменённый байт области дают отказ открытия.
- Личность выводится из ключа тома той области, которая открылась, и только после успешного
  открытия; ключ тома освобождается сразу после вывода пары и F.
- Вывод личности принадлежит формату файла v1: другой вывод это новый формат и другой размер
  файла, иначе прежние контейнеры при открытии дали бы другие личности.
- Следствия: другой пароль или новый контейнер дают новую личность, копия файла сохраняет её.
  Смена пароля это смена личности, а закрепление у собеседника постоянно, поэтому новое
  знакомство требует нового контейнера с обеих сторон.

### Операции

| Операция | Что делает |
|---|---|
| `Prepare(p, тома...)` | один или два тома, у каждого пароль и Fill. Равные пароли: ErrSamePassword. Соль из crypto/rand и случайное место тома. Для каждого тома один PasswordKey, ключ тома и сразу личность; Fill получает личность и пишет содержимое прямо в буфер secmem длины MaxContent = 4046 (больше: ErrTooLarge; хвост после длины зануляется). Fill тома, кроме первого, вернул 0: ErrEmpty. Тома, кроме первого, и пустой том запечатываются и открываются обратно, их ключи и буферы освобождаются. Draft держит соль, запечатанные области, ключ первого тома, его личность и его буфер; файла ещё нет |
| `Draft.Identity()` | личность первого тома до записи: из неё строится своя карточка |
| `Draft.Write(path, fill)` | fill (может быть nil) правит содержимое первого тома; ошибка fill оставляет том без содержимого; L = 0: ErrEmpty, файла нет. Файл по пути: ErrExists до того, как на диск попал хоть один байт. Seal первого тома со свежим r, единственная запись (ниже), перечитывание: байты те же, первая область открывается. Write, который не создал ссылку на файл (ErrExists, ошибка записи или ссылки), оставляет Draft годным для новой попытки. С первой попытки, дошедшей до диска, байты файла закреплены: каждая следующая попытка пишет те же байты, а fill тогда должен дать то же содержимое, иначе он отвергается и Draft остаётся как был. После удачной ссылки ключ и буфер первого тома освобождаются, а следующий Write даёт ErrWritten; ошибка после ссылки (удаление имени tmp, fsync каталога, перечитывание) это ErrWritten с причиной |
| `Draft.Close()` | освобождает всё, что не взято через Take |
| `Create(p, path, тома...)` | Prepare и Write(path, nil) |
| `Open(p, path, пароль)` | размер не 8224: ErrNotVault. Файл читается целиком, один PasswordKey, k_0 и k_1. Открытие пробуется в обеих областях всегда, в одном порядке, каждая попытка в свой буфер secmem. Из ключа открывшейся области выводится личность. Open ничего не пишет и не удаляет |
| `Volume.Content()`, `Volume.Identity()`, `Volume.Close()` | содержимое и личность открытого тома; Close освобождает то, что не взято через Take |
| `Identity` | Public: открытый ключ; Agree: согласование закрытым ключом, вместе с Public это noise.Static; Fetch: F во временное пользование; Take: передаёт ключи вызывающему, после неё Agree отказывает. Закрытый ключ под RWMutex, как у noise.KeyPair |
| `Clean(path)` | удаляет `<path>.tmp`: оставшийся от создания, которое убили до ссылки, или файл создания по тому же пути, идущего в этот момент, и это создание тогда не удаётся |

- Свой буфер у каждой попытки нужен потому, что на c25519 путь AVX2 при неверном теге зануляет
  выход: неудачная попытка зануляет свой буфер, а не чужой. Обе области пробуются всегда,
  поэтому работа не зависит от того, какая область открылась; вывод личности идёт только после
  успешного открытия.

| Ошибка | Когда |
|---|---|
| ErrNotVault | размер файла не 8224 или это не обычный файл |
| ErrNoVolume | не открылась ни одна область: неверный пароль, тома нет, другой набор, изменённая соль или изменённая область; одна ошибка на все эти случаи |
| ErrCorrupt | открылись обе области, длина 0 или больше 4046, ненулевой хвост; при открытии отказ выборки ключа (crypto.ErrNoScalar) или нулевой F |
| ErrExists | файл по пути уже есть, до записи или при ссылке; он не тронут |
| ErrSamePassword | у двух томов один пароль |
| ErrTooLarge | Fill вернул длину больше MaxContent |
| ErrWritten | Write после того, как этот Draft уже создал ссылку на файл; с причиной, Write, у которого ссылка удалась, а следующий шаг нет: файл по пути есть, Draft израсходован |
| ErrEmpty | записанный том без содержимого |

- Пароль, который нарушает правила провайдера, это crypto.ErrBadPassword. ErrNoScalar и нулевой
  F (каждый около 2^-128 или реже) при создании дают ошибку без файла; повторов нет, создание
  запускают заново. Прочие ошибки провайдера и secmem, в том числе нехватка памяти под mlock,
  отдаются как есть, а не как ErrCorrupt: исправный контейнер не выглядит испорченным.
- Обе области открываются только при равных паролях, а Prepare их исключает.

### Одна запись

- Файл пишется ровно один раз, при создании, когда у каждого тома есть карточка контакта.
  Записи после создания в API нет, Open только читает. Поэтому все состояния файла после
  создания совпадают байт в байт, а число и момент записей не зависят от числа томов.
- Запись: оставшийся `<path>.tmp` удаляется, а существующий файл отвергается ErrExists до любой
  записи; новый tmp создаётся с O_CREATE|O_EXCL и правами 0600, получает 8224 байта, fsync и
  close; затем `os.Link(tmp, path)`: если файл по пути тем временем появился, ErrExists, и этот
  файл не тронут; tmp удаляется (tmp, которого уже нет, считается удалённым), на Linux fsync
  каталога.
- Первая попытка, дошедшая до tmp, закрепляет байты файла в Draft: первый том запечатывается
  один раз, и попытка после ошибки записи или ссылки пишет те же 8224 байта. Поэтому блоки,
  которые неудачная попытка оставляет на диске, хранят ту же версию, что и файл, а не другую
  версию этого контейнера.
- Жёсткая ссылка не заменяет файл, поэтому существующий контейнер не перезаписывается.
  Предполагается одно создание на путь за раз: каждый запуск начинается с Clean, а он удаляет
  `<path>.tmp`, поэтому запуск, который пересёкся с созданием по тому же пути, срывает это
  создание, а два пересёкшихся создания могут не удаться оба.
- Остаток `<path>.tmp` от создания, убитого до ссылки, это другой контейнер с другой солью, а не
  версия этого: следующий запуск делает новый Prepare. Его удаляет Clean при следующем запуске;
  блоки на диске удаление не стирает (LIMITATIONS).
- Цена: смена контакта это новый контейнер, новая личность и новое знакомство, а карточка
  контакта второго тома нужна уже при создании.

### Профиль клиента (vault/profile)

Том хранит `u8 версия = 1 | каноническая карточка контакта`, не больше 339 байт.

| Функция | Что делает |
|---|---|
| `New(p, mailbox, contact)` | Fill для Prepare: строит свою карточку из личности тома (набор, mailbox, QueueID(F), открытый ключ) и проверяет её круговым разбором. Контакт, если дан, проверяется так же, как при PUT /contact (подраздел "Клиент -peer"): тот же набор и mailbox, не свой ключ и не своя очередь, ключ принимает пробное согласование (обмен e2e/check). Пишет версию и карточку контакта; без контакта не пишет ничего, а это допустимо только для первого тома до Write |
| `WithContact(p, own, contact)` | Fill для Draft.Write, когда личность уже взята: сверяет контакт со своей карточкой по открытым значениям, проверяет его ключ пробным согласованием с одноразовой парой (обмен e2e/check) и пишет версию и карточку |
| `Parse(p, volume)` | версия 1 и L больше 1; карточка каноническая и набора провайдера; не свой ключ и не своя очередь. Затем ключи переходят в профиль (Take), а своя карточка строится с адресом контакта. Любой отказ разбора содержимого это ErrCard |
| `Profile.Fit(mailbox)` | адрес карточки контакта равен -mailbox |
| `Profile.Identity(p)` | личность сквозного слоя (e2e.Identity) поверх пары профиля; ключом владеет профиль |
| `Profile.Close()` | освобождает ключ личности и F |

- Нулевая очередь (около 2^-128) это ошибка профиля: New отказывает, и Prepare не создаёт
  файла, а Parse отвечает ErrCard.
- Адрес своей карточки равен адресу карточки контакта: выход закреплён на mailbox, поэтому свой
  адрес в томе не хранится.

### Команды jimichi vault

| Команда | stdin | Действие |
|---|---|---|
| `jimichi vault init -suite S -mailbox ADDR -contact CARD [-contact CARD] FILE` | нет | один том на каждый -contact, не больше двух; формальные проверки каждой карточки (каноническая, набор -suite, адрес -mailbox, у двух карточек нет общего ключа и общей очереди) и отказ при существующем файле идут до растяжения пароля, а ключ контакта и совпадение со своей карточкой проверяются после вывода личности, до записи; пароли команда генерирует сама (16 байт crypto/rand, base32 без дополнения, 128 бит) и после удачного Create печатает в stdout по одному на строку в порядке -contact, один раз; затем `created` в stderr. Создание, которое не удалось после ссылки, удаляет файл: после ошибки нет ни файла, ни пароля |
| `jimichi vault init ... -stdin FILE` | пароли построчно | свои пароли; в stderr предупреждение, что для них утверждение о втором томе не заявляется |
| `jimichi vault show -suite S FILE` | пароль | своя карточка, выведенная из пароля, её card_hash, адрес mailbox и card_hash контакта, строками `card=<набор>:<base64>`, `card_hash=`, `mailbox=`, `contact_card_hash=`; ни номера области, ни числа томов |

- Пароль читается из stdin прямо в буфер secmem до \n или до конца ввода, завершающий \r
  снимается; правила байтов те же, что у PasswordKey (CRYPTO, "Интерфейс").
- Каждый запуск сначала вызывает Clean. Цена растяжения всегда производственная.
- -keymem и -harden те же, что у enroll: если блокировка памяти запрошена, но не работает,
  команда не берёт пароль. На хосте Windows нужны `-keymem zero -harden=false`, и команда
  предупреждает, что пароль, растяжение и ключи могут уйти в pagefile.sys и hiberfil.sys; путь с
  блокировкой работает в WSL2.
- Ошибки show в stderr теми же классами, что у открытия тома: `vault: no volume opens with this
  password`; `vault: the volume is corrupt` (ErrCorrupt и отказ разбора содержимого);
  `vault: not opened: memory: ...` при ошибке secmem и `vault: not opened: io: ...` при прочих.
  Файл другого размера даёт `vault: not a container`.
- show одним паролем дважды даёт одну карточку, новый контейнер с тем же паролем другую.

### Свойство и проверка

Что заявляется и при каких допущениях, записано в CRYPTO ("Контейнер") и THREAT_MODEL
("Контейнер клиента"), границы в LIMITATIONS. Различитель одного и двух томов с контролями и
трасса состояний файла в плане (EXPERIMENT, блок 5). Статистические наборы вроде NIST STS
доказательством не служат: они могут показать, что файл отличается от случайных данных, но не
что он от них неотличим.

## Развёртывание

- deploy/kind: конфигурации кластера kind, cluster.yaml для стенда (управляющий узел и два
  рабочих) и ci.yaml для CI (один узел). API-сервер стенда слушает 127.0.0.1:16443, ниже
  динамического диапазона портов 49152-65535: Windows после перезагрузки резервирует блоки этого
  диапазона, и управляющий узел, чей порт попал в такой блок, не стартует. kind закрепляет порт хоста при
  создании кластера, поэтому смена порта действует только на новом кластере.
- deploy/base: пространство имён jimichi, пять relay (relay-1 ... relay-5), каждый как
  Deployment со своим Service и с -exit mailbox, и два клиента -peer, client-a и client-b,
  которые перечисляют все пять, держат очереди на mailbox relay-5 и выбирают цепочки из трёх с
  выходом на нём. client-a шлёт сообщение каждые 2 с, client-b отвечает на каждое (-respond).
  Счётчики mailbox остальных relay остаются нулевыми, это проверяет scripts/e2e.sh. Томов нет,
  корневая файловая система только для чтения, пользователь 65532, seccomp RuntimeDefault, все
  capabilities сброшены; relay и клиенты оставляют только IPC_LOCK для mlock.
- Клиенты разворачиваются со стратегией Recreate и селектором `{app: client, client: a|b}`:
  каждый pod это новая личность, поэтому двух подов одного клиента не бывает. Селектор
  Deployment не меняется, поэтому `make deploy` удаляет client-a со старым селектором `{app:
  client}` перед применением манифеста, а scripts/e2e.sh удаляет обоих клиентов в начале.
- scripts/introduce.sh знакомит клиентов: с RESTART=yes (по умолчанию) перезапускает обоих, читает
  из журнала текущего контейнера каждого ровно одну строку card_hash=, ждёт строки admin listening,
  через port-forward на локальные порты 19401 и 19402 забирает карточки с GET /card, сверяет хэш
  каждой (`jimichi card-hash`) со строкой журнала того же контейнера, доставляет каждую PUT /contact
  другому клиенту, ждёт 10 с строк contact pinned и проверяет, что ни один контейнер не
  перезапустился за это время. Любой сбой начинает попытку заново с перезапуском, после трёх
  выход 1. Перезапуск любого клиента даёт новую личность, поэтому enroll, deploy, start и e2e.sh
  вызывают знакомство сами.
- В манифестах нет ни одного Secret: ключи узлов создаются в памяти процесса, и больше узел их
  нигде не хранит: ни в Secret, ни в томе, ни в файле. Заблокированы только буферы secmem: копии,
  которые библиотеки держат на куче, не заблокированы, и попадут ли они в swap, зависит от хоста
  ([#36](https://github.com/jimichi-org/jimichi/issues/36)). В кластер попадает только открытый
  якорь, в ConfigMap jimichi-ca.
- УЦ работает вне кластера: `jimichi enroll` (cmd/jimichi) через scripts/enroll.sh на машине
  оператора или раннере CI.
- Узлы разворачиваются со стратегией Recreate, поэтому у каждого Deployment ровно один живой pod
  и выдача находит именно его. Флаги -name и -advertise задают имя и адрес в сертификате, адрес
  совпадает с тем, который знает клиент.
- Узлы запускаются с -onion-rotate 1h и -descriptor-ttl 20m: льготный период 22 мин, поэтому
  остальные 38 минут каждого часа узел держит один онион-ключ.
- deploy/base/network.yaml: сетевая политика пускает к порту ячеек каждого relay только поды
  клиентов и поды relay; информационный порт открыт для пространства имён, а port-forward,
  которым идут выдача сертификатов и счётчики, через неё не проходит. Политика действует только
  там, где сетевой плагин кластера применяет сетевые политики: scripts/e2e.sh проверяет это из
  пода, который не клиент и не relay, в CI без неё падает, а на машине разработки, где плагин
  её не применяет (например, kindnet под WSL2), только предупреждает.
- Скрипты (enroll, e2e, stats, redeploy) берут relay из Deployment с меткой app=relay, поэтому
  их число задаёт один манифест. Метка hop только различает relay: любой relay занимает любое
  место в цепочке, у клиентов стенда выход закреплён на relay-5.
- Service каждого relay открывает порт ячеек 9000 и информационный порт 9100. Клиент использует
  оба порта только у своего входа; узлы обращаются к информационному порту каждого узла ростера
  за дескрипторами соседей и к порту ячеек следующего узла цепочки.
