# Программа исследования

[English](../en/EXPERIMENT.md) | Русский

Работа отвечает на один вопрос: **какой ценой в полосе и задержке покупается стойкость к анализу
трафика в трёхузловой цепочке с постоянным размером ячейки, и где эта стойкость перестаёт
работать**. Остальное подчинено ответу на него.

Каждый прогон воспроизводим: в отчёт пишутся конфигурация, зерно генератора, версия кода и время.
Результаты в artifacts/, графики строятся из тех же файлов.

Реальные клиенты запускаются в несвязанные моменты, поэтому в обвязке lab расписание каждого клиента
получает случайную фазу из зерна прогона. Клиенты, запущенные подряд, тикали бы почти в одной
фазе и давали атаке ничьи, которых в настоящей сети нет. Окно наблюдения тоже открывается в
случайный момент относительно расписаний: иначе последний запущенный клиент тикал бы в такт окнам.

Зёрна: из базового зерна серии выводится зерно каждого повтора, из него отдельные потоки для фаз
клиентов и для интервалов каждого потока (splitmix64). Соседние повторы и потоки не делят
случайных последовательностей. Цепочки, которые выбираются в блоке 3, берутся из своего потока,
выведенного из зерна так же. Фазы часов узлов берутся не из зерна, а из генератора самого узла,
как в настоящем развёртывании. В каждой строке отчёта записаны конфигурация, зёрна, ревизия
кода и загрузка хоста до и после прогона.

## Модели нарушителя

Обозначения используются во всех таблицах результатов. Пока измерены: П1 атакой корреляции
числа ячеек (блок 1) и выбор цепочек для П4 (блок 3). Эксперименты для П3, П5 и П6 в плане,
см. статус каждого блока; у П2 своего блока пока нет.

| Код | Нарушитель | Что видит и может |
|---|---|---|
| П1 | Пассивный на обоих плечах | временные метки и размеры пакетов на участках клиент-первый узел и последний узел-получатель. Получателя пока нет ([#18](https://github.com/jimichi-org/jimichi/issues/18), [#47](https://github.com/jimichi-org/jimichi/issues/47)): наблюдатель обвязки берёт вместо дальнего плеча канал к последнему узлу, а последний узел возвращает сообщение эхом |
| П2 | Пассивный на одном плече | то же, но только на входе цепочки |
| П3 | Активный сетевой | задерживает, дублирует и отбрасывает ячейки, встраивает временную метку в поток |
| П4 | Компрометация узлов | полный доступ к части узлов, включая память процесса: к одному или двум из трёх узлов цепочки, к k из N узлов, из которых клиент выбирает цепочки |
| П5 | Локальный на устройстве | доступ к памяти и диску узла или клиента во время работы и после |
| П6 | Локальный с историей | несколько снимков файла контейнера в разные моменты времени |

Нарушитель знает устройство системы и исходный код. Стойкость держится на ключах и статистической
неразличимости, а не на секретности реализации.

## Метрики

### Связывание отправителя и получателя

| Метрика | Определение | Зачем нужна |
|---|---|---|
| ROC AUC | площадь под кривой ошибок атаки связывания; пара с равными оценками у верной и неверной пары считается за половину | сводный показатель, сравним между конфигурациями |
| Точность top-1 | доля входных потоков, у которых выходной поток с наибольшей оценкой их собственный; если наибольшую оценку делят k выходных потоков и свой среди них, поток даёт 1/k | что получает нарушитель, который выбирает лучшую пару |
| TPR при FPR 0.01 | доля верно связанных пар при фиксированной доле ложных | атака опасна именно в области малых ложных срабатываний |
| Точность при базовой ставке (в плане) | доля верных среди положительных решений при реальном числе потоков | защищает от подмены понятий: при тысяче потоков AUC 0.9 для нарушителя почти бесполезна |
| Степень анонимности (в плане) | отношение энтропии апостериорного распределения отправителей к максимальной | стандартная мера, сравнима с литературой |
| Размер множества анонимности (в плане) | число кандидатов, неотличимых для нарушителя | наглядно на защите |

Обвязка считает ROC AUC, точность top-1 и TPR при FPR 0.01. Три метрики с пометкой «в плане» пока
не считаются ([#119](https://github.com/jimichi-org/jimichi/issues/119)).

### Скомпрометированные цепочки

| Метрика | Определение |
|---|---|
| Доля цепочек с подставными входом и выходом | доля цепочек, у которых и первый, и последний узел подставные, то есть принадлежат нарушителю, который тогда связывает два конца цепочки; цепочка из одного узла считается, когда этот узел подставной. Равновероятный выбор h разных узлов из N, k из которых подставные, даёт k(k-1)/(N(N-1)), а при h = 1 даёт k/N |
| Доля цепочек с подставным узлом | доля цепочек, в которых есть хотя бы один подставной узел; равновероятный выбор даёт 1 - C(N-k,h)/C(N,h) |
| Доля отказов | доля попыток построить цепочку, в которых вход отдал зеркало, от которого клиент отказывается: в нём нет больше min(-missing, N - h) узлов списка; комплект, не прошедший проверку, считается отсутствующим |
| Доля попыток, сорвавшихся при установке | доля попыток, в которых клиент выбирает цепочку, которую узлы не устанавливают: честный узел продлевает цепочку только к узлу, проверенный дескриптор которого у него есть, поэтому цепочка, где честный узел стоит прямо перед узлом, не отдающим свой дескриптор, срывается. Две доли цепочек выше считаются по установленным цепочкам |
| Стандартная ошибка доли | sqrt(p(1-p)/n) для доли из n независимых попыток при значении p, которое даёт модель; n это число установленных цепочек, а для долей отказов и срывов число попыток |

### Неразличимость трафика

Статус: в плане, не реализовано ([#119](https://github.com/jimichi-org/jimichi/issues/119)). В
обвязке пока нет различителя ячеек с сообщением и фоновых, распределения интервалов не
сравниваются.

| Метрика | Определение |
|---|---|
| AUC различителя | классификатор отличает ячейку с сообщением от фоновой, ожидается 0.5 |
| Расстояние Колмогорова-Смирнова | между распределениями межпакетных интервалов реального и фонового потоков |
| Оценка полной вариации | верхняя оценка различимости двух распределений по выборке |

### Цена защиты

| Метрика | Определение |
|---|---|
| Множитель полосы | кадров на канале за окно наблюдения к числу сообщений, переданных клиентам. Считается отдельно для канала клиент-вход и для наблюдаемого канала между узлами, в каждую сторону. Окно открывается, когда потоки начинают слать, после того как установка каждой цепочки прошла все наблюдаемые каналы: установка цепочек и всё, что ушло до неё, не входит. Клиенты шлют, только пока окно открыто. Кадр в момент открытия окна входит, кадр в момент закрытия не входит. Сообщение, переданное перед самым закрытием окна, может пройти канал или вернуться уже после закрытия, поэтому отдельный прогон без защиты может показать там на кадр меньше на каждое такое сообщение, то есть множитель чуть ниже x1; такие прогоны редки, и медиана серии без защиты остаётся x1 |
| Полезная скорость (в плане, [#118](https://github.com/jimichi-org/jimichi/issues/118)) | байт полезной нагрузки в секунду на клиента |
| Задержка | медиана, 95 и 99 процентили. Обвязка lab измеряет круг: от передачи сообщения клиенту до прихода эха выхода, эхо сопоставляется с сообщением по номеру, а не по порядку |
| Стоимость ячейки | наносекунд процессора и аллокаций на снятие слоя |
| Стоимость сессии | наносекунд на согласование ключа, по наборам примитивов |

### Гигиена ключевого материала

Статус: в плане, не реализовано ([#24](https://github.com/jimichi-org/jimichi/issues/24)).
Обвязка пока не снимает дампы памяти и не записывает служебные ячейки. То, что заменённый
онион-ключ перестаёт открывать установки после освобождения, покрыто тестами узла; доля в
зависимости от возраста ячейки не измеряется.

| Метрика | Определение |
|---|---|
| Доля успешных извлечений | в какой доле из N попыток ключ найден в дампе |
| Окно жизни ключа | время от конца сессии до момента, когда ключ перестаёт находиться в памяти |
| Доля расшифрованного при краже ключей узла | проверка прямой секретности: ноль для записи с провода (каналы на эфемерных ключах); для соседа, сохранившего служебные ячейки, доля тех из них, чей слой открывается ключами из памяти узла, в зависимости от возраста ячейки в момент кражи. С ротацией онион-ключа ожидается единица, пока узел держит ключ ячейки, и ноль позже периода ротации плюс срок дескриптора плюс допуск часов; без ротации единица за всё время работы узла |

### Контейнер клиента

Статус: в плане, не реализовано ([#20](https://github.com/jimichi-org/jimichi/issues/20)). NIST
STS и энтропия показывают только отсутствие статистической структуры в шифротексте и не
показывают отрицаемость второго тома. Это задача различителя томов.

| Метрика | Определение |
|---|---|
| Доля пройденных тестов NIST STS | из 15 тестов набора, выборка не менее 100 контейнеров |
| Энтропия на байт | оценка по выборке, ожидается близко к восьми |
| AUC различителя томов | классификатор отличает контейнер с одним томом от контейнера с двумя, ожидается 0.5 |
| Стоимость перебора | параметры Argon2id, время открытия, оценка стоимости подбора пароля заданной энтропии |

## Блоки экспериментов

### Блок 1. Связывание потоков, нарушитель П1

Статус: реализовано частично. Обвязка проводит базовую атаку в сериях с фоновым трафиком,
постоянной скоростью клиента и отправкой узлов по своим часам; остальное в этом блоке в плане.

Базовая атака, реализована: корреляция Пирсона числа ячеек в окнах на канале клиент-вход и на
канале к последнему узлу, каждый входной поток против каждого выходного. Усиленная атака, в
плане: градиентный бустинг на признаках окна (число ячеек, дисперсия интервалов, длины пауз,
автокорреляция) с обучением на одной выборке и проверкой на другой, разделение по времени.
Коррелятор на глубоком обучении как самый сильный нарушитель тоже в плане
([#67](https://github.com/jimichi-org/jimichi/issues/67)).

| Фактор | Уровни |
|---|---|
| Фоновый трафик | нет, 0.5 от полезного, 1.0, 2.0 |
| Расписание клиента | сразу, постоянная скорость, где сообщение занимает слот фоновой ячейки |
| Размер ячейки | постоянный; переменный размер не реализован: у ячейки один размер и нет переключателя, поэтому фактор не измеряется. Классы размеров сообщений в плане ([#68](https://github.com/jimichi-org/jimichi/issues/68)) |
| Задержка на узле | нет, отправка по своим часам узла; равномерная, экспоненциальная и пакетирование по k ячеек в плане ([#45](https://github.com/jimichi-org/jimichi/issues/45), [#82](https://github.com/jimichi-org/jimichi/issues/82)) |
| Число одновременных потоков | 2, 5, 10, 20 |
| Набор примитивов | ГОСТ, X25519 |

План: сначала по одному фактору при прочих базовых, затем полный факторный план на подмножестве
уровней, где ожидается взаимодействие фона и задержек. Главный результат работы это кривая
«множитель полосы против AUC атаки»; доверительные интервалы по прогонам в плане вместе с полной
серией ([#23](https://github.com/jimichi-org/jimichi/issues/23)).

### Блок 2. Активный нарушитель П3, временная метка в потоке

Статус: в плане, не реализовано ([#116](https://github.com/jimichi-org/jimichi/issues/116)). В
обвязке нет активного нарушителя и детектора метки, а пакетирование на узлах, которое этот блок
проверит, тоже в плане ([#82](https://github.com/jimichi-org/jimichi/issues/82)). Из таблицы
ниже существуют только поля flow_closed и flow_closed_after в строках отчёта, серии по
отношению периодов в обвязке нет.

Нарушитель будет задерживать ячейки на входе по заданному шаблону и искать этот шаблон на выходе.
Атака сильнее пассивной корреляции и проверит, помогает ли пакетирование.

| Что меряем | Метрика |
|---|---|
| Обнаружимость метки | AUC детектора метки на выходе |
| Порог стойкости | параметры пакетирования, при которых метка перестаёт обнаруживаться |
| Цена стойкости | прирост задержки доставки, которым это оплачено |
| Живучесть цепочки | доля цепочек, открытых к концу прогона, и время до первой закрытой цепочки в зависимости от отношения периода узла к периоду клиента, по полям flow_closed и flow_closed_after строк отчёта; одна потерянная или переставленная ячейка закрывает цепочку |

### Блок 3. Компрометация узлов, нарушитель П4

Статус: реализовано частично. Измеряется выбор цепочки (`cmd/lab -set paths`). Остальные
сценарии в плане ([#117](https://github.com/jimichi-org/jimichi/issues/117)): в обвязке нет
сценария со скомпрометированным или подставным узлом, а повтор и подмена ячейки покрыты тестами
узла и клиента, но не измеряются как доля.

| Сценарий | Метрика |
|---|---|
| Один узел из трёх | что доступно узлу: соседи, содержимое, доля восстановленного маршрута |
| Первый и последний узлы | доля верно связанных пар, время до связывания |
| Средний и один крайний | то же, для сравнения с предыдущим |
| Подставной узел с валидным сертификатом | доля перехваченных сессий, доля расшифрованного |
| Выбор цепочки при k подставных узлах из N | доля цепочек с подставными входом и выходом и доля цепочек с подставным узлом среди установленных цепочек из тех, что выбраны функцией выбора самого клиента, против значений, которые даёт модель: при полных зеркалах, при подставных входах, исключающих честные узлы из своих зеркал, и при подставных узлах, не отдающих свои дескрипторы |
| Упорядоченные пары узлов, занятые с одного адреса (в плане, [#125](https://github.com/jimichi-org/jimichi/issues/125)) | доля выживших цепочек с подставными входом и выходом и с подставным узлом против числа адресов и цепочек, которые тратит нарушитель (LIMITATIONS, ограничения узла) |
| Повтор и подмена ячейки | доля повторённых, переставленных или изменённых ячеек, которые не проходят дальше первой стороны, способной их проверить: вперёд это первый узел, который их видит (ячейка не по порядку закрывает цепочку, изменённая отбрасывается); назад порядок проверяет первый узел, а изменённое тело ответа только клиент, который закрывает цепочку; ожидается сто процентов |

Блок должен показать, какая доля компрометации цепочки уничтожает свойство и совпадает ли это с
теоретической вероятностью выбора скомпрометированной цепочки.

Выбор цепочки измеряется без трафика и без узлов. `cmd/lab -set paths` делает -samples попыток
выбрать цепочку из -hops узлов среди -nodes так же, как клиент, его собственными функциями
выбора входа, приёма зеркала или отказа от него и выбора остальной цепочки, на потоке,
выведенном из -seed, вместо системного генератора: вход среди всех узлов, отказ, когда в его
зеркале нет больше min(-missing, N - h) из них (это граница), остальные хопы среди узлов,
которые есть в зеркале. Выбранная цепочка затем устанавливается, когда каждый её узел продлевает
цепочку к следующему, и здесь обвязка применяет правило узла: честный узел продлевает только к
узлу, дескриптор которого у него есть, подставной к любому. Подставными считаются первые -rogue
узлов, и действуют они сообща:

| Флаг | Что делают подставные узлы | Что это меняет в цепочках |
|---|---|---|
| -leftout o | каждый из них как вход исключает из своего зеркала o честных узлов | выход при подставном входе выбирается из N - o - 1 узлов, k - 1 из которых подставные |
| -withhold w | w из них не отдают свои дескрипторы честным узлам | в зеркале честного входа нет w узлов: в пределах границы его цепочка выбирается среди N - w узлов, которые в зеркале есть, сверх неё попытка получает отказ. Ни один честный узел не продлевает цепочку к узлу, не отдающему дескриптор, поэтому цепочка, выбранная через подставной вход, срывается при установке, когда честный узел стоит прямо перед таким узлом |

Когда оба равны 0, как по умолчанию, все зеркала полные, все цепочки устанавливаются и выбор
равновероятный. Попытка кончается одним из трёх исходов: отказ, срыв цепочки при установке,
установленная цепочка. Отчёт даёт доли отказов и срывов и, по установленным цепочкам, обе доли
цепочек, каждую рядом со значением, которое даёт модель, и стандартной ошибкой доли при этом
значении, а рядом значения равновероятного выбора. Конфигурация, в которой ни одна попытка не
даёт установленной цепочки, не принимается: цепочек, по которым считать долю, нет. В строке
отчёта записаны nodes, hops, rogue_nodes, missing, left_out, withheld, samples, seed и rev,
поэтому ту же выборку можно получить снова. Файл отчёта назван по всем этим значениям, кроме
rev, и по секунде записи, поэтому два прогона в пределах одной секунды затирают друг друга,
только когда не отличаются ничем, кроме rev.

Строки, полученные при одном зерне, читают один и тот же поток: пока ни одна попытка не
получает отказ, входы в них одни и те же, а честный вход с полным зеркалом выбирает одну и ту
же цепочку. Такие строки не являются независимыми выборками, и их доли могут совпасть до
последнего знака: при -leftout в пределах границы и без -withhold доля цепочек с подставным
узлом по выборке та же, что при полных зеркалах и том же зерне. Строки, которые нужны как
независимые выборки, берутся при разных зёрнах.

Значения, которые даёт модель, считаются точно, цепочки подставного входа суммированием по
виду узла на каждой позиции, и проверены в тестах метрики перебором по одной всех цепочек,
которые клиент может выбрать. Доля по выборке отличается от своего значения примерно на
стандартную ошибку. Там, где значение равно 0 или 1, доля точна по построению: каждая попытка
даёт один и тот же ответ, доля по выборке равна значению при любом зерне и любом числе попыток,
стандартная ошибка равна 0, и о выборе такая строка ничего не говорит. Частые случаи:

| Строка | Точная доля |
|---|---|
| подставных узлов нет или подставные все | обе доли цепочек, 0 или 1 |
| один подставной узел, цепочки из двух узлов и больше | подставные вход и выход, 0 |
| два подставных узла, оба не отдают дескрипторы, цепочки из трёх узлов и больше | подставные вход и выход, 0: перед выходом стоит честный узел, и он к нему не продлевает |
| честных узлов меньше, чем хопов | подставной узел, 1 |
| зеркала честных входов получают отказ (-withhold выше границы) | подставной узел, 1 |
| зеркала подставных входов получают отказ (-leftout выше границы) | подставные вход и выход, 0 |
| ни в одном зеркале не пропущено больше границы | отказы, 0 |
| ни один узел не скрывает дескриптор, или цепочки из одного или двух узлов | срывы при установке, 0 |

Печатная строка даёт четыре знака после запятой. Значение, которое они округлили бы до 0 или 1,
печатается с двумя значащими цифрами его расстояния до этого края, поэтому напечатанные 0.0000 и
1.0000 это ровно 0 и 1. Выборочная доля тоже может оказаться ровно 0 или 1: точна по построению
только та доля, у которой и скобка читается 0.0000 или 1.0000 +- 0.0000.

При N = 5, k = 2 и h = 3 упорядоченных цепочек 5 * 4 * 3 = 60. У шести подставные узлы на обоих
концах (2 варианта входа, второй подставной узел как выход, любой из 3 честных узлов между
ними): 6/60 = 0,1 = k(k-1)/(N(N-1)). В шести нет подставного узла (три честных узла в любом
порядке), значит в 54/60 = 0,9 = 1 - C(3,3)/C(5,3) он есть. Тест метрики перебирает все 60
цепочек и требует ровно эти значения.

При -leftout 1 в той же конфигурации подставной вход отдаёт четыре узла и выбирает два
следующих хопа из трёх остальных: 3 * 2 = 6 цепочек, две из которых кончаются вторым подставным
узлом. Честный вход отдаёт все пять: 4 * 3 = 12 цепочек, в десяти из них есть подставной узел.
Входом с вероятностью 1/5 становится любой узел, поэтому оба конца подставные с вероятностью
2/5 * 2/6 = 2/15 против 0,1 при полных зеркалах, а подставной узел есть в
2/5 + 3/5 * 10/12 = 0,9 цепочек, как и прежде. Свой дескриптор здесь никто не скрывает, поэтому
все цепочки устанавливаются.

При -withhold 2 и -missing 1 в зеркалах трёх честных узлов нет двух узлов, и они получают
отказ, 3/5 попыток. Каждая цепочка, которую выбирает клиент, входит через подставной узел,
который отдаёт все пять: 12 цепочек. В трёх из них честный узел стоит перед вторым подставным,
дескриптора которого у него нет, и цепочка срывается при установке: 2/5 * 3/12 = 1/10 попыток.
Остальные девять устанавливаются, 3/10 попыток, и каждая кончается честным узлом. Значит, среди
установленных цепочек подставной узел есть в каждой, а подставных входа и выхода нет ни в
одной, тогда как сам выбор, до установки, даёт 3/12 = 1/4: скрывая дескрипторы, два узла
забирают все входы и теряют выход. При -withhold 1 отказов нет, срывается 1/20 попыток, а среди
установленных цепочек у 1/19 подставные вход и выход и в 15/19 есть подставной узел. Цепочки
этих случаев тесты тоже перебирают.

Серии корреляции блока 1 идут с числом узлов, равным числу хопов, в порядке, который обвязка
задаёт сама: выбор цепочки в них не участвует. Обвязка запускает узлы и клиентов в одном
процессе и соединяет их через loopback, а не в кластере, поэтому сетевой задержки между ними
нет. Её узлы работают без сертификатов, с анонимными каналами между узлами, без ротации
онион-ключа и с выключенными ограничениями на один адрес, а последний узел возвращает каждое
сообщение эхом.

### Блок 6. Производительность и стоимость примитивов

Статус: реализовано частично. Замеры go test -bench есть для генерации ключа, согласования ключа,
подписи, проверки подписи, одного слоя AEAD ячейки, хэша транскрипта, вывода ключей хопа и
сцепления двух согласований на обоих наборах (crypto/suite) и для шифрования ячейки и снятия слоя
на c25519 (wire). Обвязка выдаёт круговую задержку для цепочек
из двух и более узлов. В плане ([#118](https://github.com/jimichi-org/jimichi/issues/118)): замер
установки на узле с одним и с двумя онион-ключами, пропускная способность узла при насыщении,
полезная скорость на клиента, задержка для цепочки из одного узла (обвязка не принимает меньше двух
хопов) и вклад mlock (у обвязки и у замеров нет переключателя мер защиты памяти).

| Что меряем | Как |
|---|---|
| Согласование ключа | go test -bench, наносекунд на операцию, ГОСТ против X25519 |
| Установка в льготный период | наносекунд на установку на узле с одним и с двумя онион-ключами, ГОСТ против X25519: второй ключ стоит второго согласования, и платится оно только в льготный период, 22 минуты каждого часа на стенде |
| Снятие слоя | наносекунд и аллокаций на ячейку |
| Пропускная способность узла | ячеек в секунду при насыщении, на 1, 2 и 4 ядрах |
| Задержка по хопам | один, два, три узла; p50, p95, p99 |
| Вклад mlock | те же метрики с блокировкой памяти и без |

У привязки каждого выводимого ключа к транскрипту, набору и версии схемы переключателя нет, как
нет его у метки повтора установки и у кадра подтверждения канала: сборка без неё была бы второй
схемой вывода ключей, то есть путём понижения защиты. Её вклад не меряет ни один блок. Замеры
crypto/suite берут её части по отдельности: хэш транскрипта установки аутентифицированного
узла, с ключом личности (BenchmarkNewContext; клиент считает его по одному на хоп, узел по
одному на каждый онион-ключ, который он держит; рукопожатие канала хэширует свой транскрипт
другой длины, отдельно он не замеряется),
согласование под контекстом (BenchmarkAgree),
пять значений, которые хоп выводит после согласования: ключ установки, ключ ячейки, метка
повтора и два смещения counter (BenchmarkDeriveHopKeys), и сцепление двух согласований
аутентифицированного канала (BenchmarkMixKey). В релизе v0.2.0, последнем без привязки, для
сравнения есть только замер согласования.

## Статистика

- Цель для полной серии ([#23](https://github.com/jimichi-org/jimichi/issues/23)): не менее 30
  чистых повторов на точку (без закрытых цепочек и без сработавших лимитов узла, в отчёте это
  clean_runs). Опубликованная серия предварительная, повторов на точку в ней меньше. Окно
  наблюдения открывается, когда потоки начинают слать, поэтому установка цепочек в него не
  входит; отдельный прогрев не отбрасывается.
- Серии гоняются на свободном хосте: параллельная нагрузка сбивает тайминги и занижает AUC
  отдельных прогонов. В таблицах приводится медиана.
- Внутри прогона у AUC есть доверительный интервал 95 процентов: бутстрэп BCa по потокам, 10000
  выборок. По повторам сводка даёт медиану, минимум и максимум; интервал для медианы по повторам
  в плане вместе с полной серией ([#23](https://github.com/jimichi-org/jimichi/issues/23)).
- В плане вместе с полной серией ([#23](https://github.com/jimichi-org/jimichi/issues/23)):
  сравнение конфигураций критерием Манна-Уитни на уровне 0.05, обязательно с размером эффекта
  (дельта Клиффа), значимая, но ничтожная разница указывается как таковая; поправка Холма на
  множественные сравнения; оценка объёма выборки для обнаружения разницы AUC в 0.05 при мощности
  0.8 перед серией.
- У реализованной атаки нет обучения. Обучаемая атака, когда она появится, будет обучаться и
  проверяться на разных выборках, с разделением по времени и без утечки признаков.
- Узел закрывает цепочку, если counter нарушил порядок (копия, пропуск, шаг назад, скачок, у
  выхода первый прямой counter не тот, что в его слое установки), ячейке не хватило места в
  очереди в любую сторону, назад пришла ячейка другого вида или такая, которую он не может
  обернуть, выход не смог зашифровать ответ по любой причине, кроме длины (ответ длиннее ячейки
  уходит фоновым под тем же номером), ячейку не удалось записать в канал к следующему узлу или
  обратно к клиенту. Запись в канал, который узел сам закрыл, закрывая цепочку, повторно не
  учитывается. Клиент закрывает цепочку при ответе с негодным заголовком, ответе, который не
  открылся, ответе не по порядку, ответе сверх числа записанных ячеек и кадре канала от входа,
  который не открылся. Такой кадр может создать любой на линии между клиентом и входом, поэтому
  отклонённый кадр не указывает на вход. Поток тогда останавливается раньше конца прогона, и его
  трассы короче. Поток, чья цепочка закончилась, больше не передаёт клиенту сообщений, поэтому
  messages, drop_rate и unanswered разорванного прогона считаются только до её закрытия.
- Строка отчёта несёт relay_broken_circuits (сумма закрытий, замеченных каждым узлом: одну цепочку
  могут посчитать несколько узлов), broken_flows (клиенты, отклонившие ответ или кадр канала) и
  по каждому потоку flow_closed и flow_closed_after: закрылась ли цепочка до конца прогона, по
  данным клиента и по любой причине, и через сколько после старта потоков ("" для открытой).
  Из полей клиента цепочка, которую закончил узел или противоположная сторона, видна в
  flow_closed, а не в broken_flows.
- Строка несёт также relay_timed_out (истёкшие сроки рукопожатия, установки и записи),
  relay_expired (цепочки, закрытые по простою или возрасту) и relay_refused (соединения и
  установки, в которых узлы отказали), в сумме по узлам. Прогон ограничен, если хоть одно из них
  ненулевое: то, что он потерял, он потерял из-за ограничения узла, а не из-за проверяемой
  конфигурации. Истёкший срок записи закрывает цепочку, поэтому он виден и в relay_timed_out, и в
  relay_broken_circuits.
- Прогон разорван, если хоть один из признаков закрытия ненулевой. В сводке runs считает все
  прогоны, broken_runs разорванные, limited_runs ограниченные (прогон может быть и тем, и
  другим), clean_runs те, что ни то ни другое; медианы, размах и ci_degenerate_runs берутся по
  чистым прогонам. Если таких нет, эти поля null; медиана задержки null и тогда, когда у чистых
  прогонов нет ни одного замера. Строка с одним чистым прогоном даёт его значения, а не медиану,
  и печать сводки помечает её.
- relay_dropped_cells считает ячейки, которые узлы отбросили: ячейки, чей слой не открылся, с
  неразборчивым заголовком, для неизвестной цепочки, служебные ячейки неудавшейся или отклонённой
  установки (слой не открылся, копия уже виденной установки, полный кэш меток, занятый
  идентификатор, канал уже несёт цепочку, следующий узел недоступен), ответы длиннее ячейки
  (вместо них уходит фоновый ответ под тем же номером), ячейки, оставшиеся в очереди закрытой
  цепочки, и, когда узел пересылает сразу, ячейки к следующему узлу и ответы выхода, запись
  которых пришлась на канал, который этот узел уже закрыл сам. Запись, не удавшаяся по другой
  причине, закрывает цепочку и учитывается в relay_broken_circuits, а не здесь.

## Угрозы валидности

| Тип | Угроза | Что делаем |
|---|---|---|
| Внутренняя | нарушитель видит идеальные метки времени, которых нет в реальной сети | в плане: отдельная серия с сетевым шумом и джиттером ([#46](https://github.com/jimichi-org/jimichi/issues/46)); пока наблюдатель обвязки получает идеальные метки |
| Внутренняя | синтетическая нагрузка слишком регулярна | сообщения уходят с экспоненциальными интервалами, профиль один; модель с тяжёлыми хвостами и несколько профилей активности в плане |
| Внешняя | стенд на одной машине, серии идут в одном процессе через loopback, сетевые задержки не моделируются | абсолютные значения задержки относятся к loopback и на сеть не переносятся; профили эмуляции сети в плане ([#46](https://github.com/jimichi-org/jimichi/issues/46)) |
| Конструктная | AUC сам по себе не означает практическую атаку | рядом приводятся TPR при FPR 0.01 и точность top-1; точность при реальной базовой ставке в плане ([#119](https://github.com/jimichi-org/jimichi/issues/119)) |
| Воспроизводимость | случайность прогонов | фиксированные зерна, конфигурация и версия кода в каждом отчёте |
| Ошибка выжившего | медианы без разорванных прогонов и прогонов со сработавшим лимитом описывают прогоны, где все цепочки выжили; если закрытия зависят от конфигурации, например от периода узла, близкого к периоду клиента, её медианы описывают более удачные прогоны | рядом с каждой медианой стоят runs, broken_runs, limited_runs и clean_runs, а каждая строка отчёта записывает, какие цепочки закрылись и когда (flow_closed, flow_closed_after); серия живучести по отношению периодов в плане (блок 2) |

## Сравнение с аналогами

В плане: таблица по одинаковым признакам для Tor, Session, SimpleX, Briar и этой работы.
Признаки: постоянный размер ячейки, фоновый трафик, состояние на узле, отрицаемость, набор
примитивов, опубликованные оценки задержки. Из свойств отрицаемости в этой работе сейчас есть
только отрицание факта отправки при постоянной скорости и отсутствие ключей после сессии
(THREAT_MODEL); отрицаемая аутентификация ([#19](https://github.com/jimichi-org/jimichi/issues/19))
и контейнер клиента ([#20](https://github.com/jimichi-org/jimichi/issues/20)) в плане. Числа чужих
систем будут взяты из их документации и публикаций, свои будут измерены. Прямое сравнение
производительности проводиться не будет: условия разные, это будет указано явно.

1. Живая отправка сообщения через три узла. Панель «что видит каждый узел» в плане вместе с
   дашбордом ([#21](https://github.com/jimichi-org/jimichi/issues/21)).
2. Наблюдатель: атака связывания идёт без защиты и с каждой мерой по очереди. От фонового
   трафика поверх сообщений падения AUC не ожидается: в предварительной серии атаку почти к
   угадыванию привела только отправка узлами по своим часам ([README](../../README.ru.md)). Показ
   результата атаки вживую в плане вместе с дашбордом
   ([#21](https://github.com/jimichi-org/jimichi/issues/21)).
3. Кривая «множитель полосы против AUC». На опубликованном графике интервалов нет;
   доверительные интервалы по прогонам в плане вместе с полной серией
   ([#23](https://github.com/jimichi-org/jimichi/issues/23)).
4. В плане ([#24](https://github.com/jimichi-org/jimichi/issues/24)): поиск байтов ключа в дампах
   памяти с мерами защиты памяти и без них. Будет показан измеренный результат как есть; копии
   ключей, которые библиотеки держат на куче, перечислены в [CRYPTO](CRYPTO.md), раздел
   "Известные дыры".
5. В плане ([#20](https://github.com/jimichi-org/jimichi/issues/20)): контейнер, где один пароль
   открывает легенду, а второй настоящую историю. Результаты NIST STS рядом покажут только
   отсутствие статистической структуры в шифротексте, об отрицаемости они ничего не говорят.
6. Таблица стоимости: ГОСТ против X25519 по замерам go test -bench и круговая задержка для цепочек
   из двух и трёх узлов; остальное из блока 6 в плане
   ([#118](https://github.com/jimichi-org/jimichi/issues/118)).
